  키 수령 후 T3.x 에서 주소 검색으로 교체하면서 위경도 입력칸과 프리셋을 함께 걷어낸다.

## 소유권 헬퍼 (후속 task 재사용)

```ts
// apps/web/src/features/landlord/ownership.ts
type Guarded<T> = { data: T; response?: undefined } | { data?: undefined; response: Response };
type LandlordSession = { user: SessionUser; profile: Profile };   // profile.type === "LANDLORD"
type UnitWithBuilding = Unit & { building: Building };

findLandlordProfile(user: SessionUser): Profile | null              // 서버 컴포넌트용(응답 없이 판정만)
requireLandlord(): Promise<Guarded<LandlordSession>>                // 401 · 403
requireOwnedBuilding(l: LandlordSession, buildingId: string): Promise<Guarded<Building>>        // 404 · 403
requireOwnedUnit(l: LandlordSession, unitId: string): Promise<Guarded<UnitWithBuilding>>        // 404 · 403
```

```ts
const landlord = await requireLandlord();
if (landlord.response) return landlord.response;
const owned = await requireOwnedBuilding(landlord.data, id);
if (owned.response) return owned.response;
```

| 상황 | status · code |
|---|---|
| 비로그인·만료 세션 | 401 `UNAUTHORIZED` |
| 로그인했지만 임대인 프로필 없음 | 403 `FORBIDDEN` |
| 없는 건물·호실 id | 404 `NOT_FOUND` |
| **타인 건물·호실** | 403 `FORBIDDEN` |

- 임대인 프로필은 활성 프로필 쿠키가 아니라 **유형으로** 고른다(`@@unique([userId, type])` 라 최대 1개).
  세입자로 전환한 상태에서 API 를 불러도 결과가 같다.
- 화면(서버 컴포넌트)은 남의 자원을 `notFound()`(404)로 막고, API 는 403 을 준다 —
  최소 테스트가 "타인 건물 403" 을 요구하고, 화면은 존재 여부를 흘리지 않는 편이 낫다.

### `DELETE /api/buildings/[id]` · `DELETE /api/units/[id]`

성공하면 `204 No Content`. 건물을 지우면 호실은 `onDelete: Cascade` 로 함께 지워진다.

### `POST /api/buildings/[id]/units`

```jsonc
// 요청 — label 만 필수. floor·areaM2·rooms·note 는 선택(null 이면 비움)
{ "label": "301호", "floor": 3, "areaM2": 23.1, "rooms": 1 }
// 201 — 계약이 없으므로 항상 status "VACANT"
{ "unit": { …UnitSummary…, "status": "VACANT", "currentLease": null } }
```

| 실패 | status · code |
|---|---|
| **같은 건물에 같은 라벨**(`@@unique([buildingId, label])`) | 409 `CONFLICT` |
| 라벨 빈 값·범위 밖 숫자 | 400 `VALIDATION_ERROR` |

### `GET·PATCH /api/units/[id]`

```jsonc
// 200 — 그리드 셀(UnitSummary) + 건물·과거 계약·매물·수납 요약
{
  "unit": {
    …UnitSummary…,
    "building": { "id": "cmf0…", "name": "행당해피빌", "address": "서울 성동구 행당로 79" },
    "pastLeases": [ { …LeaseSummary…, "status": "ENDED" } ],
    "listing": {
      "id": "cmf0…", "dealType": "WOLSE", "deposit": 10000000, "monthlyRent": 500000,
      "status": "OPEN", "availableFrom": null, "createdAt": "2026-09-01T00:00:00.000Z"
    },
    "chargeSummary": {
      "totalCount": 4, "unpaidCount": 3, "overdueCount": 1,
      "unpaidAmount": 1315000, "latestMonth": "2026-09"
    }
  }
}
```

`PATCH` 본문은 `POST …/units` 와 같은 필드의 부분 집합이다(빈 본문이면 400). 라벨을 같은 건물의
다른 호실 라벨로 바꾸면 **409**. `chargeSummary` 는 **저장된 청구 컬럼의 단순 집계**다 —
연체료·이월 같은 원장 계산은 T1.4 소유라 여기서 만들지 않았다.

## 호실 상태 판정 규칙 (그리드 색)

`features/landlord/unit-status.ts` 의 `deriveUnitStatus` 한 곳에서만 판정한다. 위에서부터 먼저 맞는 것.

| 상태 | 판정 | 배지 tone(semantic) |
|---|---|---|
| `OVERDUE` 연체 | ACTIVE 계약 + **`RentCharge.status === 'OVERDUE'` 행 존재** | `danger` |
| `OCCUPIED` 계약중 | ACTIVE 계약 | `success` |
| `PENDING` 대기 | PENDING_TENANT 계약(세입자 미연결) | `warning` |
| `VACANT` 공실 | 진행 중 계약 없음(ENDED·CANCELLED 만 있어도 공실) | `neutral` |

- 색만으로 뜻을 전하지 않게 셀마다 상태 **라벨**을 같이 적는다(T0.6 원칙). 하드코딩 색상 0.
- ⚠️ **연체 판정은 임시 구현이다.** 지금은 OVERDUE 행 존재 여부만 본다.
  **T1.4(월세 원장 엔진) 머지 후 교체할 지점은 두 곳뿐이다:**
  1. `features/landlord/queries.ts` 의 `toUnitSummary` 안 `hasOverdueCharge: (active?.charges.length ?? 0) > 0`
  2. 같은 파일의 `toChargeSummary`(수납 요약 집계) → 원장 엔진의 요약 함수 호출로
- 그리드는 `repeat(auto-fill, minmax(120px, 1fr))` 이라 480px 셸에서 3열, 좁은 화면에서 2열이 된다.

## 삭제 규칙

**계약·매물·중개 요청이 걸리면 삭제할 수 없다 — 409 `CONFLICT`.** 판정은
`countUnitBlockers` + `blockingReason`(`features/landlord/queries.ts`) 한 곳에서 한다.

| 대상 | 막는 조건 |
|---|---|
| 호실 | 그 호실에 `Lease`(상태 무관, **ENDED·CANCELLED 이력 포함**) · `Listing` · `BrokerageRequest` 가 1건이라도 있으면 |
| 건물 | 그 건물의 **호실 중 하나라도** 위 조건에 걸리면 |

- 이력까지 막는 이유: 세 테이블 모두 호실을 필수로 참조하고 cascade 가 없어 지우면 FK 위반이 나고,
  무엇보다 **계약 이력은 남겨야** 하기 때문이다(정산·환급·분쟁).
- `CommuteCache` 는 cascade 라 함께 지워지고, `WorkOrder` 는 선택 참조라 null 로 풀린다.

## 머지 후 정리 (T1.4 원장 엔진 연결)

T1.1 작업 시점에는 원장 엔진이 아직 없어 호실 상태·수납 요약을 **저장된 `RentCharge.status` 컬럼**으로 판정했다. 그 컬럼은 크론이 하루 1회 갱신하므로 기한이 막 지난 청구는 아직 `SCHEDULED` 로 남아 있고, 원장 엔진으로 실시간 재판정하는 수납 탭(T1.5)·대시보드(T1.9)와 **최대 하루 어긋났다.** T1.2·T1.9 가 둘 다 같은 문제를 보고했다.

`features/landlord/queries.ts` 두 곳을 엔진 호출로 교체했다.

| 위치 | 전 | 후 |
|---|---|---|
| `currentLeasesInclude` + `toUnitSummary` | `status = OVERDUE` 행이 있는지 | 미납 청구를 `dueDate`·`totalDue`·`paidAmount` 와 함께 가져와 `resolveChargeStatus({ asOf: kstToday() })` 로 재판정 (`hasOverdueNow`) |
| `toChargeSummary` | 저장 컬럼 단순 집계 | `resolveChargeStatus` + `calcOutstanding` |

이제 자산 그리드·호실 상세·수납 탭·대시보드가 **같은 함수로 같은 답**을 낸다.
