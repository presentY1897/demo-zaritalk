## pull 과 push 는 데이터가 다른 곳에서 온다

| | 어디서 읽나 | 조건 | 정렬 | 누가 |
|---|---|---|---|---|
| **전체 피드**(pull) | `WorkOrder` 를 직접 훑는다 | `REQUESTED` + 내 업종 + 내 활동반경 안 | **거리순** | 전 마스터(무료 포함) |
| **추천받은 의뢰**(push) | 이미 만들어진 `WorkOrderTarget` 을 읽는다 | 나에게 발송된 것 | **최신 발송순** | 유료(PRO)만 |

피드는 **지금 이 순간의 계산**이고, 추천함은 **그때 보낸 기록**이다. 그래서 추천 카드의 거리는 발송 시점에 굳은 `WorkOrderTarget.distanceKm` 를 그대로 쓴다(마스터가 사무소를 옮겨도 "그때 이 거리라서 보냈다" 가 남는다).

반경 판정은 T5.1 이 만든 `lib/geo/distance.ts` 의 `rankByDistance` 하나로 한다 — 피드는 원점이 **마스터 사무소**, 후보가 **의뢰 건물**이라 push 매칭과 원점·후보가 뒤바뀐 모양이지만 거리 판정식은 같다.

## 선행 스키마 변경 (이 task 에서 마이그레이션 — [T5.1 문서](./t5.1-workorder.md#스키마-변경-이-task-가-만든-마이그레이션)에 전체 표)

마이그레이션 파일: **`packages/db/prisma/migrations/20260902092120_work_order_target_master_plan/migration.sql`**

- `enum MasterPlan { FREE PRO }`, `MasterDetail.plan`(기본 `FREE`) · `MasterDetail.planUntil DateTime?`
- `model WorkOrderTarget` — `BrokerageTarget` 과 동형: `workOrderId` · `masterProfileId` · `distanceKm` · `status`(`WorkOrderTargetStatus`) · `sentAt`, `@@unique([workOrderId, masterProfileId])`
- 시드: 최마스를 **PRO** 로 두고, 무료 마스터 **한마스**(01066666666 · 성수 · `INTERIOR`+`REPAIR` · 5km · FREE)를 추가해 pull/push 차이가 화면에 보이게 했다. 시드 의뢰 1건(행당해피빌 201호 REPAIR)과 최마스에게 간 추천 1건도 함께 넣었다.

> 한마스의 업종에 `REPAIR` 를 함께 둔 이유는 T5.1 문서의 시드 표에 적었다 — 업종이 하나도 겹치지 않으면 무료 마스터는 피드에서도 아무 것도 못 봐서 **pull/push 차이가 화면에 드러나지 않는다.**

## 플랜 규칙 — `features/master/plan.ts`

```ts
isProActive(plan, planUntil, now = new Date()): boolean
// FREE → 항상 false
// PRO + planUntil === null → true (만료 없음)
// PRO + planUntil >= now  → true (경계값 포함)
// PRO + planUntil <  now  → false ("결제가 끊긴 계정에 추천이 계속 가면 안 된다")

demoPlanUntil(plan, now): Date | null   // PRO 로 켜면 30일 뒤, FREE 면 null
```

**화면과 서버가 같은 판정을 쓴다.** 갈라지면 "PRO 인데 추천이 안 온다" 같은 거짓말이 화면에 남는다. `GET /api/master/targets` 의 `upgradeRequired`, `MasterHomeView` 의 업그레이드 안내, `matching.ts` 의 추천 대상 선정이 전부 이 함수를 읽는다.

**FREE 로 내려가도 과거 `WorkOrderTarget` 행은 지우지 않는다** — 발송 기록이므로 남기고 **조회에서만 가린다**.

## 플랜을 PRO 로 켜면 추천함을 **즉시 채운다**

추천은 원래 "의뢰가 생기는 순간" 발송된다. 그래서 유료로 갈아탄 직후에는 추천함이 비어 있고, 데모에서 유료의 값어치가 화면에 안 보인다. 그래서 `POST /api/master/plan` 이 `PRO` 를 받으면 `backfillTargetsForMaster`(T5.1 `features/workorder/matching.ts`)로 **지금 열려 있는 `REQUESTED` 의뢰 중 내 업종·반경에 맞는 것**을 한 번 훑어 추천을 채운다(최근 50건까지).

각 의뢰마다 `dispatchWorkOrderTargets` 를 그대로 부르므로 **의뢰당 거리순 10명 상한이 그대로 지켜지고**(내가 11번째로 먼 마스터면 채워지지 않는다) 중복 타겟도 생기지 않는다.

## 상세 접근 판정 — `getMasterWorkOrder`

볼 수 있으면 DTO, 아니면 `null`(화면은 `notFound()`). 둘 중 하나면 통과한다:

1. **나에게 추천으로 온 의뢰**(`WorkOrderTarget` 이 있다) — 상태·반경과 무관하다. 발송 뒤 사무소를 옮겨 피드에서 빠져도 받은 추천은 계속 열린다.
2. **내 피드에 들어오는 의뢰** — 업종이 맞고 내 활동반경 안이다. **상태는 보지 않는다** — 피드에서 열어 본 의뢰가 완료됐다고 갑자기 404 가 되면 안 된다.

건물이 없는 의뢰는 거리를 잴 수 없어 언제나 `null` 이다.

## 요청·응답

에러는 D1 규약대로 `{ "error": { "code", "message", "details?" } }` 한 형태다.
공통 실패: 비로그인 **401 `UNAUTHORIZED`** / 마스터 프로필 없음·업종·활동지역 미등록 **403 `FORBIDDEN`**.

### `GET /api/master/feed` (pull — 전 마스터)

```jsonc
// 200 — 내 업종 + 활동반경 안의 REQUESTED 의뢰, 거리순
{
  "workOrders": [
    {
      "id": "cmf0…",
      "category": "REPAIR",
      "description": "201호 온수가 미지근합니다. 보일러 점검 부탁드립니다.",
      "desiredDate": "2026-09-10",
      "status": "REQUESTED",
      "createdAt": "2026-09-01T15:00:00.000Z",
      "updatedAt": "2026-09-01T15:00:00.000Z",
      "place": {
        "buildingId": "cmf0…", "buildingName": "행당해피빌",
        "buildingAddress": "서울 성동구 행당로 79",
        "unitId": "cmf0…", "unitLabel": "201호"
      },
      "distanceKm": 2.554,                 // 내 사무소 → 의뢰 건물(소수 3자리)
      "landlordName": "김임대",
      "recommended": true,                 // 나에게 추천으로도 온 의뢰인가
      "sentAt": "2026-09-01T15:00:00.000Z" // 추천이 아니면 null
    }
  ],
  "master": {
    "plan": "PRO", "planUntil": "2026-12-31T15:00:00.000Z",
    "companyName": "성수홈케어", "categories": ["REPAIR", "CLEANING"], "radiusKm": 5

```

- 업종이 하나도 등록돼 있지 않으면 빈 목록이다.
- 같은 의뢰가 추천함과 피드에 **둘 다** 보일 수 있다(D4 가 의도한 겹침). 피드 카드에도 「추천」 배지가 붙어 어디서 온 것인지 드러난다.

### `GET /api/master/targets` (push — PRO 전용)

```jsonc
// 200 (PRO) — 최신 발송순. workOrders 원소 모양은 feed 와 같다(recommended 는 항상 true)
{ "workOrders": [ { "…", "recommended": true, "sentAt": "2026-09-02T04:02:11.004Z" } ],
  "master": { "…" }, "upgradeRequired": false }

// 200 (FREE · 만료된 PRO) — 403 이 아니다. 화면이 "권한 없음" 대신 업그레이드 안내를 그린다
{ "workOrders": [], "master": { "plan": "FREE", "planUntil": null, "…" }, "upgradeRequired": true }
```

**FREE 를 403 으로 막지 않은 이유**: 화면이 그려야 하는 것은 "권한 없음" 이 아니라 **"왜 비어 있는지 + 어떻게 채우는지"** 이고, 그 안내에도 내 플랜·업종·반경 정보가 필요하다.

### `POST /api/master/plan` (데모용 토글)

```jsonc
// 요청
{ "plan": "PRO" }        // FREE | PRO
// 200 — PRO 로 켜면 그 자리에서 채워진 추천 수가 함께 온다
{
  "master": { "plan": "PRO", "planUntil": "2026-10-02T09:12:00.000Z", "…" },
  "backfilledCount": 1
}
```

| 실패 | status · code |
|---|---|
| 비로그인 | 401 `UNAUTHORIZED` |
| 마스터 프로필·업종/활동지역 없음 | 403 `FORBIDDEN` |
| 모르는 플랜 값 | 400 `VALIDATION_ERROR` |

같은 플랜을 두 번 보내도 200(멱등). 내 `MasterDetail` 만 바뀐다.

## T5.3 에 넘기는 자리

- `/master/orders/[id]` 의 「견적 보내기」(`master-quote-cta`)는 **비활성 + "T5.3에서 열립니다"** 다. `WorkOrderQuote` 모델은 이미 있고(`@@unique([workOrderId, masterProfileId])` = 의뢰당 1회) DTO 에도 `quoteCount` 자리가 있다.
- 임대인 상세(`/landlord/workorders/[id]`)의 「받은 견적」 카드도 같은 자리다.
- `WorkOrderTargetStatus` 의 `VIEWED`·`ACCEPTED`·`DECLINED` 는 아직 아무도 쓰지 않는다 — 견적 제안·수락이 붙을 때 채우면 된다(`BrokerageTarget` 과 형태가 같아 T3.6 과 나란히 간다).
- `/master/quotes` 탭 목적지는 여전히 플레이스홀더다(T5.3 소유).
