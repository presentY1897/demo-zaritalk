# T2.6 민원 접수·스레드

> Phase 2 · 상태: ✅ · [Phase 구성](../PHASES.md)

| 라우트 | 화면·기능 |
|---|---|
| `/tenant/complaints` | 접수(제목·내용·**사진은 T2.4 대기**)·목록·상태 |
| `/tenant/complaints/[id]` `/landlord/complaints/[id]` | 스레드 — 메시지 교환, 임대인 상태 변경(진행중/해결/반려). 「작업 의뢰로 전환」 버튼은 Phase 5에서 활성화 |
| `/landlord/complaints` | **표에 없던 화면** — 임대인 민원 목록(아래 "임대인 목록을 만든 이유") |

| 엔드포인트 | 동작 |
|---|---|
| `GET·POST /api/complaints` | 목록·접수, `POST /[id]/messages` 스레드, `PATCH /[id]` 상태 |

**이 task 의 핵심은 권한 판정이다** — 스레드는 **해당 계약의 세입자와 임대인 둘만** 볼 수 있고
제3자는 403 이다. 임대인 자원(T1.1·T1.2)처럼 "내 것인가" 한 방향으로 끝나지 않고 **두 방향**이라,
판정이 화면·API 로 흩어지면 한쪽만 고쳐서 구멍이 난다. 그래서 규칙 자체를 순수 함수 하나로 두고
화면과 API 가 **같은 함수**를 부른다.

**데이터 흐름** — 서버 컴포넌트가 `queries.ts` 로 첫 데이터를 읽어 화면에 넘기고, 접수 후에는
Tanstack Query 무효화로 목록을 다시 읽는다. **스레드 상세는 쿼리로 두지 않았다** — 답장·상태 변경
응답에 갱신된 상세가 그대로 실려 오므로 화면 state 로 충분하고, 상세 전용 GET 을 만들 이유가 없다.

## 권한 판정 — 헬퍼 시그니처와 규칙

```ts
// apps/web/src/features/complaint/ownership.ts
type ComplaintParty = "TENANT" | "LANDLORD";
type ComplaintPartyTarget = {
  leaseTenantProfileId: string | null;    // Lease.tenantProfileId
  complaintTenantProfileId: string;       // Complaint.tenantProfileId
  ownerProfileId: string;                 // Unit.building.ownerProfileId
};
type ComplaintPartyMatch = { party: ComplaintParty; profileId: string };
type ComplaintAccess = ComplaintPartyMatch & { user: SessionUser; complaint: ComplaintWithContext };

// ① 판정의 단일 출처 — DB 를 모르는 순수 함수(테스트가 DB 없이 돈다)
resolveComplaintParty(
  profiles: readonly Pick<Profile, "id" | "type">[],
  target: ComplaintPartyTarget,
): ComplaintPartyMatch | null

// ② 민원 행에서 판정 입력을 뽑는다(가드가 읽은 행과 화면용 조회가 읽은 행 둘 다 이 모양에 맞는다)
toPartyTarget(complaint: ComplaintPartySource): ComplaintPartyTarget

// ③ API 가드 — ①을 감싼다
requireComplaintAccess(complaintId: string): Promise<Guarded<ComplaintAccess>>      // 401 · 404 · 403
requireComplaintLandlord(complaintId: string): Promise<Guarded<ComplaintAccess>>    // + 세입자 403
requireOwnComplaintLease(tenantProfileId, leaseId): Promise<Guarded<ComplaintLease>> // 404 · 403 · 409

// ④ 화면(서버 컴포넌트)용 — features/complaint/queries.ts. 내부에서 ①을 그대로 부른다
getComplaintForViewer(complaintId, user): Promise<{ complaint: ComplaintDetailDto; viewer: ComplaintPartyMatch } | null>
```

`Guarded<T>` 는 T1.1 `features/landlord/ownership.ts` 의 규약 그대로다 — 성공하면 `{ data }`,
실패하면 `{ response }`(이미 D1 규약 본문이 담긴 Response).

```ts
const access = await requireComplaintAccess(id);
if (access.response) return access.response;      // 401 · 404 · 403
const { complaint, party, profileId } = access.data;
```

### 판정 규칙

| 대상 | 판정 키 | 결과 |
|---|---|---|
| 계약의 세입자 | `Lease.tenantProfileId` == 내 **TENANT** 프로필 | `TENANT` |
| 민원을 접수한 세입자 | `Complaint.tenantProfileId` == 내 **TENANT** 프로필 | `TENANT` |
| 건물 주인 | `Unit.building.ownerProfileId` == 내 **LANDLORD** 프로필 | `LANDLORD` |
| 그 외 전부(제3자·다른 임대인·다른 세입자·프로필 없음) | — | **403** |

- **접수자도 함께 본다.** 계약이 정리돼 세입자 연결이 끊겨도 자기가 쓴 민원은 계속 읽을 수 있어야 한다 — 접수자는 제3자가 아니다.
- **id 만이 아니라 프로필 유형까지 본다.** 임대인 프로필 id 가 우연히 세입자 id 와 같아도 통과하지 못한다.
- 한 계정이 이 계약의 세입자이자 이 건물의 임대인이면 **임대인**으로 판정한다(상태 변경까지 포함하는 넓은 쪽. 데모 시드에는 없는 조합).
- 프로필은 활성 프로필 쿠키가 아니라 **유형으로** 고른다(`@@unique([userId, type])`) — T1.1·T1.3 과 같은 규칙.

### 상태 코드 규칙

| 상황 | status · code |
|---|---|
| 비로그인·만료 세션 | 401 `UNAUTHORIZED` |
| 없는 민원·계약 id | 404 `NOT_FOUND` |
| **제3자** | 403 `FORBIDDEN` |
| 세입자가 상태를 바꾸려 함 | 403 `FORBIDDEN` |
| 남의 계약에 접수 | 403 `FORBIDDEN` |
| 진행 중이 아닌 계약에 접수 | 409 `CONFLICT` |

남의 민원을 404 로 감추지 않고 403 을 주는 것은 T1.1 과 같은 선택이다(최소 테스트가 403 을 요구한다).
**화면(서버 컴포넌트)만 `notFound()`(404)로 막는다** — 존재 여부를 흘리지 않는 편이 낫다.
스레드 페이지는 경로와 시점을 일치시킨다: `/tenant/complaints/[id]` 는 `TENANT` 로 판정되지 않으면,
`/landlord/complaints/[id]` 는 `LANDLORD` 로 판정되지 않으면 404 다(반대편 화면에 상태 버튼이나
반대쪽 목록 링크가 섞이지 않게).

## 상태 전이표

| 현재 \ 목표 | `IN_PROGRESS` 진행중 | `RESOLVED` 해결 | `REJECTED` 반려 |
|---|---|---|---|
| `OPEN` 접수 | ✅ | ✅ | ✅ |
| `IN_PROGRESS` 진행중 | ❌ 409 (같은 상태) | ✅ | ✅ |
| `RESOLVED` 해결 | ✅ (재개) | ❌ 409 | ❌ 409 |
| `REJECTED` 반려 | ✅ (재개) | ❌ 409 | ❌ 409 |

- **`OPEN` 은 목표가 될 수 없다** — 접수 시점에만 붙는 초기 상태이고, 임대인 홈(T1.9)의 미확인 민원 배지가
  `status === "OPEN"` 을 **미확인의 대리 지표**로 쓴다. 한 번 손댄 민원을 다시 "미확인" 으로 되돌리면
  배지가 거짓말을 한다. 요청 스키마 enum 에서 아예 빠져 있어 **400 `VALIDATION_ERROR`** 다.
- **종결끼리는 못 넘어간다**(해결 ↔ 반려). 다시 열려면 「진행중」으로 재개한 뒤에 바꾼다 —
  "해결됐다더니 또 샌다" 는 담되, 종결 사유를 조용히 바꿔치기하지는 못하게 한 선택이다.
- 같은 상태로의 전이는 **409**. 화면에서는 현재 상태 버튼이 비활성이다.
- 전이 판정은 `features/complaint/status.ts` 의 `canTransition` 한 곳뿐이다 — 화면 버튼의 `disabled` 도
  같은 함수를 읽는다. 저장은 전이 전 상태를 조건에 넣은 단일 `updateMany` 라 동시 요청도 한쪽만 성공한다.
- **상태와 무관하게 메시지는 언제나 쓸 수 있다** — 종결된 민원에도 이어 쓸 수 있고, 손봐야 하면 재개하면 된다.

## 요청·응답

에러는 D1 규약대로 `{ "error": { "code", "message", "details?" } }` 한 형태다.

### `GET /api/complaints`

민원은 당사자가 둘이라 목록도 둘이다. `?role=tenant|landlord` 로 시점을 고르고,
**생략하면 내 프로필로 정한다**(세입자 우선). 없는 유형의 시점을 찍으면 403 이다.

```jsonc
// 200 — role=tenant: 내가 접수한 민원(최근 활동 순) + 접수 폼의 계약 선택지
{
  "complaints": [
    {
      "id": "cmf0…", "leaseId": "cmf0…",
      "title": "온수가 나오지 않습니다",
      "status": "OPEN",                         // OPEN | IN_PROGRESS | RESOLVED | REJECTED
      "createdAt": "2026-09-02T03:11:20.512Z",
      "updatedAt": "2026-09-02T03:11:20.512Z",
      "messageCount": 1,                        // 접수 본문 포함
      "lastMessageAt": "2026-09-02T03:11:20.512Z",
      "photos": [],                             // 지금은 항상 [] — T2.4 업로드 대기
      "tenantName": "박세입", "landlordName": "김임대",
      "unit": {
        "id": "cmf0…", "label": "201호", "buildingId": "cmf0…",
        "buildingName": "행당해피빌", "buildingAddress": "서울 성동구 행당로 79"
      }
    }
  ],
  "leases": [                                   // role=landlord 면 항상 []
    { "leaseId": "cmf0…", "unitLabel": "201호", "buildingName": "행당해피빌", "landlordName": "김임대" }
  ]
}
```

`role=landlord` 는 **내 건물의 민원 전체**를 주고 **미확인(OPEN)을 위로** 올린다(그다음 최근 활동 순).
집계 조건은 임대인 홈(T1.9) 배지와 같은 `lease.unit.building.ownerProfileId` 다.

| 실패 | status · code |
|---|---|
| 비로그인 | 401 `UNAUTHORIZED` |
| 요청한 시점의 프로필이 없음 | 403 `FORBIDDEN` |
| 모르는 `role` 값 | 400 `VALIDATION_ERROR` |

### `POST /api/complaints`

```jsonc
// 요청 — photos 는 선택(지금 화면은 보내지 않는다)
{ "leaseId": "cmf0…", "title": "온수가 나오지 않습니다", "body": "어제 저녁부터 …" }

// 201 — 상세 DTO(목록 필드 + body · messages · workOrderId)
{
  "complaint": {
    "…목록 필드 그대로…",
    "status": "OPEN",
    "body": "어제 저녁부터 …",
    "messages": [
      {
        "id": "opening:cmf0…",                  // ComplaintMessage 행이 아니다(아래 설명)
        "kind": "OPENING",                      // OPENING | REPLY
        "authorProfileId": "cmf0…", "authorRole": "TENANT", "authorName": "박세입",
        "body": "어제 저녁부터 …",
        "createdAt": "2026-09-02T03:11:20.512Z"
      }
    ],
    "workOrderId": null                         // Phase 5(T5.1) 전환 결과
  }
}
```

| 실패 | status · code |
|---|---|
| 비로그인 | 401 `UNAUTHORIZED` |
| 세입자 프로필 없음(임대인 계정 포함) | 403 `FORBIDDEN` |
| 없는 계약 | 404 `NOT_FOUND` |
| **내 계약이 아님**(계약이 아예 없는 세입자 포함) | 403 `FORBIDDEN` |
| 진행 중(ACTIVE)이 아닌 계약 | 409 `CONFLICT` |
| 제목 2자 미만·내용 5자 미만·사진 URL 형식/개수 | 400 `VALIDATION_ERROR` |

> **접수 본문은 `ComplaintMessage` 로 복사하지 않는다.** 본문의 원본은 `Complaint.body` 하나뿐이고,
> 스레드 DTO 에서만 첫 말풍선(`kind: "OPENING"`, `id: "opening:<민원id>"`)으로 합성한다.
> 그래서 화면은 `messages` 만 그리면 되고, DB 에는 같은 글이 두 벌 남지 않는다.
> `messageCount` 는 접수 본문을 포함한 말풍선 수다(메시지 행 수 + 1).

### `POST /api/complaints/[id]/messages`

```jsonc
// 요청
{ "body": "내일 오전에 설비 기사가 방문합니다." }

// 201 — 방금 쓴 말풍선 + 갱신된 상세(화면이 그대로 갈아 끼운다)
{
  "message": {
    "id": "cmf0…", "kind": "REPLY",
    "authorProfileId": "cmf0…", "authorRole": "LANDLORD", "authorName": "김임대",
    "body": "내일 오전에 설비 기사가 방문합니다.",
    "createdAt": "2026-09-02T04:02:11.004Z"
  },
  "complaint": { "…상세 DTO…" }

```

**작성자는 판정이 돌려준 프로필 id 를 그대로 쓴다** — 클라이언트가 보낸 값을 믿지 않는다.
`authorRole` 은 저장하지 않고 `authorProfileId === ownerProfileId` 로 가른다(스레드 참여자는 둘뿐이다).

| 실패 | status · code |
|---|---|
| 비로그인 | 401 `UNAUTHORIZED` |
| 없는 민원 | 404 `NOT_FOUND` |
| **제3자** | 403 `FORBIDDEN` |
| 빈 메시지·1,000자 초과 | 400 `VALIDATION_ERROR` |

## 사진 슬롯 — T2.4 연결 지점

업로드 엔드포인트(D3 Vercel Blob)는 **아직 세팅 전**이고 [T2.4](./t2.4-refund-apply.md) 소유다.
그래서 이 task 는 **사진 없이 제목·내용만으로 완결**하고, 자리만 열어 뒀다.

| 자리 | 지금 | T2.4 가 붙으면 |
|---|---|---|
| `Complaint.photos`(스키마) | `Json?` — 이미 있다 | 그대로 |
| `createComplaintSchema.photos`(`features/complaint/schema.ts`) | `z.url()` 배열 5장 제한, 선택 — **이미 받는다** | 손댈 것 없음 |
| `POST /api/complaints` | 배열이 오면 그대로 저장(단위 테스트로 왕복 확인) | 손댈 것 없음 |
| DTO `photos: string[]` | 항상 `[]` | 저장된 URL 이 실린다 |
| 접수 시트 `data-testid="complaint-photo-slot"` | 안내 문구 ("사진 첨부는 곧 제공됩니다 (T2.4 업로드 연결).") | **여기를 업로더로 교체** → 받은 URL 배열을 `createComplaint({ …, photos })` 로 실어 보낸다 |
| 스레드 `data-testid="complaint-photos"` | `photos` 가 비어 있어 렌더되지 않는다 | 자동으로 그려진다 |

> 스레드의 사진은 `next/image` 가 아니라 `<img>` 다 — 외부 Blob 호스트가 정해지지 않아
> `images.remotePatterns` 를 적을 수 없다. 도메인이 정해지면 그때 바꾼다.

## Phase 5(T5.1) 작업 전환 버튼 자리

스레드의 임대인 패널 아래 `data-testid="complaint-workorder-cta"` 버튼이 자리다 —
지금은 **비활성 + "민원을 협력업체 작업 의뢰로 넘기는 기능은 Phase 5(T5.1)에서 열립니다."** 안내다.

- 스키마는 이미 준비돼 있다 — `WorkOrder.complaintId String? @unique`(민원 1건 → 의뢰 1건).
- DTO 에 `workOrderId: string | null` 이 있고 `queries.ts` 가 `complaint.workOrder` 를 읽어 채운다.
  지금은 항상 `null` 이다.

## 임대인 목록을 만든 이유 (`/landlord/complaints`)
