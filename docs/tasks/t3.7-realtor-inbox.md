# T3.7 중개인 수신함·수락

> Phase 3 · 상태: ✅ · [Phase 구성](../PHASES.md)

## 상태 전이표 — 한 곳에만 있다

규칙은 `features/brokerage/status.ts` 의 `checkTargetTransition` **한 함수**이고,
DB 에 적용하는 곳은 `features/brokerage/respond.ts` **한 곳**이다.
라우트·화면·테스트가 전부 이 표를 읽는다.

| 현재 \ 목표 | `VIEWED` 열람 | `ACCEPTED` 수락 | `DECLINED` 거절 |
|---|---|---|---|
| `SENT` 발송됨 | ✅ 바뀐다 | ❌ 409 "요청을 먼저 열람해 주세요." | ❌ 409 (같은 사유) |
| `VIEWED` 열람 | ⚪️ 멱등(200·변화 없음) | ✅ | ✅ |
| `ACCEPTED` 수락 | ⚪️ 멱등 | ❌ 409 "이미 수락한 요청입니다." | ❌ 409 |
| `DECLINED` 거절 | ⚪️ 멱등 | ❌ 409 "이미 거절한 요청입니다." | ❌ 409 |

**즉, 상태가 실제로 바뀌는 길은 `SENT→VIEWED` · `VIEWED→ACCEPTED` · `VIEWED→DECLINED` 셋뿐이다**
(테스트가 전이표 전수를 훑어 이 셋만 남는지 확인한다).

- **뒤로 가는 전이는 없다.** 수락·거절은 종결 상태이고 열람도 되돌릴 수 없다.
- **열람은 멱등이다** — 상세 화면은 열릴 때마다 열람을 표시하므로 여기서 409 를 내면
  이미 응답한 요청을 다시 열어볼 때마다 화면이 에러를 그린다.
- **보지 않고 수락할 수 없다.** 임대인이 보는 「열람 n · 수락 n」 현황이 뜻을 가지려면
  수락은 반드시 열람을 지나야 한다. 화면은 상세를 열 때 자동으로 열람을 표시하므로
  사용자는 이 규칙을 만날 일이 없다 — API 를 직접 부르는 쪽만 순서를 지키면 된다.
- `respondedAt` 은 **수락·거절에만** 찍는다. 열람은 응답이 아니다.

### 요청 쪽 상태 — 첫 수락에서 한 번만

```ts
shouldMatchRequest(requestStatus, response)  // OPEN + ACCEPTED 일 때만 true
```

수락은 **복수 허용**이라 두 번째 수락에서는 이미 `MATCHED` 다(응답은 `matched: false`).
`CLOSED` 된 요청은 되살리지 않는다. 거절은 요청 상태를 옮기지 않는다.

### 한 번의 수락이 하는 일 셋

| | 무엇 | 왜 |
|---|---|---|
| ① | `BrokerageTarget.status = ACCEPTED` + `respondedAt` | 응답 기록 |
| ② | **첫 수락이면** 요청 `OPEN → MATCHED` | 임대인 목록에 「매칭」이 뜬다 |
| ③ | 임대인에게 알림톡 시뮬(`MessageLog`) | T1.7 과 같은 발송 로그 |

세 가지는 한 트랜잭션이다. 그리고 그 순간 **매물 등록 권한**이 함께 열린다(아래 절).

## 수락 중개인의 매물 등록 권한 — **T3.1 이 열어 둔 판정이 실제로 동작한다**

[T3.1](./t3.1-listing-create.md#중개인-경로는-판정만-열어-뒀다-t37-미구현)은
`features/listing/permissions.ts` 의 `hasAcceptedBrokerage`(= 이 호실 요청에 `ACCEPTED` 타겟이 있나)로
판정만 열어 두고 "T3.7 이 respond 라우트를 붙이면 **코드 변경 없이** 동작한다" 고 적어 뒀다.

**확인 결과: 그대로 동작한다. `features/listing/**` 는 한 줄도 고치지 않았다.**

세 겹으로 확인했다.

1. **단위 테스트** — `app/api/brokerage-targets/[id]/respond/route.test.ts` 의
   "수락하면 T3.1 매물 등록 권한이 코드 변경 없이 열린다":
   같은 중개인 세션으로 **실제 `POST /api/listings` 라우트를 직접 부른다.**
   - 수락 **전** → `403 FORBIDDEN`
   - `respond {status:"ACCEPTED"}` → 200
   - 수락 **후** 같은 요청 → **`201`**, `listing.listedBy.role === "REALTOR"`
2. **E2E** — 중개인이 화면에서 수락 → 「매물 등록」 → `/landlord/units/[id]/listing` 에서
   월세 매물 등록 → 「공개 중」. DB 로 `Listing.listedByProfileId` 가 이중개의 REALTOR 프로필인지 확인한다.
3. **차단 사유 문구도 공유한다** — 수신함 카드의 `listingBlockedReason` 은 T3.1 의
   `listingBlockedReason(unitStatus, liveListing)` 을 그대로 부른다. 그래서 "계약이 있는 호실에는
   매물을 등록할 수 없습니다." 가 두 화면에서 **같은 문자열**이다(테스트가 확인한다).

매물 등록·수정·상태 변경 **화면도 새로 만들지 않았다** — `/landlord/units/[id]/listing` 이
이미 "소유 임대인 **또는 수락 중개인**" 을 받으므로 `/realtor/listings` 와 요청 상세의 버튼이
그 화면으로 보낸다. 화면을 하나 더 만들면 상태 전이·409 규칙이 두 벌이 된다.

## 열람(`VIEWED`)은 어디서 찍히나 — 상세 화면이 **클라이언트에서** 보낸다

`/realtor` 수신함 목록에서는 찍지 않는다. 목록을 스쳐 본 것과 요청을 열어 본 것은 다르고,
임대인이 보는 「열람 n」 은 후자여야 한다.

서버 컴포넌트 렌더 중에 찍지도 않는다 — **링크 프리페치만으로 "열람" 이 될 수 있기 때문이다.**
그래서 `RealtorRequestDetailView` 가 마운트될 때 `POST …/respond {"status":"VIEWED"}` 를 한 번 보낸다.
사람이 실제로 연 순간에만 찍힌다. 실패해도 상세는 그대로 읽힌다(열람 표시는 화면의 본질이 아니다).

`VIEWED` 를 respond 라우트가 함께 받는 이유는 **상태를 옮기는 길을 하나로 두기 위해서다** —
길이 둘이면 전이 규칙이 둘로 갈라진다.

## 요청·응답

에러는 D1 규약대로 `{ "error": { "code", "message", "details?" } }` 한 형태다.
공통 실패: 비로그인 **401 `UNAUTHORIZED`** / 중개인 프로필·활동지역(`RealtorDetail`) 없음 **403 `FORBIDDEN`**.

### `GET /api/realtor/inbox`

```jsonc
// 200 — 최신 요청순
{
  "requests": [
    {
      "targetId": "cmf0…",
      "status": "SENT",                       // SENT | VIEWED | ACCEPTED | DECLINED
      "distanceKm": 0.12,                    // **발송 시점에 굳은 값**
      "respondedAt": null,
      "requestId": "cmf0…",
      "requestStatus": "OPEN",
      "message": "즉시 입주 가능합니다. 월세 50만원 선입니다.",
      "createdAt": "2026-09-02T12:00:00.000Z",
      "place": {
        "unitId": "cmf0…", "unitLabel": "101호", "floor": 1, "areaM2": 23.1, "rooms": 1,
        "buildingId": "cmf0…", "buildingName": "행당해피빌",
        "buildingAddress": "서울 성동구 행당로 79", "lat": 37.56152, "lng": 127.03648
      },
      "landlord": { "name": "김임대", "phone": null },   // 연락처는 **수락 뒤에만**
      "listing": null,                                   // 그 호실에 살아 있는 매물 요약(mine 포함)
      "canCreateListing": false,
      "listingBlockedReason": "요청을 수락하면 이 호실에 매물을 등록할 수 있습니다."
    }
  ],
  "realtor": {
    "officeName": "왕십리부동산", "address": "서울 성동구 왕십리로 300",
    "lat": 37.56133, "lng": 127.03782, "radiusKm": 3, "licenseNo": null
  }
}
```

**거리를 다시 계산하지 않는 이유**: 사무소를 옮겨도 "그때 이 거리라서 받았다" 가 남아야 한다
(T5.2 추천함과 같은 규칙). 그래서 `BrokerageTarget.distanceKm` 을 그대로 쓴다.

**연락처를 수락 뒤에만 주는 이유**: 수락이 곧 "연락해도 된다" 는 합의다. 임대인 쪽도 같다 —
수락한 중개인의 이름·전화번호만 `GET /api/brokerage-requests` 의 `accepted` 에 담긴다.

### `POST /api/brokerage-targets/[id]/respond`

```jsonc
// 요청
{ "status": "ACCEPTED" }        // VIEWED | ACCEPTED | DECLINED
// 200
{
  "target": { "…RealtorInboxItemDto…", "status": "ACCEPTED",
              "respondedAt": "2026-09-02T12:10:00.000Z",
              "landlord": { "name": "김임대", "phone": "01011111111" },
              "canCreateListing": true, "listingBlockedReason": null },
  "matched": true                // 이 수락으로 요청이 MATCHED 로 넘어갔는가(첫 수락에만 true)
}
```

| 실패 | status · code |
|---|---|
| 비로그인 | 401 `UNAUTHORIZED` |
| 중개인 프로필·활동지역 없음 | 403 `FORBIDDEN` |
| 없는 타겟 id | 404 `NOT_FOUND` |
| **다른 중개인에게 간 타겟** | 403 `FORBIDDEN` — "나에게 온 중개 요청만 볼 수 있습니다." |
| 전이표가 막는 변경(안 보고 수락 · 이미 응답함) | 409 `CONFLICT` |
| 모르는 상태 값(`SENT` 포함) | 400 `VALIDATION_ERROR` |

**남의 타겟은 404 로 감추지 않고 403 을 준다** — T1.1 이 정한 규칙 그대로다.
화면(`/realtor/requests/[id]`)은 같은 상황에서 `notFound()` 로 막는다.

## E2E — 어디까지 갔고 무엇을 남겼나

`e2e/brokerage.spec.ts` 한 여정으로 두 task 의 완료 기준을 지난다:

1. 임대인 → 자산 → **공실 101호** 상세 → 「중개 요청」(`?unitId=` 로 그 호실이 골라진 채 시트가 열린다)
2. **미리보기 1명**(시드 이중개·왕십리 3km) + 목록에 「왕십리부동산」 · **연락처가 없는지 확인**
3. 발송 → 「1명」 안내 + 요청 카드(대상 1명 · 열람 0 · 수락 0) + **중개인 번호로 알림톡 로그**(DB)
4. 중개인 로그인 → 수신함 카드(호실·거리·메시지) → 카드 클릭
5. 상세가 열리며 **열람** — 배지 「열람」 + DB `BrokerageTarget.status = VIEWED` + 연락처 없음
6. **수락** → 「수락」 배지 · 임대인 연락처 노출 · DB **요청 `MATCHED`** · 임대인에게 수락 알림 로그
7. 「매물 등록」 → `/landlord/units/[id]/listing` → 월세 매물 등록 → **「공개 중」** ·
   DB 로 등록자가 **이중개(REALTOR)** 인지 확인
8. 중개인 「매물」 탭 → `/realtor/listings` 에 내 매물 1건
9. 임대인 재로그인 → 「중개요청」 탭 → **매칭** 배지 · 수락 1 · **연락 카드(왕십리부동산 · 이중개 · `tel:`)** ·
   중개인이 올린 매물 표시
10. 트래킹 3종(`brokerage_request_complete` · `brokerage_inbox_view` · `brokerage_respond_complete`)

### `/search` 노출은 남겼다 — T3.2 머지 후

T3.7 문서의 통합 시나리오는 「… → 매물 등록 → `/search` 노출」 이지만 **`/search`(T3.2)는
이 작업 시점에 아직 플레이스홀더**다(동시 작업 중). 그래서 **매물이 `OPEN` 으로 올라간 것까지**
검증하고 `/search` 노출은 확인하지 않았다.

**T3.2 머지 후 할 일**: `e2e/brokerage.spec.ts` 의 ⑧ 다음에 `/search` 로 이동해
「행당해피빌 101호」 월세 매물이 목록에 뜨는지 한 단계만 더하면 된다
(그 매물은 `status = OPEN`, 좌표는 `Listing.unit.building` 이다).

### 101호는 여러 스펙이 함께 쓰는 유일한 공실이다

이 스펙은 앞뒤로 `BrokerageRequest`·`BrokerageTarget`·101호 `Listing`·`BROKERAGE_REQUEST`
발송 로그를 지운다(`test.beforeAll`/`test.afterAll`). 안 지우면 **뒤에 도는
`listing.spec.ts`(101호에 매물을 새로 등록한다)가 등록 폼을 못 본다.**
`workorder.spec.ts` 가 한마스 플랜을 되돌리는 것과 같은 이유다(CI 재시도 포함).

**기존 E2E 파일은 고치지 않았다** — 새로 깨진 스펙이 없다.
