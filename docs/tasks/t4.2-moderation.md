# T4.2 신고·모더레이션

> Phase 4 · 상태: ✅ · [Phase 구성](../PHASES.md)

| 라우트/API | 동작 |
|---|---|
| `POST /api/reports` | 글/댓글 신고 → 어드민 큐 |
| `GET /api/reports` | **어드민 큐 조회** — 상태 필터 + 대상 미리보기 |
| `POST /api/reports/[id]/action` | **블라인드(soft delete) / 기각** — 처리자·시각 기록 |
| `/reports` (admin) | 대기 목록, 대상 미리보기, 액션 버튼 |

**[T4.1 커뮤니티 보드](./t4.1-community.md)와 한 묶음으로 구현했다**([D7](../DECISIONS.md#-d7-백오피스-진행-방식)) — 신고는 커뮤니티 화면(접수)과 어드민 큐(처리) 양쪽에 걸쳐 있고, 블라인드 결과가 다시 커뮤니티 화면에 나타나기 때문이다. 보드·글·댓글·좋아요는 T4.1 문서에 있다.

## 블라인드 노출 규칙표

> **정의는 `apps/web/src/features/community/moderation.ts` 한 곳뿐이다.** 순수 함수 다섯 개(`moderationStateOf`·`isListed`·`canSeeOriginal`·`canInteract`·`blockedReason`)이고 단위 테스트(`moderation.test.ts`)가 이 표와 같은지 지킨다. 목록 쿼리·상세 DTO·댓글 DTO·어드민 미리보기가 **전부 같은 함수**를 부른다.

### ① 상태는 셋이다

스키마에는 `deletedAt` 컬럼 하나뿐이라, **글이 사라지는 두 경로**를 신고 이력으로 가른다.

| 상태 | 판정 |
|---|---|
| `VISIBLE` 정상 | `deletedAt == null` |
| `BLINDED` 블라인드 | `deletedAt != null` **이고** 그 대상에 `Report.status = ACTIONED` 가 있다 |
| `REMOVED` 작성자 삭제 | `deletedAt != null` 이고 처리된 신고가 없다 |

블라인드는 **신고 처리로만** 생기므로 이 둘로 정확히 갈린다(전용 컬럼이 없어서 파생한다 — 아래 「스키마가 필요했지만 만들지 않은 것」).

### ② 어디에 어떻게 나오나

| 상태 | 목록 `GET /api/posts` | 상세 `GET /api/posts/[id]` | 제목·본문 | 좋아요·댓글·신고·수정 |
|---|---|---|---|---|
| **정상** | 보인다 | 200 | 그대로 | 가능 |
| **블라인드** | **자리를 남긴다** — 제목·본문 자리에 안내문. 작성자·시각·좋아요/댓글/조회 수는 그대로 | **200** | **가림**(예외는 ③) | **막는다 — 409 `CONFLICT`** |
| **작성자 삭제** | **빠진다** | **404** | — | — |

| 댓글 상태 | 스레드 목록 | 본문 | 삭제 |
|---|---|---|---|
| **정상** | 보인다 | 그대로 | 작성자만 |
| **블라인드** | **자리를 남긴다** | **가림**(예외는 ③) | **막는다 409** |
| **작성자 삭제** | **빠진다**(댓글 수에도 안 잡힌다) | — | 404 |

**블라인드 글을 목록에서 통째로 빼지 않는 이유** — 달린 댓글이 통째로 증발하면 대화가 끊기고, "왜 없어졌는지" 가 화면에서 사라진다. 자리를 남기고 내용만 가리는 쪽이 모더레이션의 결과를 커뮤니티에 드러낸다. 반대로 **작성자가 스스로 지운 글은 흔적을 남기지 않는다** — 남길 이유가 없다.

### ③ 누가 원문을 보나

| 보는 사람 | 블라인드 글·댓글의 원문 |
|---|---|
| **작성자 본인** | **보인다** + 「블라인드」 배지 | 
| **어드민**(`User.isAdmin`) | **보인다** — 심사하려면 봐야 한다(신고 큐의 대상 미리보기도 같은 규칙) |
| 그 밖의 사용자 | **가려진다** — 안내문만(`"블라인드 처리된 글입니다"` · `"신고가 접수되어 관리자가 가린 글입니다."`) |

- **작성자에게 원문을 보여 주는 이유**: 왜 가려졌는지 알고 다시 쓰려면 원문이 필요하다. 자기가 쓴 글을 자기만 못 보는 것도 이상하다.
- **원문이 보이는 사람에게도 참여·수정·삭제는 막힌다**(`canInteract`) — **보는 것과 되살리는 것은 다르다.** 블라인드된 글을 작성자가 고쳐서 되살리면 모더레이션이 무의미해진다.
- "내 글인가" 는 **계정 단위**(그 계정의 모든 `profileId`)로 본다 — 프로필을 전환해도 판정이 흔들리지 않는다.
- 가림은 **서버에서** 한다. DTO 에 이미 안내문이 담겨 오므로 원문이 브라우저까지 내려가지 않는다.

## 신고 접수 — 중복을 어떻게 다루나

| 상황 | 결과 |
|---|---|
| **같은 사람**이 **같은 대상**을 다시 신고 (대기 중인 내 신고가 있다) | **새 행을 만들지 않고** 그 신고를 **200 `duplicated: true`** 로 돌려준다 |
| **다른 사람**이 같은 대상을 신고 | 새 행(201) — 큐에 나란히 쌓인다. **몇 명이 신고했는지가 판단 재료**다 |
| 내 지난 신고가 이미 처리됨(블라인드·기각) | 새 행(201) — 같은 대상이라도 **새 사건**이다 |

같은 사람의 재신고를 에러로 막지 않는다. 화면에서 두 번 눌렀을 때 에러가 뜨면 신고가 안 된 것처럼 보이기 때문이다 — **큐는 깨끗하게, 사용자에게는 성공으로.** 화면 문구도 "이미 접수된 신고입니다. 관리자가 확인 중입니다." 로 다르게 나온다.

그 밖의 규칙:

- **사유는 필수다.** `trim` 후 2~500자. 화면은 선택지 5개(광고·홍보성 글 / 욕설·비방 / 허위·사기 의심 / 음란·불쾌감 / 기타)와 상세 사유 입력을 함께 보내고, 서버는 문자열 한 줄로만 본다.
- **내 글·댓글은 신고할 수 없다** — 403. 지우면 될 일이다.
- **이미 블라인드된 대상**은 409 — 더 할 일이 없다.
- 없는 대상·작성자가 지운 대상은 404.

## 어드민 액션 — 무엇이 함께 바뀌나

요청은 **액션 이름만** 보낸다(`{ "action": "BLIND" | "DISMISS" }`). 무엇이 바뀌는지는 서버가 정한다 — T2.5 환급 심사와 같은 방식이다.

| 액션 | 대상 | 이 신고 | 같은 대상의 다른 **대기** 신고 |
|---|---|---|---|
| **`BLIND` 블라인드** | `deletedAt` 을 찍는다(소프트 삭제) | `ACTIONED` | **함께 `ACTIONED`** — 같은 처리자·시각 |
| **`DISMISS` 기각** | 그대로 | `DISMISSED` | **건드리지 않는다** |

**왜 블라인드만 형제 신고를 닫나** — 블라인드는 **대상에 대한 결정**이라 같은 글이 큐에 5줄로 남을 이유가 없다. 기각은 **그 신고에 대한 결정**이다: "광고" 로 낸 신고를 기각했다고 다른 사람이 "욕설" 로 낸 신고까지 사라지면 안 된다.

### 액션마다 무엇이 기록되나

| 기록 | 어디에 |
|---|---|
| 결과 | `Report.status` (`OPEN` → `ACTIONED` · `DISMISSED`) |
| **처리자** | `Report.handledById` — 세션이든 서비스 시크릿이든 **실재하는 `isAdmin` User** |
| **시각** | `Report.handledAt` |
| 블라인드 결과 | 대상의 `deletedAt`(글은 `Post`, 댓글은 `Comment`) |

저장은 **`status: OPEN` 을 조건에 넣은 `updateMany`** 라 두 어드민이 동시에 눌러도 한쪽만 성공한다(`count === 0` → **409**). 대상 블라인드와 형제 신고 종결까지 **한 트랜잭션**이다. 이미 처리된 신고에 다시 액션을 걸면 409다.

**블라인드 해제는 없다.** 되살리기는 이 task 범위가 아니고, 하려면 `deletedAt` 을 지우는 것만으로 되지만(그러면 상태가 `VISIBLE` 로 돌아간다) 왜 되살렸는지 남길 자리(`handledNote`)가 없어 열지 않았다.

## 어드민 인증 — **어드민 앱에는 로그인이 없다**(T6.3 범위)

[T2.5 환급 심사](./t2.5-refund-review.md#어드민-인증--어드민-앱에는-로그인이-없다t63-범위)가 세운 방식을 **그대로 따랐다 — 인증을 새로 발명하지 않았다.**

```
[어드민 브라우저]  ──(세션 없음)──▶  어드민 서버(3001)  ──x-admin-secret──▶  web API(3000)
                                     서버 액션·라우트                        requireModerationAdmin()
                                     (시크릿은 서버에만)                      ↓
                                                                    isAdmin User 를 찾아 처리자로 기록
```

판정 함수는 **복사하지 않고 그대로 다시 내보낸다**:

```ts
// apps/web/src/features/community/ownership.ts
export const requireModerationAdmin = requireRefundAdmin;   // features/refund/ownership.ts
```

규칙을 한 벌 더 만들면 한쪽만 고쳐서 구멍이 나기 때문이다. 판정은 T2.5 표 그대로다:

| 통로 | 판정 |
|---|---|
| ① **세션 쿠키** | `getCurrentUser()` → `isAdmin` 이면 통과(처리자 = 그 사용자), 아니면 **403 `FORBIDDEN`** |
| ② **서비스 시크릿**(`x-admin-secret`) | 세션이 없을 때만 본다. 값이 맞으면 DB 에서 `isAdmin: true` 인 계정을 찾아 **그 사람을 처리자로 기록**. 관리자 계정이 하나도 없으면 **403** |
| ③ 둘 다 없음 | **401 `UNAUTHORIZED`** |

- 값은 `ADMIN_API_SECRET`, 없으면 `CRON_SECRET`(로컬·배포에 이미 있는 값이라 새 환경변수를 요구하지 않는다).
- **시크릿은 신분을 만들어 내지 못한다** — 통과해도 실재하는 `isAdmin` 계정을 찾아야 하고, 못 찾으면 403 이다. `handledById` 는 언제나 진짜 관리자다.
- **로그인한 비어드민이 시크릿을 붙여도 승격되지 않는다**(①이 ②보다 먼저다).
- T6.3 이 어드민 로그인을 붙이면 `resolveServiceAdmin` 분기 하나를 지우는 것으로 **환급 심사와 신고 처리가 함께** 바뀐다.

> ⚠️ **어드민 앱 자체에는 아직 인증이 없다** — 환급 심사·크론 트리거와 같은 상태다. **어드민 배포를 비공개로 두는 것이 전제**이고 T6.3 이 닫는다. (web API 는 이 전제 없이도 안전하다 — 시크릿 없이는 401/403 이다.)

## 어드민 화면 — **규칙을 하나도 들고 있지 않다**

어드민은 별도 Next 앱이라 `apps/web/src/features/**` 를 import 할 수 없다. 노출 규칙과 액션의 파급 범위를 복사하고 싶은 자리인데, 그러면 규칙이 두 벌이 된다.

**대신 API 응답이 버튼을 실어 보낸다.**

```jsonc
"availableActions": [
  { "action": "BLIND",   "label": "블라인드", "tone": "danger",
    "description": "대상 글·댓글을 가리고, 같은 대상의 다른 대기 신고도 함께 종결합니다." },
  { "action": "DISMISS", "label": "기각",     "tone": "neutral",
    "description": "이 신고만 기각합니다. 다른 사람이 낸 신고는 큐에 남습니다." }
]
```

어드민 화면은 이 배열을 그대로 그리고(라벨·톤·설명까지), 상태 배지도 응답의 `statusLabel`·`statusTone` 을 쓴다. 처리된 신고는 배열이 비어 있어 버튼이 사라진다. `apps/admin/src/app/reports/shared.ts` 에 있는 것은 **응답을 읽기 위한 타입 미러**일 뿐 규칙이 아니다.

| 파일 | 역할 |
|---|---|
| `apps/admin/src/app/reports/page.tsx` | 서버 컴포넌트 — `?filter=` 로 큐를 읽어 화면에 넘긴다(`force-dynamic`) |
| `apps/admin/src/app/reports/actions.ts` | `"use server"` — `fetchReportQueue`·`runReportAction`. 시크릿을 붙여 web 을 호출한다 |
| `apps/admin/src/app/reports/ReportQueueView.tsx` | 클라이언트 — 상태 필터 탭·목록·대상 미리보기·액션 버튼 |
| `apps/admin/src/app/reports/shared.ts` | 응답 타입 미러 + 필터 정의 + 포맷 |

- 목록은 **오래 기다린 순**(접수 시각 오름차순)으로 온다 — T2.5 환급 큐와 같은 정렬.
- 필터 탭은 대기 · 블라인드 · 기각 · 전체이고 각 탭에 상태별 건수가 붙는다.
- 각 행에 「같은 대상 대기 N건」이 붙는다 — 여러 사람이 신고한 글이 한눈에 드러난다.
- `apps/admin/src/app/_shell/menu.ts` 는 **손대지 않았다** — T0.5 가 `/reports` 자리를 이미 잡아 뒀다.

## API 요청·응답

### `POST /api/reports`

```jsonc
// 요청 — 신고자는 활성 프로필이라 보내지 않는다
{ "targetType": "POST", "targetId": "cmf0…", "reason": "광고·홍보성 글 — 대출 광고입니다." }

// 201(새 신고) · 200(내가 이미 낸 대기 신고가 있음)
{ "report": { "id": "cmf0…", "targetType": "POST", "targetId": "cmf0…",
              "reason": "광고·홍보성 글 — …", "status": "OPEN",
              "createdAt": "2026-09-02T05:00:00.000Z" },
  "duplicated": false }
```

| 실패 | status · code |
|---|---|
| 비로그인 | 401 `UNAUTHORIZED` |
| 프로필 없음 | 403 `FORBIDDEN` |
| **내 글·댓글 신고** | 403 `FORBIDDEN` |
| 없는 대상 · 작성자가 지운 대상 | 404 `NOT_FOUND` |
| **이미 블라인드된 대상** | 409 `CONFLICT` |
| **사유 누락·공백뿐**·모르는 대상 유형 | 400 `VALIDATION_ERROR` |

### `GET /api/reports` (어드민)

```
?status=OPEN            // 콤마로 여러 개. 생략하면 OPEN. 모르는 값은 버린다
```

### `POST /api/reports/[id]/action` (어드민)

```jsonc
// 요청 — **액션 이름만**
```

## E2E 에서 어드민을 어떻게 다뤘나

`e2e/community.spec.ts` E2E② 는 **사용자 여정은 브라우저로, 신고 처리는 web API 로** 친다 — T2.5 가 환급 심사에서 한 것과 같은 판단이다.

| 판단 | 이유 |
|---|---|
| 어드민 화면을 Playwright 로 몰지 않았다 | 어드민은 **별도 앱(3001)** 이고 `playwright.config.ts` 의 `webServer` 는 web 하나만 띄운다 — 그 설정 파일은 이 task 소유가 아니라 손대지 않았다. 게다가 신고 큐 화면은 규칙을 들고 있지 않아(위 참조) **위험이 전부 web API 쪽에 있다.** 화면 렌더링은 `pnpm build` 와 타입체크가 지킨다 |
| 처리 요청은 **어드민 세션 쿠키**로 보냈다(시크릿 헤더가 아니라) | 시드 관리자(`isAdmin: true`)에 세션 한 줄을 직접 만들어 쓰므로, 검증되는 것이 **본선 경로("`User.isAdmin` 기반 판정")** 다. 시크릿 경로는 단위 테스트가 따로 지킨다. 끝나면 그 세션을 지운다 |
| 블라인드 결과는 **일반 사용자 화면**에서 확인한다 | task 문서가 요구한 것이 그것이다 — 신고자(세입자) 화면에서 제목·본문이 안내문으로 바뀌고 좋아요·댓글이 잠기는지, 그리고 **작성자 화면에서는 원문이 그대로인지**까지 본다 |

## 스키마가 필요했지만 만들지 않은 것

`packages/db/prisma/**` 는 이 task 소유가 아니라 열지 않았다.

| 필요했던 것 | 지금 어떻게 대신했나 |
|---|---|
| **`Post.blindedAt`·`blindedById`**(또는 `moderationState` enum) | `deletedAt` + **처리된 신고 존재 여부**로 파생한다(위 ①). 판정은 정확하지만 목록 쿼리마다 `Report` 관계 조건이 붙고, "블라인드 해제" 이력을 남길 자리가 없다 |
| **`Report.handledNote`** — 왜 기각했는지 남길 자리 | 액션에 코멘트를 받지 않는다(T2.5 환급 심사는 `reviewNote` 가 있어 받는다). 감사 로그가 필요하면 이 컬럼부터다 |
| **`Report` 의 대상 유니크 제약** | 중복 신고 판정을 앱에서 한다(`findFirst` → 있으면 그것을 돌려준다). `@@unique([reporterProfileId, postId])` 는 **처리 뒤 재신고까지 막아** 부적절하고, 정확히 필요한 것은 "대기 중인 내 신고" 라는 부분 유니크 인덱스(Prisma 미지원)다. 아주 짧은 경합 창에서 같은 사람의 대기 신고가 두 줄 생길 수 있지만, 큐에 한 줄 더 보이는 것뿐이고 블라인드가 둘을 함께 닫는다 |
| **신고 알림** | 신고자·작성자에게 알림톡 시뮬(`MessageLog`)을 남기지 않았다. `MessageKind` 에 맞는 값이 없고(T2.5 는 `ETC` 로 우회했다) task 요구도 아니다 |
