## 집계 기준

### ① 기준일은 `paidAt` — 청구 월이 아니라 **실제 납부 시점** (현금주의)

시드 7월 청구(70만)는 7/10 에 40만만 들어왔다. 이 40만은 **7월 수입**이다.
8월 청구(연체, 납부 0건)는 **어느 달에도 잡히지 않는다** — 아직 들어온 돈이 아니다.
청구 월 기준(발생주의) 집계가 필요하면 원본인 `RentCharge` 가 그대로 남아 있으니 다시 집계하면 된다.

### ② 월 경계는 **KST 달력** (`kstYearMonth(paidAt)`)

`paidAt` 은 `@db.Date` 가 아니라 **타임스탬프**(UTC 저장)고, 장부의 "몇 월"은 한국 달력이다.
그냥 UTC 로 묶으면 매달 말일 `15:00Z~24:00Z`(= KST 다음 달 0~9시)에 들어온 납부가 한 달 앞으로 밀린다.
**이 프로젝트는 시드에서 이미 하루 밀림 버그를 겪었다.** 그래서 경계를 두 곳에서 명시적으로 처리한다:

| 어디 | 무엇 |
|---|---|
| 버킷 판정 | `kstYearMonth(payment.paidAt)` — 엔진 함수 하나만 쓴다. 직접 `getMonth()` 를 부르지 않는다 |
| DB 조회 범위 | `kstYearRange(year)` → `[UTC (year-1)-12-31T15:00Z, year-12-31T15:00Z)` |

```
2026년 = 2025-12-31T15:00:00Z 이상 ~ 2026-12-31T15:00:00Z 미만
12/31 14:59:59Z (KST 12/31 23:59) → 2026년 12월
12/31 15:00:00Z (KST 01/01 00:00) → 2027년 1월
```

조회 범위와 버킷 판정이 **같은 경계**를 쓰므로, 범위에 걸린 납부가 버킷에서 탈락하는 일이 없다.

### ③ 항목 배분은 **전부 원장 엔진이 한다**

납부액을 월세·관리비·연체료·이월로 나누는 건 엔진의 **충당 순서**가 정한다 —
`이월 → 연체료 → 관리비 → 월세` ([T1.4](./t1.4-rent-engine.md) 계산 규칙표).
장부는 자체 배분 규칙을 만들지 않는다. **여기서 규칙을 다시 쓰면 T1.5 수납 화면과 숫자가 어긋난다.**

| 엔진에서 쓴 것 | 쓰임 |
|---|---|
| `allocatePayments(amounts, payments)` | 납부 1건이 어느 항목에 얼마씩 들어갔는지. `paidAt` 오름차순 누적 충당 |
| `kstYearMonth(paidAt)` | 월 버킷 판정 |
| `KST_OFFSET_MS` | `kstYearRange` 의 UTC 구간 환산 |
| `CHARGE_LINE_LABELS` · `CHARGE_LINE_ORDER` · `ChargeLineKey` | 항목 라벨·표시 순서(월세 → 관리비 → 전월 이월 → 연체료) |

> **충당 계산은 그 청구의 모든 납부를 누적으로 봐야 한다.** 그래서 조회할 때 납부를 연도로 자르지 않고
> "그 해에 납부가 하나라도 있는 청구"를 고른 뒤 **납부는 전부** 딸려 오게 한다. 연도 필터는 버킷 단계에서만 건다.
> (잘라 넣으면 앞선 납부가 이미 지운 이월·연체료를 뒤 납부가 다시 지운다.)

### ④ 이월분(`carriedOver`)은 **납부한 달**의 수입 — 회계적으로 논쟁 여지가 있는 지점

**결정: 이월분도 `paidAt` 이 속한 달에 잡고, 다만 「전월 이월」 항목으로 분리해 표시한다.**

| 대안 | 왜 안 골랐나 |
|---|---|
| 원래 미납이 생긴 **과거 달**로 소급 | 기준이 두 개가 된다(나머지는 `paidAt`, 이월만 발생 월). 무엇보다 **이미 보여 준 과거 달의 합계가 나중 납부로 바뀐다** — 장부가 뒤로 흔들리면 임대인이 믿을 수 없다 |
| 그 달 **월세에 합산** | 늦게 받은 달의 월세가 부풀어 보인다. "이 달 순수 월세"를 읽을 수 없다 |
| **(채택) 납부한 달 + 별도 항목** | 현금 흐름이 정확하고("이 달에 얼마 들어왔나"), 밀린 돈을 이제 받았다는 사실도 항목으로 남는다 |

발생주의 장부가 필요하면 원장(청구)이 원본이다. **T6.2(어드민 지표)** 가 다른 기준을 쓰려면
같은 `RentCharge`·`RentPayment` 에서 다시 집계하면 된다 — 이 결정은 장부 화면에만 적용된다.

### ⑤ 합계 불변식

```
total = rent + maintenance + carriedOver + lateFee + excess
```
그리고 **한 달의 `total` 은 그 달 `paidAt` 을 가진 납부액 합계와 정확히 같다.**
`excess`(총액 초과 납부분)를 버리지 않고 담는 이유가 이 불변식이다 — T1.5 가 초과 납부를 400 으로
막으므로 정상 흐름에서는 항상 0 이고, 0 이면 화면에도 표시되지 않는다.

## 월 비교 미니 차트

**새 의존성 없이**(`pnpm-lock.yaml` 무변경) panda CSS 로만 그린 **12개월 가로 누적 막대**다.

- **왜 가로인가** — 480px 셸에서 세로 막대 12개는 하나가 30px 남짓이라 값 라벨을 붙일 자리가 없다.
  눕히면 한 행이 `[6월] [막대] [700,000원]` 으로 읽히고 긴 항목 이름(전월 이월·연체료)도 감당된다.
- **색만으로 정보를 전달하지 않는다**(T0.6 원칙) — ① 행마다 월 이름과 합계 금액을 **글자로** 적고
  ② 범례가 색 + 글자를 함께 주고 ③ 각 조각에 `title`(항목·금액) ④ 행마다 스크린리더 전용 요약
  ⑤ 바로 아래 **월별 항목 표**가 같은 숫자를 항목별로 다시 보여 준다.
- **하드코딩 색상 0** — 월세 `text.brand` · 관리비 `info` · 전월 이월 `success` · 연체료 `danger` ·
  초과 납부 `border.strong`. 인접 조각은 테두리 대신 **2px 흰 틈**으로 떨어뜨리고, 막대 끝만 4px
  둥글게 해 0원 기준선이 흐려지지 않게 했다. 이 네 색 조합은 색각 이상 인접 대비 검증(ΔE)을 통과한다.
- 수입이 0인 해는 막대 대신 "들어온 납부가 없습니다" 빈 상태를 보여 준다.
