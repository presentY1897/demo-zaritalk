## 커뮤니티는 로그인 필수다 — 왜 `(protected)` 인가

화면은 `apps/web/src/app/(app)/(protected)/community/**` 에 있고 API 도 비로그인이면 **401** 이다.

- [T0.5](./t0.5-shell-profile.md) 가 **비로그인 허용 화면을 셋으로 못 박았다** — `/search`(T3.2) · `/refund/calculator`(T2.3) · `/notice/[token]`(T1.8). 커뮤니티는 거기에 없고, 탭 배정표에서도 `(protected)` 아래 플레이스홀더로 깔려 있었다. 그 자리를 그대로 채웠다.
- **참여가 전부 프로필을 요구한다.** 글·댓글·좋아요·신고는 예외 없이 `Profile` 한 줄이 필요하다(누가 썼는지가 곧 유형 배지다). 비로그인에게 열어 두면 잠긴 버튼만 늘어선 화면이 된다.
- 읽기만 열어 주는 절충안은 **규칙이 둘로 갈린다**(목록은 되고 상세는 안 되고…). SEO 가 필요해지면 T6.4 가 공개 읽기 전용 경로를 따로 여는 편이 낫다 — 지금 열어 두면 되돌리기가 더 비싸다.

로그인은 했지만 프로필이 없는 계정(온보딩 전)은 화면에서 `/onboarding` 으로 보내고, API 는 **403** 이다.

### 어느 프로필로 쓰는가 — **활성 프로필**

커뮤니티는 네 유형 공용 탭이라 "임대인 API" 처럼 유형으로 프로필을 고를 수 없다. 그래서
**활성 프로필 쿠키**(`zari_profile`, T0.5)가 가리키는 프로필이 글쓴이가 되고, 그 유형이 목록의 배지가 된다.

반대로 **"내 글인가" 는 계정 단위로 본다**(그 계정의 모든 `profileId` 와 비교) — 세입자 프로필로 쓴 글을 임대인 프로필로 전환한 뒤에도 지울 수 있어야 하기 때문이다. **쓰기는 활성 프로필, 소유는 계정.** 좋아요도 같은 규칙이라(누를 때는 활성 프로필, 취소·표시는 계정) 프로필을 바꿔도 하트가 흔들리지 않는다.

## 커서 페이지네이션 규약 — **정의는 한 곳뿐이다**

원본은 `apps/web/src/features/community/cursor.ts` 이고, 단위 테스트(`cursor.test.ts`)와 API 테스트(`api/posts/route.test.ts`)가 지킨다.

| 탭 | 정렬 | 커서에 담기는 값 |
|---|---|---|
| 최신 `latest` | `createdAt DESC, id DESC` | `createdAt` · `id` |
| 인기 `popular` | `likeCount DESC, createdAt DESC, id DESC` | `likeCount` · `createdAt` · `id` |

### 동점 처리 — 마지막 키는 **언제나 `id`**

`likeCount` 는 동점이 흔하고(0점 글이 수두룩하다) `createdAt` 도 같은 밀리초에 둘이 들어올 수 있다. 정렬 키가 유니크하지 않으면 DB 가 같은 조건에 다른 순서를 돌려줄 수 있고, 그러면 페이지 경계에서 **한 줄이 두 번 나오거나 한 줄이 사라진다.** 그래서 두 탭 모두 **유니크 컬럼 `id` 로 정렬을 닫는다.** 인기 탭에 `createdAt` 을 한 겹 더 끼운 것은 같은 좋아요 수라면 최신 글이 위로 오게 하려는 취향이고, **안정성 자체는 `id` 가 보장한다.**

keyset 조건은 정렬 키를 그대로 `OR` 사슬로 편 것이다:

```sql
-- popular: (likeCount, createdAt, id) < (c.likeCount, c.createdAt, c.id)
   likeCount <  c.likeCount
OR (likeCount = c.likeCount AND createdAt <  c.createdAt)
OR (likeCount = c.likeCount AND createdAt =  c.createdAt AND id < c.id)
```

### 커서에 **정렬 키를 함께 싣는다**

커서는 `base64url("<sort>|<likeCount>|<createdAtMs>|<id>")` 다.

- **불투명 문자열**이라 클라이언트가 내부 값을 파싱해 쓸 수 없다(규약이 새어 나가지 않는다).
- 커서 안의 `sort` 가 요청의 `sort` 와 다르면 **400** 이다. 최신 탭 커서를 인기 탭에 그대로 쓰면 조건과 정렬이 어긋나 **조용히 중복·누락**이 나는데, 그것을 에러로 드러낸다. 탭을 바꾸면 커서를 버리고 처음부터 읽는 것이 맞다(화면도 쿼리 키가 바뀌며 자동으로 그렇게 한다).
- 깨진 커서도 400 이다 — 첫 페이지로 조용히 되돌리면 무한 스크롤이 같은 자리를 맴돈다.

`take: limit + 1` 로 한 줄 더 읽어 다음 페이지 유무를 판단하고, 마지막으로 **내보낸** 행으로 다음 커서를 만든다.

> **한계(정직하게)**: 커서는 "그 시점의 좋아요 수" 를 기억한다. 읽는 도중 어떤 글의 좋아요가 늘어 커서 위치를 뛰어넘으면 그 글이 다음 페이지에 한 번 더 나올 수 있다. 정렬 키 자체가 변하는 값이라 keyset 으로도 없앨 수 없고(offset 은 여기에 더 취약하다), **페이지 경계에서 값이 변하지 않는 한 중복·누락이 없다**는 것이 이 규약의 보장이다.

## 좋아요 정합성 — `likeCount` 는 **다시 세어 덮어쓴다**

`Post.likeCount` 는 `PostLike` 행 수의 비정규화 사본이라 어긋나면 **인기 탭 정렬이 거짓말을 한다.**

- **API 가 토글이 아니다.** `POST` = "좋아요 상태로 만든다", `DELETE` = "안 누른 상태로 만든다" — 목표 상태를 지정하는 두 동사라 같은 요청이 몇 번 와도 결과가 같다(멱등). 더블클릭·재전송·오프라인 재시도에 안전하다.
- 한 **트랜잭션** 안에서 ① 글 행을 `SELECT … FOR UPDATE` 로 잠그고 ② `PostLike` 를 만들거나(`skipDuplicates`) 지우고 ③ **남은 행을 다시 세어** `likeCount` 에 덮어쓴다.
- 증감식(`increment: 1`)이 아니라 **재계산**이라, 어떤 이유로 값이 어긋나 있어도 **다음 토글에서 스스로 고쳐진다**(테스트가 `likeCount = 99` 로 만들어 두고 확인한다).
- 잠금 덕에 같은 글에 동시에 들어온 요청이 줄을 서므로 세는 사이에 행이 늘거나 줄지 않는다.
- 마지막 갱신은 raw `UPDATE` 다 — Prisma 의 `update` 를 쓰면 `@updatedAt` 이 바뀌어 "언제 고친 글인지" 가 사라진다. **조회수 증가도 같은 이유로 raw UPDATE** 다.

테스트(`api/posts/[id]/like/route.test.ts`)는 모든 경로에서 `Post.likeCount === count(PostLike)` 를 확인한다.

## 지역(region) 선택지 — 상수표 하나

`Post.regionCode` 는 스키마 주석대로 **법정동 시군구 코드 5자리**, `regionName` 은 표시명이다.
선택지의 원본은 **`apps/web/src/features/community/regions.ts` 상수표 하나**이고, 서버(검증)와 클라이언트(셀렉트 UI)가 같은 배열을 읽는다.

| 항목 | 내용 |
|---|---|
| 출처 | 행정안전부 **법정동코드**의 앞 5자리(시도 2 + 시군구 3) |
| 범위 | **서울 25개 자치구**(11110 종로구 … 11740 강동구) + **경기 주요 10개 시**(41110 수원시 … 41590 화성시) |
| 기본값 | `11200` 서울 성동구 — 데모 시드의 건물이 성동구·강남구에 있다 |
| 검증 | zod `z.enum(코드 목록)` — 표에 없는 코드는 **400** |
| 저장 | 코드와 **그 시점의 표시명**(`"서울 성동구"`)을 함께 박는다 — 표가 바뀌어도 옛 글이 깨지지 않는다 |

**외부 주소 API 를 부르지 않는다.** 시군구 목록은 1년에 한 번 바뀔까 말까 한 값이라 런타임 의존을 만들 이유가 없다 — 키가 필요하고, 오프라인·CI 에서 목록이 비고, 선택지가 요청마다 달라져 테스트가 흔들린다. 지역을 늘리려면 배열에 줄만 더하면 된다. (T3.x 의 `features/address/**` 는 건물 주소 검색용이고 이 task 소유가 아니라 건드리지 않았다.)

## API 요청·응답

에러는 전부 `{ "error": { "code", "message", "details?" } }` 한 형태다([D1](../DECISIONS.md#-d1-api-스타일)).

### `GET /api/posts`

```
?region=11200&sort=popular&cursor=cG9wdWxhcnw1fDE3Nzg…&limit=20
```

`region` 생략 시 `11200`, `sort` 생략 시 `latest`, `limit` 생략 시 20(1~50).

```jsonc
// 200
{
  "posts": [
    {
      "id": "cmf0…",
      "regionCode": "11200",
      "regionName": "서울 성동구",
      "title": "관리비가 갑자기 두 배가 됐어요",
      "body": "지난달보다 관리비가 …",        // 목록은 120자 발췌
      "viewCount": 12,
      "likeCount": 3,
      "commentCount": 2,                      // 스레드에 보이는 댓글 수
      "createdAt": "2026-09-02T05:00:00.000Z",
      "updatedAt": "2026-09-02T05:00:00.000Z",
      "author": { "profileId": "cmf0…", "name": "김임대", "type": "LANDLORD" },
      "moderation": "VISIBLE",                // VISIBLE | BLINDED  (REMOVED 는 목록에 오지 않는다)
      "bodyHidden": false,                    // true 면 title·body 가 안내문으로 바뀌어 온다
      "mine": false,
      "liked": true
    }
  ],
  "nextCursor": "bGF0ZXN0fDB8MTc3O…",         // null 이면 끝
  "sort": "latest",
  "region": { "code": "11200", "name": "성동구", "label": "서울 성동구" }
}
```

| 실패 | status · code |
|---|---|
| 비로그인 | 401 `UNAUTHORIZED` |
| 프로필 없음(온보딩 전) | 403 `FORBIDDEN` |
| 모르는 지역·정렬·limit 범위 초과 | 400 `VALIDATION_ERROR` |
| **다른 탭의 커서·깨진 커서** | 400 `VALIDATION_ERROR` |

### `POST /api/posts`

```jsonc
// 요청 — 글쓴이는 활성 프로필이라 보내지 않는다
{ "regionCode": "11200", "title": "관리비가 갑자기 두 배가 됐어요", "body": "지난달보다 …" }

// 201
{ "post": { "…PostSummary…", "comments": [], "canEdit": true, "canInteract": true } }
```

제목 2~60자, 본문 5~2,000자(둘 다 `trim` 후). 어기면 400.

### `GET·PATCH·DELETE /api/posts/[id]`

```jsonc
// GET 200 — **조회수가 1 오른다**
{ "post": { "…PostSummary(body 전문)…",
            "comments": [
              { "id": "cmf0…", "postId": "cmf0…", "body": "저희도요",
                "createdAt": "…",
                "author": { "profileId": "cmf0…", "name": "박세입", "type": "TENANT" },
                "moderation": "VISIBLE", "bodyHidden": false, "mine": true, "canDelete": true }
            ],
            "canEdit": true, "canInteract": true } }

// PATCH 요청 — 보낸 필드만 바꾼다
{ "title": "고친 제목" }        // regionCode·body 도 가능. 빈 객체는 400

// DELETE 200 — 소프트 삭제
{ "deleted": true, "postId": "cmf0…" }
```

| 실패 | status · code |
|---|---|
| 비로그인 · 프로필 없음 | 401 · 403 |
| 없는 글 · **작성자가 지운 글** | 404 `NOT_FOUND` |
| **남의 글** 수정·삭제 | 403 `FORBIDDEN` |
| **블라인드된 글** 수정·삭제 | 409 `CONFLICT` |

**삭제가 소프트인 이유** — `Report.postId` 가 글을 참조하고 있어 하드 삭제가 애초에 불가능하고, 지난 신고 이력이 남아야 어드민이 판단할 수 있다. 그래도 **작성자가 지운 글은 목록·상세에서 완전히 사라진다**(404) — 블라인드와 다른 점이다([T4.2 규칙표](./t4.2-moderation.md#블라인드-노출-규칙표)).

### `POST·DELETE /api/posts/[id]/like`

```jsonc
// 200 — 응답의 likeCount 는 **다시 센 값**이라 그 자체가 진실이다
{ "liked": true, "likeCount": 3 }
```

| 실패 | status · code |
|---|---|
| 비로그인 · 프로필 없음 | 401 · 403 |
| 없는 글 · 작성자가 지운 글 | 404 `NOT_FOUND` |
| **블라인드된 글** | 409 `CONFLICT` |

### `GET·POST /api/posts/[id]/comments` · `DELETE /api/comments/[id]`

```jsonc
// GET 200 — 오래된 순
{ "comments": [ { "…PostCommentDto…" } ] }

// POST 요청·201 — **갱신된 스레드가 함께 온다**(왕복 1회로 댓글 수·목록이 맞는다)
{ "body": "저희 라인도 두 배 나왔어요." }
{ "comment": { … }, "post": { …PostDetail… } }

// DELETE /api/comments/[id] 200
{ "post": { …PostDetail… } }
```

| 실패 | status · code |
|---|---|
| 비로그인 · 프로필 없음 | 401 · 403 |
| 없는 글·댓글, 이미 지운 댓글 | 404 `NOT_FOUND` |
| **남의 댓글 삭제**(글쓴이라도) | 403 `FORBIDDEN` |
| **블라인드된 글에 댓글 · 블라인드된 댓글 삭제** | 409 `CONFLICT` |
| 본문 1~500자 위반 | 400 `VALIDATION_ERROR` |

## 조회수는 **화면 진입 1회 = 1**

상세는 서버 컴포넌트가 `getPostDetail(..., { countView: true })` 로 그리고, **클라이언트에서 다시 읽지 않는다** — 좋아요·댓글 응답에 실려 온 갱신본으로 화면 state 를 갱신한다(T2.6 민원 스레드와 같은 판단). Tanstack Query 로 상세를 두면 마운트 직후 재조회가 일어나 조회수가 두 번 오른다.

`GET /api/posts/[id]` 도 같은 함수를 부르므로 API 로 열어도 1 오른다.
