## 상태 전이표 — **정의는 한 곳뿐이다**

원본은 `apps/web/src/features/refund/status.ts` 의 `REFUND_TRANSITIONS` 이고, 단위 테스트(`status.test.ts`)가 이 표와 같은지 지킨다. 세입자 화면·세입자 API·어드민 화면이 **전부 같은 표**를 본다.

| 현재 | 목표 | 주체 | 액션 | 코멘트 |
|---|---|---|---|---|
| `DRAFT` 작성중 | `SUBMITTED` 제출 | 세입자 | `POST /api/refunds/[id]/submit` | — |
| `SUBMITTED` 제출 | `REVIEWING` 심사중 | 어드민 | **심사시작** `START` | 선택 |
| `REVIEWING` 심사중 | `NEED_MORE_DOCS` 보완요청 | 어드민 | **보완요청** `NEED_MORE_DOCS` | **필수** |
| `REVIEWING` 심사중 | `APPROVED` 승인 | 어드민 | **승인** `APPROVE` | 선택 |
| `REVIEWING` 심사중 | `REJECTED` 반려 | 어드민 | **반려** `REJECT` | **필수** |
| `NEED_MORE_DOCS` 보완요청 | `REVIEWING` 심사중 | 세입자 | 보완 재제출(같은 submit 엔드포인트) | — |
| `APPROVED` 승인 | `COMPLETED` 완료 | 어드민 | **지급 완료** `COMPLETE` | 선택 |
| `REJECTED` · `COMPLETED` | — | — | **종결(전이 없음)** | — |

**이 표에 없는 조합은 전부 409 `CONFLICT`** 다(같은 상태로의 전이 포함). 7개 상태 × 7개 = 49조합 중 허용은 7개뿐이고, 단위 테스트가 나머지 42조합을 하나씩 확인한다.

### 왜 이렇게 정했나

- **`SUBMITTED` 에서 바로 승인·반려할 수 없다.** 심사시작을 거쳐야 `reviewedById`(심사자)가 찍히고, 큐에서 "누가 잡고 있는 건인지" 가 드러난다. task 가 요구한 "SUBMITTED 에서만 심사시작" 도 이 규칙의 다른 면이다.
- **보완 재제출은 `SUBMITTED` 가 아니라 `REVIEWING` 으로 돌아간다.** 이미 심사자가 붙은 건이므로 제출 대기 줄의 맨 뒤가 아니라 **그 심사자 책상**으로 돌아가는 것이 맞다. 같은 엔드포인트가 현재 상태로 목표를 고른다(`submitTargetFor`).
- **반려·완료는 종결이다.** 되살리려면 새 신청을 만든다 — 결정 사유를 조용히 바꿔치기하지 못하게.
- **코멘트 필수는 보완요청·반려 둘뿐이다.** 신청자가 다음에 무엇을 해야 하는지 모르는 채 상태만 바뀌는 것을 막는다.
- 저장은 **전이 전 상태를 조건에 넣은 단일 `updateMany`** 라, 두 심사자가 동시에 눌러도 한쪽만 성공한다(`count === 0` → 409).

### 액션마다 무엇이 기록되나

| 기록 | 어디에 |
|---|---|
| 상태 | `RefundApplication.status` |
| **심사자** | `reviewedById` — **모든 심사 액션**에서 갱신(심사시작 포함) |
| **시각** | 결정은 `decidedAt`(심사시작은 결정이 아니라 찍지 않는다), 최초 제출은 `submittedAt`, 그 밖은 `updatedAt` |
| 심사 코멘트 | `reviewNote` — 액션마다 덮어쓴다(= 마지막 심사 코멘트) |
| **세입자 통지** | `MessageLog` 한 줄(알림톡 시뮬) — 액션마다 남으므로 **시간순 이력**이 된다 |

`MessageKind` 에 환급 전용 값이 없어 `ETC` 를 쓰고, 제목·본문에 상태·심사자·시각·신청 id·코멘트를 적는다.

> **완전한 감사 로그에는 테이블이 하나 더 필요하다**(`RefundReviewLog`: 신청 id·이전/다음 상태·심사자·코멘트·시각). 스키마는 Phase 5 가 마이그레이션 중이라 이 task 가 열 수 없어서 위 컬럼 + `MessageLog` 로 대신했다 → [T2.4 문서의 "스키마가 필요했지만 만들지 않은 것"](./t2.4-refund-apply.md#스키마가-필요했지만-만들지-않은-것).

## 어드민 인증 — **어드민 앱에는 로그인이 없다**(T6.3 범위)

어드민 로그인은 T6.3 몫이고, 이 task 는 그 파일들을 건드리지 않는다. 그래도 **심사 API 는 반드시 `User.isAdmin` 으로 판정해야** 한다. 그래서 이렇게 나눴다.

```
[어드민 브라우저]  ──(세션 없음)──▶  어드민 서버(3001)  ──x-admin-secret──▶  web API(3000)
                                     서버 액션·라우트                        requireRefundAdmin()
                                     (시크릿은 서버에만)                      ↓
                                                                    isAdmin User 를 찾아 심사자로 기록
```

`requireRefundAdmin(request)` (`apps/web/src/features/refund/ownership.ts`) 의 판정:

| 통로 | 판정 |
|---|---|
| ① **세션 쿠키** | `getCurrentUser()` → `isAdmin` 이면 통과(심사자 = 그 사용자), 아니면 **403 `FORBIDDEN`** |
| ② **서비스 시크릿** (`x-admin-secret`) | 세션이 없을 때만 본다. 값이 맞으면 DB 에서 `isAdmin: true` 인 계정을 찾아 **그 사람을 심사자로 기록**한다. 관리자 계정이 하나도 없으면 **403** |
| ③ 둘 다 없음 | **401 `UNAUTHORIZED`** |

- ②는 T1.4 크론 트리거(`CRON_SECRET` + 서버 액션)와 **같은 방식**이다. 시크릿은 어드민 서버에만 있고 브라우저 번들에 실리지 않는다. 값은 `ADMIN_API_SECRET`, 없으면 `CRON_SECRET` 을 쓴다(로컬·배포에 이미 있는 값이라 새 환경변수를 요구하지 않는다).
- **시크릿은 신분을 만들어 내지 못한다.** 통과해도 실재하는 `isAdmin` 계정을 찾아야 하고, 못 찾으면 403 이다 — `reviewedById` 는 언제나 진짜 관리자다.
- **로그인한 비어드민이 시크릿을 붙여도 승격되지 않는다.** 세션이 있으면 세션으로 판정한다(①이 ②보다 먼저다).
- **T6.3 이 어드민 로그인을 붙이면** ②분기(`resolveServiceAdmin`)를 지우고 어드민 앱이 세션 쿠키를 전달하게 바꾸면 된다. web 쪽 판정 코드는 그대로다.

> ⚠️ **어드민 앱 자체에는 아직 인증이 없다** — 크론 트리거 화면(T1.4)도 같은 상태다. 어드민 앱에 접근할 수 있으면 심사 화면과 서류 프록시를 쓸 수 있다. **어드민 배포를 비공개로 두는 것이 전제**이고, 이 구멍은 T6.3 이 닫는다. (web API 는 이 전제 없이도 안전하다 — 시크릿 없이는 401/403 이다.)

## 어드민 화면 — **규칙을 하나도 들고 있지 않다**

어드민은 별도 Next 앱이라 `apps/web/src/features/**` 를 import 할 수 없다. 상태 전이표를 복사하고 싶은 자리인데, 그러면 규칙이 두 벌이 되어 한쪽만 고치는 사고가 난다.

**대신 API 응답이 버튼을 실어 보낸다.**

```jsonc
"availableActions": [
  { "action": "NEED_MORE_DOCS", "label": "보완 요청", "targetStatus": "NEED_MORE_DOCS", "requiresNote": true },
  { "action": "APPROVE",        "label": "승인",      "targetStatus": "APPROVED",       "requiresNote": false },
  { "action": "REJECT",         "label": "반려",      "targetStatus": "REJECTED",       "requiresNote": true }
]
```

어드민 화면은 이 배열을 그대로 그리고, 코멘트 필수 여부도 `requiresNote` 를 읽는다. 상태 배지도 응답의 `statusLabel`·`statusTone` 을 쓴다. `apps/admin/src/app/refunds/shared.ts` 에 있는 것은 **응답을 읽기 위한 타입 미러**일 뿐 규칙이 아니다.

| 파일 | 역할 |
|---|---|
| `apps/admin/src/app/refunds/page.tsx` | 서버 컴포넌트 — `?filter=` 로 큐를 읽어 화면에 넘긴다(`force-dynamic`) |
| `apps/admin/src/app/refunds/actions.ts` | `"use server"` — `fetchRefundQueue`·`runRefundReview`. 시크릿을 붙여 web 을 호출한다 |
| `apps/admin/src/app/refunds/RefundReviewView.tsx` | 클라이언트 — 상태 필터 탭·목록·상세(신청 정보·산출 내역·서류)·액션 버튼·코멘트 |
| `apps/admin/src/app/refunds/documents/route.ts` | **서류 뷰어 프록시** — 브라우저 대신 어드민 서버가 web 의 private Blob 스트림을 받아 흘려보낸다 |
| `apps/admin/src/app/refunds/shared.ts` | 응답 타입 미러 + 필터 정의 + 포맷 |

- 목록은 **오래 기다린 순**(최초 제출 시각 오름차순)으로 온다.
- 필터 탭은 처리 대기(제출+심사중+보완요청) · 제출 · 심사중 · 보완요청 · 승인 · 반려 · 완료 · 작성중이고, 각 탭에 상태별 건수가 붙는다.
- 서류 링크는 어드민 프록시(`/refunds/documents?applicationId=…&documentId=…`)를 거친다 — 브라우저에는 세션이 없어 web 의 뷰어 경로를 직접 열 수 없기 때문이다.

## API 요청·응답

### `GET /api/refunds?scope=review`

```
?scope=review&status=SUBMITTED,REVIEWING,NEED_MORE_DOCS
```

`status` 를 생략하면 "손이 필요한" 세 상태가 기본이다. 모르는 값은 버린다.

```jsonc
// 200 — applications[] 는 T2.4 의 신청 DTO + 신청자 정보
{
  "applications": [
    {
      "…T2.4 RefundApplicationDto 그대로…",
      "tenantName": "박세입",
      "tenantPhone": "01022222222",
      "tenantProfileId": "cmf0…",
      "availableActions": [ { "action": "START", "label": "심사 시작",
                              "targetStatus": "REVIEWING", "requiresNote": false } ]
    }
  ],
  "counts": { "DRAFT": 1, "SUBMITTED": 2, "REVIEWING": 0, "NEED_MORE_DOCS": 1,
              "APPROVED": 0, "REJECTED": 0, "COMPLETED": 3 }
}
```

| 실패 | status · code |
|---|---|
| 세션도 시크릿도 없음 | 401 `UNAUTHORIZED` |
| **비어드민 세션** | 403 `FORBIDDEN` |
| 시크릿 불일치 · `isAdmin` 계정 없음 | 403 `FORBIDDEN` |

### `POST /api/refunds/[id]/review`

```jsonc
// 요청 — **액션 이름만** 보낸다. 목표 상태·코멘트 필수 여부는 서버의 전이표가 정한다
{ "action": "NEED_MORE_DOCS", "note": "주민등록등본에 전입일이 보이지 않습니다. 다시 올려 주세요." }
```

```jsonc
// 200 — 갱신된 신청 + 방금 남긴 알림톡 시뮬
{
  "application": { "…신청 DTO + tenantName/tenantPhone…", "status": "NEED_MORE_DOCS",
                   "reviewNote": "주민등록등본에 전입일이 …", "reviewedByName": "관리자",
                   "decidedAt": "2026-09-02T05:02:00.000Z",
                   "availableActions": [] },
  "notification": { "id": "cmf0…", "title": "[자리] 환급 신청이 「보완요청」 상태로 바뀌었습니다",
                    "toPhone": "01022222222", "sentAt": "2026-09-02T05:02:00.000Z" }
}
```

| 실패 | status · code |
|---|---|
| 세션도 시크릿도 없음 | 401 `UNAUTHORIZED` |
| **비어드민**(세입자 본인 포함) | 403 `FORBIDDEN` |
| 없는 신청 | 404 `NOT_FOUND` |
| 모르는 액션·1,000자 초과 코멘트 | 400 `VALIDATION_ERROR` |
| **코멘트가 필수인데 비었거나 공백뿐** | 400 `VALIDATION_ERROR` |
| **지금 상태에서 못 하는 액션**(SUBMITTED 에서 승인 등) | 409 `CONFLICT` — 문구가 이유를 설명한다 |

### `GET /api/refunds/[id]` · `GET /api/refunds/[id]/documents/[documentId]`

상세와 서류 뷰어는 세입자와 **같은 엔드포인트**를 쓴다(`requireApplicationAccess` 가 "낸 세입자 또는 어드민" 을 판정한다). 어드민이 부르면 상세에 신청자 정보가 붙는다. → [T2.4 문서](./t2.4-refund-apply.md#api-요청응답)

## E2E 에서 어드민을 어떻게 다뤘나

`e2e/refund-apply.spec.ts` 는 **세입자 여정은 브라우저로, 심사는 web API 로** 친다.

| 판단 | 이유 |
|---|---|
| 어드민 화면을 Playwright 로 몰지 않았다 | 어드민은 **별도 앱(3001)** 이고 `playwright.config.ts` 의 `webServer` 는 web 하나만 띄운다 — 그 설정 파일은 이 task 소유가 아니라 손대지 않았다. 게다가 어드민 화면은 규칙을 들고 있지 않아(위 참조) **위험이 전부 web API 쪽에 있다.** 화면 렌더링은 `pnpm build` 와 타입체크가 지킨다 |
| 심사 요청은 **어드민 세션 쿠키**로 보냈다(시크릿 헤더가 아니라) | 시드 관리자(`isAdmin: true`)에 세션 한 줄을 직접 만들어 쓰므로, 검증되는 것이 **본선 경로("`User.isAdmin` 기반 판정")** 다. 시크릿 경로는 단위 테스트가 따로 지킨다. 끝나면 그 세션을 지운다 |
| 업로드는 **실제 Blob 을 타지 않는다** | E2E 는 테스트 DB 를 보고 돌고, 그때 저장소가 메모리 드라이버로 떨어진다. 실제 Blob 은 ① 네트워크·토큰 의존으로 CI 를 깨뜨리고 ② 스토어에 테스트 쓰레기를 쌓는다. 드라이버만 바뀌고 **권한·제한·`documents` 기록·뷰어 스트리밍은 그대로 지나간다** |
