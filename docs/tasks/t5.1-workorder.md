## 거리 계산 유틸 — **T3.6 이 재사용한다**

```ts
// apps/web/src/lib/geo/distance.ts  (순수 모듈 — DB·네트워크 없음)
export type GeoPoint = { lat: number; lng: number };
export type RadiusCandidate = GeoPoint & { radiusKm: number };
export type RankedCandidate<T> = { candidate: T; distanceKm: number };

haversineKm(a: GeoPoint, b: GeoPoint): number           // 대권거리(km), 지구 반지름 6371
roundKm(km: number, digits = 3): number                  // 저장·표시용 반올림(기본 1m)
isWithinRadius(origin: GeoPoint, c: RadiusCandidate): boolean   // 거리 ≤ c.radiusKm (경계 포함)
rankByDistance<T extends RadiusCandidate>(
  origin: GeoPoint, candidates: readonly T[], options?: { limit?: number },
): RankedCandidate<T>[]                                  // 반경 필터 → 거리순 → 상한
```

- **반경은 후보가 정한다.** 요청자가 "몇 km 안에서 찾을지" 를 고르는 것이 아니라, 마스터·중개인이 자기 프로필에 "나는 여기서 N km 까지 간다"(`MasterDetail.radiusKm` · `RealtorDetail.radiusKm`)를 적어 둔다. 그래서 같은 거리라도 후보마다 판정이 갈린다.
- **T3.6 사용법**: `rankByDistance(building, realtorDetails, { limit: 20 })`. `RealtorDetail` 은 `{ lat, lng, radiusKm }` 을 이미 가지고 있어 `RadiusCandidate` 를 구조적으로 만족한다 — 어댑터가 필요 없다.
- 반환 `distanceKm` 은 `roundKm` 을 태운 값이라 그대로 `WorkOrderTarget.distanceKm`·`BrokerageTarget.distanceKm` 에 저장하고 화면에도 같은 값을 쓴다.
- 시드는 앱 소스를 import 할 수 없어(별 패키지) `seed.ts` 안에 같은 식을 한 번 더 적어 뒀다(주석으로 원본을 가리킨다).

## push 타겟 선정 규칙 — 넷을 **모두** 만족해야 한다

`features/workorder/matching.ts`

| 조건 | 판정 |
|---|---|
| ① 업종 일치 | `MasterDetail.categories` 에 의뢰의 `category` 가 들어 있다 |
| ② 활동반경 안 | `haversineKm(의뢰 건물, 마스터 사무소) ≤ MasterDetail.radiusKm` (경계 포함) |
| ③ 유료 | `plan = PRO` **이고** `planUntil` 이 null 이거나 지나지 않았다(`isProActive`) |
| ④ 상한 | 위를 통과한 마스터를 **거리순으로 최대 10명**(`WORK_ORDER_TARGET_LIMIT`) |

- **원점은 건물 좌표다.** `Unit` 에는 좌표가 없다 — 주소·좌표는 `Building` 이 가진다. 그래서 호실 작업이든 공용부 작업이든 매칭 원점은 건물이고, **건물이 없는 의뢰는 추천을 보내지 않는다**(0명).
- **두 번 불러도 안전하다.** 이미 보낸 마스터를 미리 걸러 내고(`@@unique` 가 한 겹 더 막는다) 새로 보낼 곳에만 `MessageLog` 를 남긴다 — 재발송 = *새로 조건을 만족하게 된* 마스터에게만 간다.
- **발송 실패가 의뢰를 되돌리지 않는다.** 의뢰 저장과 추천 발송을 같은 트랜잭션에 묶지 않았다. 추천은 부가 기능이고, 발송이 안 됐어도 마스터는 **전체 피드(pull)** 로 그 의뢰를 본다.
- `selectWorkOrderTargets(category, origin)` 는 **아무 것도 쓰지 않는다** — T3.6 의 "발송 전 대상 미리보기" 와 같은 자리에 그대로 쓸 수 있다.

## 상태 전이표

| 현재 \ 목표 | `DONE` 완료 | `CANCELLED` 취소 |
|---|---|---|
| `REQUESTED` 요청 | ✅ | ✅ |
| `QUOTED` 견적도착 | ✅ | ✅ |
| `ASSIGNED` 배정 | ✅ | ✅ |
| `DONE` 완료 | ❌ 409 | ❌ 409 |
| `CANCELLED` 취소 | ❌ 409 | ❌ 409 |

- **임대인이 고를 수 있는 목표는 완료·취소 둘뿐이다.** `QUOTED`·`ASSIGNED` 는 사람이 고르는 값이 아니라 견적(T5.3)이 도착·수락되며 옮기는 값이라 요청 스키마 enum 에서 빠져 있다 — 보내면 **400**. (민원 상태에서 `OPEN` 을 뺀 T2.6 과 같은 이유다.)
- **종결은 되돌릴 수 없다.** 돈이 오가는 작업의 종결 사유를 조용히 바꿔치기하지 못하게 한 선택이다 — 다시 하려면 의뢰를 새로 낸다.
- 전이 판정은 `features/workorder/status.ts` 의 `canTransitionWorkOrder` 한 곳뿐이다(화면 버튼의 `disabled` 도 같은 함수를 읽는다). 저장은 전이 전 상태를 조건에 넣은 단일 `updateMany` 라 동시 요청도 한쪽만 성공한다.

| 실패 | status · code |
|---|---|
| 비로그인 | 401 `UNAUTHORIZED` |
| 없는 민원 | 404 `NOT_FOUND` |
| 제3자 · **세입자**(스레드는 보지만 전환은 임대인만) | 403 `FORBIDDEN` |
| **이미 전환된 민원** | 409 `CONFLICT` |
| 업종 누락·모르는 업종·작업 내용 형식 오류 | 400 `VALIDATION_ERROR` |

- 권한 판정은 T2.6 의 `requireComplaintLandlord` 를 그대로 부른다 — **민원 판정을 새로 쓰지 않았다**(T2.6 이 남긴 메모의 규칙).
- 409 는 두 겹이다: 먼저 `WorkOrder.complaintId` 조회로 막고, 동시 요청은 `@unique` 위반(P2002)을 잡아 같은 409 로 바꾼다.
- 민원 상태는 **`IN_PROGRESS` 로 맞춘다**(이미 진행중이면 그대로). 전이표를 태우지 않는 이유는 여기서 하려는 일이 "상태 변경" 이 아니라 "전환" 이라서다 — 해결/반려로 닫혔던 민원도 전환하면 다시 열린다.
