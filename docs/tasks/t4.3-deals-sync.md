# T4.3 실거래가 수집 배치

> Phase 4 · 상태: ✅ · [Phase 구성](../PHASES.md)

| 엔드포인트 | 동작 |
|---|---|
| `POST /api/deals/sync` | 국토부 API 월별 수집 → upsert(금액은 원본 단위 **만원**). 크론(매일, 구독·최근 조회 지역)·온디맨드·어드민 수동 트리거 공용 |

**[T4.4 실거래가 조회·알림](./t4.4-deals-view.md)과 한 묶음으로 구현했다** — 수집한 것을 바로 소비하는 한 쌍이고,
수집이 만든 신규 거래가 곧 T4.4 구독자의 알림이 된다. **화면·구독 API·차트·접근 정책은 T4.4 문서**에 있다.

## 국토부 실거래가 API — 실호출로 확인한 것

| 용도 | 엔드포인트 | 공식 문서 |
|---|---|---|
| 아파트 **전월세** | `https://apis.data.go.kr/1613000/RTMSDataSvcAptRent/getRTMSDataSvcAptRent` | [15126474](https://www.data.go.kr/data/15126474/openapi.do) |
| 아파트 **매매** | `https://apis.data.go.kr/1613000/RTMSDataSvcAptTrade/getRTMSDataSvcAptTrade` | [15126469](https://www.data.go.kr/data/15126469/openapi.do) |

파라미터는 `serviceKey`·`LAWD_CD`(시군구 5자리)·`DEAL_YMD`(YYYYMM)·`numOfRows`·`pageNo`, **응답은 XML** 이다.

### ⚠️ 함정 ① 키는 **디코딩 상태**로 두고 이중 인코딩하지 않는다

`.env` 의 `DATA_GO_KR_API_KEY` 에는 포털의 **디코딩 키**(`+`·`/`·`=` 가 그대로 들어 있는 88자)를 넣는다.
URL 은 `features/deals/molit.ts` 의 `buildMolitUrl` **한 곳**에서만 만들고, `URLSearchParams` 가 조립하면서
**한 번만** 퍼센트 인코딩한다(`+` → `%2B`). 포털이 함께 주는 *인코딩 키*를 넣으면 여기서 한 번 더 인코딩돼
`%252B` 가 되고 **HTTP 403 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`** 가 난다. 문자열로 URL 을 이어 붙이면
반대로 인코딩이 아예 빠진다. 회귀를 막는 테스트가 `molit.test.ts > ⚠️ 이중 인코딩 방지` 에 있다.

### ⚠️ 함정 ② API 가 파라미터를 검증해 주지 않는다

**잘못된 `LAWD_CD`(99999)도, `DEAL_YMD`(2026)도 HTTP 200 + `resultCode 000` + 빈 `<items/>`** 로 온다(실호출 확인).
즉 우리가 막지 않으면 아무 값이나 통과한다. 그래서 `features/deals/schema.ts` 의 zod 가 먼저 막는다 — 지역은
**T4.1 상수표**(`features/community/regions.ts`)에 있는 35개 코드만, 월은 `YYYYMM` + 1~12월 + 2006년 이후.

### 응답 봉투는 두 가지다

| 상황 | 루트 | HTTP |
|---|---|---|
| 정상·빈 결과 | `<response><header><resultCode>000</resultCode>…<body><items>…` | 200 |
| 키 오류 | `<OpenAPI_ServiceResponse><cmmMsgHeader><errMsg>SERVICE_KEY_IS_NOT_REGISTERED_ERROR</errMsg>…` | 401·403 |

## XML 파싱 규칙 — **정의는 두 순수 모듈에 있다**

`features/deals/xml.ts`(스캐너) → `features/deals/parse.ts`(정규화). 둘 다 DB·네트워크를 모른다.

**XML 라이브러리를 넣지 않았다** — `pnpm-lock.yaml` 은 이 task 소유가 아니고, 응답이 속성·네임스페이스·CDATA·중첩이
없는 **한 겹짜리 평면 XML** 이라 30줄 스캐너로 충분하다. 실호출로 받아 둔 fixture 가 그것을 지킨다.

| 규칙 | 내용 |
|---|---|
| **금액 단위** | **만원 그대로 저장한다.** `<deposit>85,000</deposit>` → `85000`(8.5억). 원으로 환산하지 않는다 — [스키마 머리말](../../packages/db/prisma/schema.prisma)이 `RealTransaction` 만 API 원본 단위(만원)라고 못 박았고, 환산하면 원본과 대조할 수단이 사라진다 |
| **콤마** | `"249,000"` → `249000`. 콤마·공백을 지우고 정수로 읽는다. 숫자가 아니면 `null` |
| **빈 값** | `""` 가 아니라 **공백 한 칸**으로 온다(`<contractTerm> </contractTerm>`·`<floor> </floor>`·`<buildYear> </buildYear>`). 파서가 `trim` 한 뒤 **빈 문자열 = 값 없음**으로 본다 |
| **자기닫음** | 결과가 없으면 `<items/>` 다(`<items></items>` 가 아니다) |
| **엔티티** | 단지명의 `&` 는 `&amp;` 로 온다 — `&amp;`·`&lt;`·`&gt;`·`&quot;`·`&apos;`·`&#39;`·`&#x27;` 를 되돌린다 |
| **면적** | `excluUseAr` 그대로(`84.417` 처럼 소수 셋째 자리도 온다). 0 이하·빈 값이면 그 행을 버린다 |
| **층** | 지하는 `-1` 이다. 빈 값이면 `null`(버리지 않는다 — 금액은 유효하다) |
| **거래일** | `dealYear`·`dealMonth`·`dealDay` → **UTC 자정 `Date`**(T1.4 의 `@db.Date` 규칙). 2월 30일 같은 값은 버린다 |

### 유형은 응답이 아니라 **엔드포인트 + 월세액**이 정한다

| 엔드포인트 | 조건 | `RealDealType` | 채우는 칸 |
|---|---|---|---|
| `…AptTrade` (매매) | — | `SALE` | `price` = `dealAmount` |
| `…AptRent` (전월세) | `monthlyRent === 0` | `JEONSE` | `deposit`, `monthlyRent = 0` |
| `…AptRent` (전월세) | `monthlyRent > 0` | `WOLSE` | `deposit`, `monthlyRent` |

### 버리는 행

- 단지명·전용면적·거래일·대표 금액 중 하나라도 없는 행(저장해도 화면에 그릴 수 없다)
- **해제된 매매**(`cdealType === "O"`) — 취소된 계약이라 시세가 아니다
- **요청한 달·유형 밖의 행** — 저장된 행을 세는 조회가 그 달 범위로 묶여 있어, 범위를 벗어난 행이 섞이면 다른 달 조각이 그것을 자기 것으로 세지 못해 **멱등이 깨진다**

버린 수는 결과의 `discarded` 로 나온다.

## upsert 키와 멱등 보장 — **서명 개수를 맞춘다**

국토부 응답에는 **행을 가리키는 고유 id 가 없다.** `aptSeq` 는 단지 식별자이지 거래 식별자가 아니다.
그래서 "같은 거래" 를 **내용 서명**으로 정의한다(`parse.ts` 의 `dealSignature`):

```
lawdCd | dealType | 단지명(공백제거) | 면적(소수2) | 층 | 거래일 | 매매가 | 보증금 | 월세 | 건축년도
```

면적을 소수 둘째 자리로 자르는 것은 `Float` 왕복에서 끝자리가 흔들려도 같은 거래로 보기 위해서다.

### 그런데 **내용이 똑같은 행이 한 응답에 두 번 온다**

실호출 응답(성동구 2026-07 전월세)에 `강변현대 81.8㎡ 19층 보증금 6억` 이 **두 줄** 들어 있었다.
같은 날 같은 평형에 계약이 둘 있으면 그렇게 나온다. 서명으로 dedupe 해 버리면 거래 건수가 줄어 시세가 틀어진다.

그래서 **dedupe 가 아니라 개수 맞추기**다:

1. 받은 행을 서명별로 세어 `{서명 → 개수}` 를 만든다.
2. DB 의 **그 지역·그 달·그 유형** 행도 같은 방식으로 센다.
3. **부족한 만큼만** `createMany` 한다 — `max(0, 받은 개수 − 저장된 개수)`.

두 번 돌리면 2단계 개수가 이미 같아져 **0건 생성**이다. 중복 행 2건은 계속 2건으로 남는다(3건이 되지도, 1건으로 줄지도 않는다).

> **DB 유니크 제약이 없다.** `RealTransaction` 에는 `@@index([lawdCd, dealType, dealDate])` 만 있고 유니크가 없어
> (스키마는 이 task 소유가 아니다) 멱등을 애플리케이션이 보장한다. 같은 (지역·월·엔드포인트)를 **동시에** 두 번
> 수집하면 둘 다 "부족함" 을 보고 이중 삽입할 수 있어 프로세스 안에서는 `withSyncLock`(진행 중 약속 공유)으로
> 줄을 세운다. 인스턴스가 여러 개면 그 보호가 닿지 않는다 → [스키마가 필요했지만 안 만든 것](#스키마가-필요했지만-안-만든-것).

### 부분 실패 격리

수집 단위는 **(지역 × 월 × 엔드포인트)** 하나다. 매매가 죽어도 전월세는 저장되고, 7월이 죽어도 8월은 저장된다.
실패는 던지지 않고 `failures[]` 에 쌓여 응답에 그대로 실린다. 한 조각 안에서 **중간 페이지가 실패하면 그 조각은
통째로 실패**다 — 반쪽만 저장해 두면 다음 실행이 나머지를 채우지 않기 때문이다(멱등이라 통째로 다시 읽으면 된다).

## 트리거 3경로 — **엔드포인트 하나, 인증은 새로 만들지 않았다**

```
① 크론      POST /api/cron/daily ──(원장 크론 뒤에)──▶ runDealsSyncCron()
② 어드민    어드민(3001) /deals ──서버액션 + x-cron-secret──▶ POST /api/deals/sync ──▶ runDealsSync()
③ 온디맨드  GET /api/deals (미수집 지역 첫 조회) ────────서버 내부 호출────────────▶ runDealsSync()
```

| 경로 | 인증 | 대상 | 월 |
|---|---|---|---|
| ① 크론 | `x-cron-secret`·`Authorization: Bearer <CRON_SECRET>` (T1.4 그대로) | 구독 지역 + 최근 30일 수집분이 있는 지역(최대 20곳) | 당월 + 전월 |
| ② 어드민 수동 | 같은 크론 시크릿(서버 액션이 붙인다) **또는** 어드민 세션 `isAdmin`·`x-admin-secret`(T2.5 그대로) | 화면에서 고른 지역(비우면 ①과 같음) | 화면에서 입력(비우면 당월+전월) |
| ③ 온디맨드 | 없음(HTTP 를 거치지 않는 서버 내부 호출) | 지금 보고 있는 지역 **1곳** | 최근 3개월 |

### 왜 **크론을 새로 만들지 않고 일일 크론에 얹었나**

`vercel.json` 의 `crons` 는 배포 설정이고 Hobby 플랜은 스케줄 수·빈도가 제한된다. 수집도 "하루 한 번" 이면
충분하므로 스케줄을 늘리는 대신 **T1.4 의 하루치 크론 뒤에 이어 붙였다.** 응답에는 기존 필드가 한 글자도
바뀌지 않고 **`deals` 블록만 추가**된다. 실거래가 수집은 어떤 실패도 던지지 않으므로 국토부가 죽어 있어도
원장 크론 결과는 그대로 나간다. 서버에 `DATA_GO_KR_API_KEY` 가 없으면 부르지도 않고 `{"skipped":"NO_KEY"}` 다.

`POST /api/deals/sync` 는 그대로 남겨 두었다 — 어드민 수동 트리거와 curl 이 지역·월을 골라 부를 자리다.

### "최근 조회 지역" 을 어떻게 알았나

조회 이력을 남기는 테이블이 없어서 **수집분이 남아 있는 지역**(`RealTransaction.fetchedAt` 최근 30일)을 대용으로 쓴다.
누군가 `/deals` 에서 그 지역을 처음 열면 ③ 온디맨드가 행을 만들고, 그 뒤로는 ① 크론이 매일 이어서 채운다.
구독 지역이 목록 앞이라 상한(20곳)에 걸리면 **수집분 쪽부터 잘린다.**
한계: **열어 봤지만 거래가 0건인 지역**은 흔적이 남지 않아 크론 대상에 들어오지 않는다.

### 왜 당월 + 전월인가

부동산거래신고법상 계약일로부터 **30일 이내 신고**라, 지난달 거래가 이번 달 내내 계속 쌓인다. 당월만 긁으면
지난달 데이터가 영영 절반만 남는다. 온디맨드는 화면이 비어 보이지 않게 3개월을 긁는다. 둘 다 멱등이라 겹쳐도 안전하다.

## API 요청·응답

에러는 전부 `{ "error": { "code", "message", "details?" } }` 한 형태다([D1](../DECISIONS.md#-d1-api-스타일)).

### `POST /api/deals/sync`

```jsonc
// 요청 — 전부 선택. 본문이 아예 없어도 된다(크론이 그렇게 부른다)
{ "lawdCd": "11200",              // 생략 → 구독 지역 + 최근 수집 지역(최대 20곳)
  "months": ["202609", "202608"], // 생략 → 당월 + 전월
  "dealTypes": ["SALE"] }         // 생략 → 매매·전세·월세 전부
```

```jsonc
// 200 — 어드민 패널이 이 표를 그대로 그린다
{
  "ok": true,
  "ranAt": "2026-09-02T13:10:00.000Z",
  "targets": [ { "lawdCd": "11200", "regionLabel": "서울 성동구", "dealYm": "202607" } ],
  "regionsScanned": 1,
  "monthsScanned": 1,
  "requests": 4,          // 국토부 호출 횟수(페이지 포함) — 쿼터를 눈으로 본다
  "fetched": 50,          // 파싱에 성공하고 그 달·유형에 해당하는 행
  "created": 50,          // 새로 저장 — 두 번째 실행에는 0
  "skipped": 0,           // 이미 있어 건너뜀 = 멱등의 증거
  "discarded": 3,         // 필수값 누락·해제 거래·범위 밖
  "failures": [ { "lawdCd": "11200", "dealYm": "202607",
                  "endpoint": "TRADE", "reason": "UNAUTHORIZED", "status": 403 } ],
  "alertsSent": 2,        // 구독자 알림톡 시뮬(MessageLog) 건수
  "durationMs": 812,
  "triggeredBy": "CRON"   // CRON | ADMIN
}
```

| 실패 | status · code |
|---|---|
| 시크릿 없음·틀림, 비로그인 | 401 `UNAUTHORIZED` |
| 비어드민 세션, `isAdmin` 계정 없음 | 403 `FORBIDDEN` |
| 모르는 지역, `YYYYMM` 아닌 월, 모르는 유형, 깨진 JSON | 400 `VALIDATION_ERROR` |

**부분 실패는 200 이다** — 한 조각이 죽어도 나머지는 저장되고 사유는 `failures[]` 로 드러난다.

### `POST·GET /api/cron/daily` 의 `deals` 블록 (추가분)

```jsonc
// 기존 필드는 그대로이고 아래 한 칸만 붙는다
"deals": { "skipped": null, "regionsScanned": 2, "monthsScanned": 2, "requests": 8,
           "fetched": 96, "created": 12, "alreadyHad": 84, "discarded": 4,
           "failed": 0, "alertsSent": 1, "durationMs": 1204 }
// 키가 없으면
"deals": { "skipped": "NO_KEY" }
```

## 스키마가 필요했지만 안 만든 것

`packages/db/prisma/**` 는 이 task 소유가 아니라 열지 않았다. 아래는 **다음에 스키마를 여는 task 가 가져가면 좋을 것들**이다.

| 필요했던 것 | 지금 어떻게 대신했나 |
|---|---|
| **`RealTransaction` 유니크** — 예: `@@unique([lawdCd, dealType, aptName, areaM2, floor, dealDate, price, deposit, monthlyRent])` (또는 서명 문자열 컬럼 + 순번) | 서명 개수 맞추기 + 프로세스 내 락. **단일 인스턴스에서는 완전히 멱등**이지만, 여러 인스턴스가 같은 (지역·월)을 동시에 수집하면 이중 삽입이 가능하다. DB 유니크가 있으면 `skipDuplicates` 한 줄로 끝난다 |
| **`RealTransaction.canceledAt`**(해제 거래) | 해제된 매매(`cdealType=O`)는 **저장하지 않는다**. 이미 저장한 뒤에 해제된 거래는 지우지 못한다 — 컬럼이 있으면 표시만 하고 남길 수 있다 |
| **`RealTransaction.aptSeq`·`umdNm`·`jibun`** | `raw` Json 에 원본 item 을 통째로 남겨 뒀다. 단지 식별을 `aptName` 문자열로 하고 있어 같은 이름의 다른 단지를 구분하지 못한다(알림 매칭도 마찬가지) |
| **조회 이력 테이블**(크론의 "최근 조회 지역") | `RealTransaction.fetchedAt` 최근 30일로 대신한다. 열어 봤지만 거래가 0건인 지역은 크론 대상에 들어오지 않는다 |
| **`MessageKind.REAL_DEAL_ALERT`** | `ETC` 를 쓴다(T2.5 환급 통지와 같은 사정). 발송 이력 화면에서 종류로 걸러 낼 수 없다 |
| **실거래가 시드** | 시드에 `RealTransaction` 이 한 줄도 없다. 데모 첫 진입이 온디맨드 수집(수 초)을 타므로, 성동구·강남구 최근 3개월을 시드에 넣어 두면 화면이 즉시 찬다. E2E 는 그래서 **스펙 안에서 직접 적재**한다 |

> **[PHASES.md](../PHASES.md) 의 T4.3 상태는 갱신하지 않았다** — 파일 소유권상 이 task 범위 밖이라 Phase 4 통합 시점에 함께 ✅ 로 바꾼다.
