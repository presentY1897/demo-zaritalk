# T3.1 매물 등록

> Phase 3 · 상태: ✅ · [Phase 구성](../PHASES.md)

| 라우트/API | 동작 |
|---|---|
| `/landlord/units/[id]/listing` | 거래유형(전세/월세)·보증금·월세·입주가능일·사진·설명, 상태 변경(OPEN/RESERVED/CLOSED). 수락 중개인도 등록 가능(T3.7) |
| `POST /api/listings` | 등록 — 소유 임대인·수락 중개인 |
| `GET·PATCH·DELETE /api/listings/[id]` | 상세·수정·상태 변경·삭제 |

> task 표는 `POST·PATCH /api/listings` 였지만 **수정은 대상이 하나로 정해져야** 해서
> `PATCH /api/listings/[id]` 로 나눴다(나머지 리소스와 같은 모양). `DELETE` 를 더한 이유는
> T1.1 의 호실 삭제가 "등록된 매물이 있으면 409 — 매물을 먼저 내려 주세요" 라고 안내하는데
> 매물을 지울 길이 없으면 그 안내를 따를 수 없기 때문이다.

**[T3.4 근무지](./t3.4-workplace.md)와 한 묶음으로 작업했다** — 둘 다 주소 검색이 필요해서
공용 컴포넌트를 이 task 에서 만들었다. 컴포넌트 API 는 아래 "공용 주소 검색" 절.

## 권한 규칙 — 소유 임대인 또는 수락 중개인

판정은 `features/listing/permissions.ts` **한 곳**에서 한다. T1.1 소유권 가드와 같은
`Guarded<T>` 규약이라 라우트 핸들러는 결과만 early return 한다.

```ts
const actor = await requireListingActorForUnit(unitId);
if (actor.response) return actor.response;      // 401 · 404 · 403
actor.data.role;                                // "LANDLORD" | "REALTOR"
actor.data.profile.id;                          // Listing.listedByProfileId 가 된다
```

| 상황 | status · code |
|---|---|
| 비로그인·만료 세션 | 401 `UNAUTHORIZED` |
| 없는 호실·매물 id | 404 `NOT_FOUND` |
| 임대인·중개인 프로필이 아예 없음(세입자 계정 등) | 403 `FORBIDDEN` |
| 남의 호실 임대인 / 수락하지 않은 중개인 | 403 `FORBIDDEN` |

| 행위 | 소유 임대인 | 수락 중개인 |
|---|---|---|
| 등록 · 조건 수정 · 상태 변경 | ✅ | ✅ |
| **삭제** | ✅ | ❌ 403 — 중개인이 매물을 내리는 정상 경로는 `status: "CLOSED"` 다 |

- 프로필은 활성 프로필 쿠키가 아니라 **유형으로** 고른다(T1.1 `findLandlordProfile` 과 같은 규칙) —
  세입자로 전환한 상태에서 API 를 불러도 결과가 같다.
- **화면은 남의 자원을 404 로 막고 API 는 403 을 준다** — T1.1 이 정한 규칙 그대로다.

### 중개인 경로는 판정만 열어 뒀다 (T3.7 미구현)

"수락" 은 `BrokerageTarget.status === ACCEPTED` 이고 그 타겟이 붙은 `BrokerageRequest.unitId` 가
이 호실인 경우다(`hasAcceptedBrokerage`). **그 상태를 만드는
`POST /api/brokerage-targets/[id]/respond` 는 [T3.7](./t3.7-realtor-inbox.md) 소유라 아직 없다.**
지금 화면으로는 중개인이 이 경로를 탈 수 없고, 여기서는 판정만 열어 뒀다 —
T3.7 이 respond 라우트를 붙이면 **코드 변경 없이** 동작한다. 권한 판정 자체는 테스트가
데이터를 직접 만들어 검증한다(`features/listing/testing.ts` 의 `createBrokerageTarget`).

## 등록을 막는 규칙 (409)

`features/listing/queries.ts` 의 `listingBlockedReason` 한 곳에서 판정하고, 화면 안내 문구와
API 409 메시지가 **같은 문자열**이다.

| 상황 | 판정 | 문구 |
|---|---|---|
| **계약중 호실** | `deriveUnitStatus`(T1.1) ≠ `VACANT` — 즉 `ACTIVE` **또는** `PENDING_TENANT` 계약이 있음 | "계약이 있는 호실에는 매물을 등록할 수 없습니다." |
| 이미 살아 있는 매물 | 같은 호실에 `OPEN`·`RESERVED` 매물이 1건이라도 있음 | "이미 등록된 매물이 있습니다." |

- 대기(`PENDING_TENANT`)까지 막는 이유: 세입자 연결만 안 됐을 뿐 **이미 계약이 잡힌 집**이다.
- `ENDED`·`CANCELLED` 계약만 있으면 공실이라 등록된다.
- 호실 상태는 T1.1 의 `deriveUnitStatus` 를 그대로 쓰고, 연체 판정은 T1.4 원장 엔진
  (`resolveChargeStatus`)으로 오늘(KST) 기준 재판정한다 — 자산 그리드와 같은 답을 낸다.

## 상태 규칙 (`features/listing/status.ts`)

| 현재 | 갈 수 있는 곳 | 조건 |
|---|---|---|
| `OPEN` 공개 중 | `RESERVED` · `CLOSED` | — |
| `RESERVED` 예약 | `OPEN` · `CLOSED` | **`OPEN` 으로 되돌리려면 호실이 공실이어야 한다** |
| `CLOSED` 종료 | 없음 | 되돌릴 수 없다 — 다시 올리려면 새로 등록 |

- 등록은 **언제나 `OPEN`** 으로 시작한다(요청 본문으로 상태를 지정할 수 없다).
- 같은 상태로의 전이는 **멱등하게 허용**한다 — 이미 그 상태인 버튼을 눌러도 409 가 아니다.
- `CLOSED` 를 종료 상태로 둔 이유: 계약이 잡혀 내려간 매물을 조건 그대로 되살리면
  "언제 어떤 조건으로 올렸던 매물인가" 이력이 뭉개진다. 이력은 남기고 새 매물을 만든다.
  **종료한 매물은 조건 수정도 409** — 아무 데도 노출되지 않는 매물을 고치고 있다는 착각을 막는다.
- `RESERVED → OPEN` 에만 공실 조건을 다시 거는 이유: 예약 사이 계약이 성립했을 수 있다.
  계약중 호실이 `/search`(T3.2) 목록에 다시 뜨는 일을 막는다.
- 화면 버튼의 비활성 여부와 API 409 사유는 **같은 함수**(`checkStatusTransition`)가 낸다.

## 사진 처리 — URL 입력, T2.4 업로더 연결은 뒤로

**지금은 이미지 URL 입력(최대 5장) 또는 생략이다.** 파일 업로더를 새로 만들지 않았다.

- `POST /api/uploads`([T2.4](./t2.4-refund-apply.md))는 `applicationId`(환급 신청)를 **필수**로
  받고 권한 판정도 `requireOwnApplication` 에 묶여 있어 매물에 그대로 쓸 수 없다.
  그 라우트와 `features/refund/**` 는 이번 task 소유가 아니라 손대지 않았다.
- **연결 지점** — T2.4 주석이 이미 밝혀 둔 일반화 방향(`target=…&<id>=…` 분기)에
  `target=listing&listingId=…` 를 더하고 권한을 `requireListingActorForListing` 으로 바꾸면 된다.
  저장 계층(`features/refund/storage.ts`)·제한 규칙(`documents.ts`)은 그대로 쓸 수 있고,
  **저장 형태는 바뀌지 않는다** — `Listing.photos` 는 이미 URL 문자열 배열이다.
  화면에서 바꿀 곳은 `features/listing/ListingForm.tsx` 의 "사진" 블록 하나뿐이다.
- 검증: `http(s)` 스킴만, 주소 500자·5장 상한. 서버 스키마(`schema.ts`)와 폼이 같은 zod 를 쓴다.

## 요청·응답

에러는 D1 규약대로 `{ "error": { "code", "message", "details?" } }` 한 형태다.

### `POST /api/listings`

```jsonc
// 요청 — description·photos·availableFrom 은 선택. 상태는 지정할 수 없다(항상 OPEN)
{
  "unitId": "cmf0…", "dealType": "WOLSE",
  "deposit": 10000000, "monthlyRent": 500000,
  "availableFrom": "2026-11-01",
  "description": "역까지 도보 5분",
  "photos": ["https://cdn.example.com/a.jpg"]
}
// 201
{
  "listing": {
    "id": "cmf0…", "unitId": "cmf0…", "dealType": "WOLSE",
    "deposit": 10000000, "monthlyRent": 500000,
    "description": "역까지 도보 5분", "photos": ["https://cdn.example.com/a.jpg"],
    "availableFrom": "2026-11-01", "status": "OPEN",
    "createdAt": "2026-09-02T…", "updatedAt": "2026-09-02T…",
    "listedBy": { "profileId": "cmf0…", "role": "LANDLORD", "name": "김임대" }
  }
}
```

| 실패 | status · code |
|---|---|
| 비로그인 | 401 `UNAUTHORIZED` |
| 없는 호실 | 404 `NOT_FOUND` |
| 남의 호실·수락하지 않은 중개인·자격 없는 프로필 | 403 `FORBIDDEN` |
| **계약중·대기 호실** / **이미 살아 있는 매물** | 409 `CONFLICT` |
| 전세인데 월세>0, 월세인데 월세=0, 사진이 http(s) 아님·6장 이상, 날짜 형식 | 400 `VALIDATION_ERROR` |

### `PATCH /api/listings/[id]`

```jsonc
// 요청 — 보낸 필드만 바뀐다. description 은 빈 문자열이면 지워진다(null)
{ "deposit": 12000000 }
{ "status": "RESERVED" }
// 200 { "listing": …ListingDto… }
```

빈 본문 `{}` 은 400. **거래유형·월세는 저장된 값과 합친 뒤** 정합성을 본다 —
`{ "dealType": "JEONSE" }` 만 보내면 저장된 월세가 0이 아니라 400 이다.

### `GET /api/listings/[id]` · `DELETE /api/listings/[id]`

상세는 `{ "listing": …ListingDto… }`, 삭제는 `204 No Content`(임대인만).

## 화면

- `/landlord/units/[id]/listing` 한 화면에서 **등록 · 조건 수정(시트) · 상태 변경 · 삭제**를 다 한다.
  매물이 없고 공실이면 등록 폼, 매물이 있으면 요약 카드 + 상태 버튼 3개, 막혀 있으면 사유만 보여 준다.
- 진입점은 T1.1 이 자리를 잡아 둔 호실 상세의 **「매물 등록」 버튼**(`data-testid="listing-create"`)이다.
  매물이 이미 있으면 매물 카드의 **「매물 관리」**(`listing-manage`)로도 들어간다.
- 배지는 `@zari/ui` `Badge` 의 `tone` 만 쓴다 — 하드코딩 색상 0. 색과 **라벨을 함께** 보여 준다(T0.6).

# 공용 주소 검색 (T3.1 이 만들고 T3.2·T3.3·T3.6 이 재사용)

카카오 로컬 API 를 **우리 서버 프록시**로 감싸고, 그 앞에 검색 필드 컴포넌트 하나를 둔다.

| 파일 | 역할 |
|---|---|
| `features/address/coords.ts` | **좌표 검증 단일 출처** — `latSchema`·`lngSchema`·`isWithinKorea`(위 33~39 / 경 124~132) |
| `features/address/kakao.ts` | **서버 전용** 카카오 클라이언트 — 인증 헤더·정규화·실패 접기 |
| `features/address/schema.ts` | 프록시 쿼리 스키마(검색어 2~50자, size ≤ 15) |
| `features/address/failure.ts` | 카카오 실패 → D1 규약 응답(사유별 문구) |
| `features/address/types.ts` | `AddressCandidate`·`AddressSelection` + `toSelection`·`displayAddress` |
| `features/address/api.ts` · `hooks.ts` | fetch 래퍼 + `useAddressSearch()` |
| `features/address/AddressSearchField.tsx` | **검색 필드 컴포넌트** |
| `features/address/testing.ts` | 카카오 응답 픽스처(실호출 형태 그대로) |

## 컴포넌트 API

```tsx
import { AddressSearchField } from "@/features/address/AddressSearchField";
import type { AddressSelection } from "@/features/address/types";

const [area, setArea] = useState<AddressSelection | null>(null);

<AddressSearchField
  label="주소"            // 기본 "주소"
  required
  helper="…"              // 기본: "검색 후 목록에서 고르면 좌표가 자동으로 채워집니다."
  placeholder="…"
  value={area}            // AddressSelection | null
  onChange={setArea}
  errorMessage={formError} // 폼 검증 실패 문구(선택 안 함 등)
  size={8}                // 후보 수 1~15
  testId="building-address"
/>
```

```ts
type AddressSelection = {
  address: string;            // 지번 주소
  roadAddress: string | null; // 도로명(없는 결과도 있다)
  lat: number;
  lng: number;
  placeName?: string | null;  // 장소 검색 결과에만 — 근무지 라벨 자동 제안에 쓴다
};
```

- task 가 요구한 `{ address, roadAddress, lat, lng }` 에 `placeName` 만 더한 **상위 집합**이다.
- **좌표 입력칸이 없다.** 좌표는 고른 후보에서만 들어온다 — 손으로 적을 수 없다.
- 고른 뒤에는 결과 요약 + 「변경」 버튼만 남는다. 「변경」을 누르면 검색 상태로 돌아온다.
- **자동 검색을 하지 않는다** — 「검색」 버튼·Enter 로만 호출한다. 외부 호출 수를 사용자가
  통제하게 하고, 같은 검색어는 Tanstack Query 캐시(5분)로 재사용한다.
- `data-testid` 는 `testId` 접두사에 `-input` · `-submit` · `-option-<i>` · `-selected` ·
  `-change` · `-empty` 가 붙는다.
- 헬퍼 `displayAddress(value)` — 도로명이 있으면 도로명, 없으면 지번. `toSelection(candidate)` —
  후보 → 폼 값.

## 프록시 라우트 스펙

### `GET /api/address/search?query=&size=`

```jsonc
// 200
{
  "candidates": [
    {
      "id": "address:37.5582053468995,127.027507006183:서울 성동구 행당동 347",
      "address": "서울 성동구 행당동 347",
      "roadAddress": "서울 성동구 행당로 79",
      "lat": 37.5582053468995, "lng": 127.027507006183,
      "placeName": "행당동 대림아파트",   // 장소 결과면 place_name, 주소 결과면 건물명
      "category": null,                    // 장소 결과의 category_group_name
      "source": "ADDRESS"                  // ADDRESS | PLACE
    }
  ],
  "meta": { "total": 200, "isEnd": false }
}
```

- **주소 검색과 장소 키워드 검색을 함께 부른다.** 사용자는 "행당로 79"(주소)도
  "왕십리역"(장소)도 같은 칸에 치기 때문이다. 주소 결과를 앞에 놓고 합치며, 같은 좌표+주소는
  한 번만 담는다. **한쪽이 실패해도 다른 쪽 결과를 준다**(양쪽 실패면 500).
- 좌표는 카카오가 문자열 `x`(경도)·`y`(위도)로 주므로 **여기서 숫자로 바꾸고**,
  한국 범위(`isWithinKorea`) 밖 결과는 버린다.
- 결과 0건은 **에러가 아니라 200 + 빈 배열**이다.

| 실패 | status · code |
|---|---|
| 검색어 2자 미만·50자 초과, `size` 범위 밖 | 400 `VALIDATION_ERROR` (외부 호출도 하지 않는다) |
| 카카오 키 없음·인증 실패·쿼터 초과·장애·타임아웃(4초) | 500 `INTERNAL_ERROR` — 사유는 **문구로만** 구분 |

> 502 를 쓰지 않은 이유: `lib/api/response.ts` 의 `ApiErrorCode` 에 502 자리가 없고 그 파일은
> 공용 규약(다른 task 소유)이라 코드를 늘리지 않았다. 카카오 원문 오류
> (`{"errorType":"AccessDeniedError",…}`)는 **그대로 흘리지 않는다**.

### `GET /api/address/reverse?lat=&lng=`

```jsonc
// 200 — 바다·비주소 지역이면 { "address": null }
{ "address": { "address": "서울 성동구 행당동 347", "roadAddress": "서울 성동구 행당로 79",
               "lat": 37.5582, "lng": 127.0275, "placeName": null } }
```

좌표 누락·숫자 아님·**대한민국 범위 밖**이면 400. 지금 화면에서 쓰는 곳은 없고
**T3.2(지도 핀 이동 → 주소 표시)** 가 쓸 자리라 같은 규약으로 함께 열어 뒀다.

### 키 보호

- `KAKAO_REST_API_KEY` 는 **서버에서만** 읽는다(`features/address/kakao.ts` 한 곳).
  인증 헤더 `Authorization: KakaoAK <키>` 는 그 파일에서만 붙이고, 쿼리스트링에 넣지 않는다.
- 응답 본문·헤더 어디에도 키가 담기지 않는다 — 테스트가 문자열 포함 여부로 검증한다.
- 지도 표시용 `NEXT_PUBLIC_KAKAO_MAP_JS_KEY` 는 **별개의 JS 키**다(T3.2 가 쓴다).

### 로그인을 요구하지 않는다

온보딩(`/onboarding?ticket=`)의 중개인·마스터 활동지역 입력은 **세션이 생기기 전**에 주소를
고른다 — 여기서 401 을 내면 가입 자체가 막힌다. T3.2 의 비로그인 매물 탐색도 같다.
대신 검색어 길이(2~50)·후보 수(≤15)를 스키마로 조이고 응답에는 좌표·주소만 담는다.

## E2E 에서 카카오 — 실호출 대신 프록시 앞 mock

주소 검색은 화면 → `GET /api/address/search`(우리 서버) → 카카오 순으로 흐른다.
E2E 가 카카오까지 실제로 가면 ①네트워크·쿼터에 여정 전체가 매달리고 ②CI 에는
`KAKAO_REST_API_KEY` 가 없어 항상 깨지며 ③검색 결과가 바뀌면 단언이 깨진다.

그래서 **브라우저가 우리 API 를 부르는 지점**을 `page.route("**/api/address/search*")` 로
가로채 고정 응답을 준다(`e2e/address.ts`). 컴포넌트(검색·후보 목록·선택·좌표 반영)와
그 뒤 저장 여정은 그대로 지나간다. 프록시 라우트 자체(키 보호·정규화·빈 결과·업스트림 오류)는
Vitest 에서 `fetch` 를 mock 해 검증하므로 **커버리지 구멍이 생기지 않는다.**

`playwright.config.ts` 에 플래그를 넣는 방법(서버 쪽 픽스처 모드)도 가능했지만 루트 설정 파일이라
이번 task 범위 밖이고, 프로덕션에 픽스처 스위치를 남기지 않는 편이 낫다고 판단했다.

## 스키마를 건드리지 않고 앱에서 막은 것

`packages/db/prisma/**` 는 이번 task 소유가 아니라 손대지 않았다. 대신 규칙을 라우트에서 지킨다 —
**동시 요청이 아주 짧은 창에서 겹치면 뚫릴 수 있는 지점**이라 여기 남겨 둔다.

| 규칙 | 지금 | 스키마로 옮긴다면 |
|---|---|---|
| 호실당 살아 있는 매물 1건 | `findLiveListing` + 409 | `Listing` 에 부분 unique 인덱스(`unitId` where `status <> 'CLOSED'`) — Prisma 가 부분 인덱스를 직접 지원하지 않아 raw 마이그레이션이 필요하다 |
| 세입자당 근무지 이름 유일 | 라우트 조회 + 409 | `Workplace` 에 `@@unique([tenantProfileId, label])` |
| 근무지 도로명 주소 | `Workplace.address` 에 **표시용 한 줄**(도로명 ?? 지번)을 저장 | `Workplace.roadAddress String?` — `Building` 에는 있고 `Workplace` 에는 없다 |
| 중개인 → 호실 권한 조회 | `BrokerageTarget` → `request.unitId` 조인 | `BrokerageTarget(realtorProfileId, status)` 복합 인덱스가 있으면 조회가 짧아진다 |

데모 규모에서는 앱 판정으로 충분하다고 보고 그대로 뒀다.
