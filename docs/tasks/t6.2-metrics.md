## 어드민 인증 — **새로 발명하지 않았다**

```
[어드민 브라우저]  ──(세션 없음)──▶  어드민 서버(3001)  ──x-admin-secret──▶  web API(3000)
                                     서버 액션                              requireMetricsAdmin()
                                     (시크릿은 서버에만)                     → requireRefundAdmin()
                                                                             ↓ User.isAdmin 로 판정
```

[T2.5](./t2.5-refund-review.md) 가 만든 판정을 그대로 위임한다(T4.3 실거래가도 같은 함수를 쓴다).

| 통로 | 판정 |
|---|---|
| ① 세션 쿠키 | `isAdmin` 이면 통과, 아니면 **403 `FORBIDDEN`** |
| ② `x-admin-secret` | 세션이 없을 때만. 값이 맞으면 DB 의 `isAdmin` 계정을 찾는다. 없으면 **403** |
| ③ 둘 다 없음 | **401 `UNAUTHORIZED`** |

시크릿 값은 `ADMIN_API_SECRET`, 없으면 `CRON_SECRET`. 어드민 **서버에만** 있어 브라우저 번들에
실리지 않는다. T6.3 이 어드민 로그인을 붙이면 `requireRefundAdmin` 의 시크릿 분기만 사라지고
`features/metrics/ownership.ts` 와 이 화면은 그대로다.

## 퍼널 — 중복 제거 규칙

D2 퍼널: `notice_view → notice_cta_click → signup_start → signup_complete`.

### ① 단계 카운트는 **anonId 중복 제거**다

같은 사람이 고지서를 세 번 열어도 1단계는 **1**이다. 전환율의 분모·분자가 "사람 수" 여야
비율이 뜻을 갖는다 — 이벤트 수로 세면 **새로고침이 잦은 변형의 전환율이 낮게 나온다.**

### ② 각 단계는 **앞 단계를 지난 사람 중에서만** 센다 (누적 퍼널)

단계 집합이 부분집합으로 좁아지므로 카운트가 절대 늘지 않고 전환율이 100%를 넘을 수 없다.
고지서를 안 보고 다른 경로로 가입한 사람이 `signup_complete` 만으로 4단계에 끼는 일도 없다.
시간 순서는 보지 않는다 — anonId 하나가 곧 한 방문자의 한 여정인 규모라 순서 검증은 과하다
(필요해지면 `TrackingEvent.createdAt` 이 남아 있으니 `funnel.ts` 한 곳에 조건을 더하면 된다).

### ③ 모수는 **배정된 사람**(`AbAssignment`)이다

배정은 공개 고지서를 실제로 연 순간에만 생기므로(T1.8 화면이 `assignVariant` 를 부른다),
"실험에 노출된 사람" 과 "배정 줄이 있는 사람" 이 같다. `signup_*` 은 변형을 싣지 않으므로
**배정으로 귀속**한다.

### ④ 변형을 싣고 오는 이벤트는 **배정과 일치할 때만** 센다

`notice_view`·`notice_cta_click` 의 `props.variant` 는 **화면에 실제로 그려진 문구**다.
[T6.1 의 `?variant=` 미리보기](./t6.1-ab-test.md#variant-강제-경로--남겼다-대신-실험을-오염시키지-못하게-했다)나
주소창을 손으로 바꾼 방문자는 배정과 다른 화면을 봤으므로 어느 변형의 성과도 아니다 — 세지 않고
`totals.mismatchedEvents` 로 몇 건이 빠졌는지 화면에 드러낸다.

## 수납률 산식

```
청구액(charged)     = Σ calcTotalDue(청구)              // 월세+관리비+전월이월+연체료
미납액(outstanding) = Σ calcOutstanding(청구액, 납부합)   // 청구별 max(0, 청구−납부)
수납액(collected)   = 청구액 − 미납액
수납률(rate)        = 수납액 ÷ 청구액                    // 청구가 없으면 0
```

- **금액 계산을 새로 만들지 않았다** — `calcTotalDue`·`sumPayments`·`calcOutstanding` 은 전부
  [T1.4 원장 엔진](./t1.4-rent-engine.md) 함수다. 여기서 다시 더하면 수납 화면(T1.5)·장부(T1.6)와
  숫자가 어긋난다.
- **"납부 합계 ÷ 청구액" 이 아닌 이유**: 초과 납부가 있으면 그 달 수납률이 100%를 넘어 다른 청구의
  미납을 가려 버린다. 청구별로 미납을 구해 더하면 값이 0~100% 안에 있고 "아직 못 받은 돈"과 정확히
  반대가 된다. T1.5 가 초과 납부를 400 으로 막으므로 실제 데이터에서는 두 산식이 같지만,
  **지표는 데이터가 이상해도 거짓말을 하면 안 된다.**
- **버킷은 청구의 연·월**이다(`paidAt` 이 아니라). "청구 대비 납부" 이므로 분모(청구)의 달에
  분자(납부)를 붙인다 — 8월 청구를 9월에 늦게 받아도 **8월 수납률**을 채운다.
  장부(T1.6)가 현금주의(`paidAt`)를 쓰는 것과 기준이 다르고, 그 이유가 이것이다.

### 다른 지표의 기준

| 지표 | 분자 · 분모 | 버킷 |
|---|---|---|
| 신규 가입 | `User.createdAt` | KST 일 |
| DAU(순 방문자) | `TrackingEvent.anonId` **중복 제거** | KST 일 |
| 발송·열람률 | 열람(`openedAt`) ÷ **공개 고지서 링크(token)가 붙은 발송** | `sentAt` KST 월 |
| 결제액 | `TossPayment.status = DONE` 의 `amount` | `approvedAt`(없으면 `createdAt`) KST 월 |
| 환급 파이프라인 | `RefundApplication` 상태별 건수·`expectedAmount` 합 | 전체(기간 무관) |

열람률의 분모에서 OTP·일반 안내 발송을 뺀 이유: 그 발송에는 공개 링크가 없어 **열람을 판정할
방법이 아예 없다.** 분모에 넣으면 열람률이 구조적으로 낮게 나온다. 화면에도 "발송 N · 링크 M 중
K 열람" 을 함께 적어 분모가 무엇인지 숨기지 않는다.

**모든 시간 버킷은 KST 달력**이다. UTC 로 묶으면 매일 `15:00Z~24:00Z` 에 생긴 데이터가 하루 앞으로
밀린다 — 이 프로젝트는 시드에서 실제로 그 하루 밀림을 겪었다(T1.6). 경계는 원장 엔진의
`kstToday`·`kstYearMonth` 한 곳이 처리하고, **조회 범위와 버킷이 같은 경계를 쓴다**(범위에 걸린
행이 버킷에서 탈락해 조용히 사라지지 않게).

## 차트 — 새 의존성 0, PandaCSS 만

[T1.6 장부](./t1.6-ledger.md)의 미니 차트와 같은 방식이다. 필요한 형태가 막대·비율·퍼널 셋뿐이고
그 정도는 flex + 퍼센트 폭으로 끝난다. 차트 라이브러리는 번들·SSR 설정·테마 이중화를 데려온다.

| 컴포넌트 | 쓰임 |
|---|---|
| `TrendColumns` | 일별 가입·방문 — 세로 그룹 막대(가로 스크롤). 값은 막대 **아래에 `2 / 5` 로 글자** |
| `BarRows` | 월별 수납률·열람률·결제액·환급 파이프라인 — 가로 (누적) 막대 + 오른쪽 값·보조 문구 |
| `FunnelChart` | 변형별 퍼널 — 변형마다 한 판, **막대는 두 변형 공통 최대값으로 정규화** |
| `StatTiles` | 요약 8칸 |

- **색만으로 정보를 전달하지 않는다**(T0.6): 모든 막대에 값을 글자로 붙이고, 계열은 범례(색+글자)·
  조각 `title`·행마다 스크린리더 전용 요약으로 **셋 다** 제공한다. 막대를 지워도 표로 읽힌다.
- 색은 전부 semantic 토큰(하드코딩 색상 0).
- 퍼널 막대를 변형마다 자기 1단계 기준으로 그리면 **모수가 다른 두 변형이 같은 길이로 보여** 비교가
  거짓말이 된다. 그래서 전체 최대 단계 인원으로 정규화한다.
- 480px 셸(D5)이 아니라 데스크톱 어드민이라 세로 막대를 쓸 수 있었다. 일별 30~90개는 폭이 모자라면
  **가로 스크롤**한다(값 라벨을 겹치게 만들지 않으려고).

**클라이언트 상태가 0이라 전부 서버 컴포넌트다**(`"use client"` 없음). 구간 전환(14/30/90일)은
`?days=` 링크라 새로고침·공유가 되고 자바스크립트 없이도 화면이 완성된다.

### 어드민 화면은 집계 규칙을 하나도 들고 있지 않다

어드민은 별도 Next 앱이라 `apps/web/src/features/**` 를 import 할 수 없다. 수납률 산식이나 퍼널 단계
정의를 복사하면 규칙이 두 벌이 되어 한쪽만 고치는 사고가 난다. 대신 **web 이 단계 목록(`steps`)·
라벨·비율까지 계산해서 보내고 어드민은 그대로 그린다** — T2.5 가 `availableActions` 로 푼 방식 그대로다.
`_dashboard/shared.ts` 의 타입은 응답을 읽기 위한 **미러**일 뿐이다.

### 어드민을 화면이 아니라 web API 로 친 이유 (T2.5 와 같은 판단)

| 판단 | 이유 |
|---|---|
| 어드민 화면을 Playwright 로 몰지 않았다 | 어드민은 **별도 앱(3001)** 이고 `playwright.config.ts` 의 `webServer` 는 web 하나만 띄운다 — 그 설정 파일은 이 task 소유가 아니라 손대지 않았다. 게다가 대시보드는 집계 규칙을 하나도 들고 있지 않아 **위험이 전부 web API 쪽에 있다.** 화면 렌더링은 `pnpm build` 와 타입체크가 지킨다 |
| 요청은 **어드민 세션 쿠키**로 보냈다(시크릿 헤더가 아니라) | 시드 관리자(`isAdmin`)에 세션 한 줄을 만들어 쓰므로 검증되는 것이 **본선 경로(`User.isAdmin` 판정)** 다. 시크릿 경로는 단위 테스트가 따로 지킨다. 끝나면 그 세션을 지운다 |
