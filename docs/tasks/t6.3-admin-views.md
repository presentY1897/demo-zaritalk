# T6.3 어드민 조회 화면 일괄 + 어드민 인증

> Phase 6 · 상태: ✅ · [Phase 구성](../PHASES.md)

| 라우트(admin) | 화면·기능 |
|---|---|
| `/users` | 검색(이름·전화), 상세: 프로필·계약·**신청 이력 타임라인** |
| `/leases` `/charges` | 상태 필터, **연체 계약 드릴다운** |
| `/messages` | 발송 이력 전체 — 종류·수신자 필터, 열람 여부, **본문 미리보기(알림톡 스타일)** |

어드민 API 는 `/api/admin/*` 네임스페이스, 전부 `isAdmin` 가드다.

**그리고 이 task 의 절반은 화면이 아니라 문이다** — 어드민 앱에는 로그인이 없었다. 아래가 그 이야기다.

---

## 1. 어드민 인증 — 무엇이 열려 있었고, 무엇을 닫았나

### 1-1. 지금까지의 상태

T2.5(환급 심사)·T4.2(신고 처리)·T1.4(크론 트리거)는 **web API 는 단단히** 잠갔다. 판정은 언제나
`User.isAdmin` 이고, 세션이 있으면 세션으로(비어드민 403), 없으면 서비스 시크릿(`x-admin-secret`)을
확인한 뒤 **DB 에서 실재하는 `isAdmin` 계정을 찾아** 행위자로 기록했다. 시크릿은 신분을 만들어
내지 못한다.

열려 있던 것은 **어드민 앱 자체**다.

```
[아무나]  ──▶  어드민 서버(3001)  ──x-admin-secret──▶  web(3000)
               ✅ 그냥 열린다        (시크릿은 서버에만)      ✅ isAdmin 으로 판정
```

주소만 알면 환급 심사 큐를 보고, 서류 뷰어 프록시로 남의 등본을 열고, 크론·실거래가 수집 버튼을
누를 수 있었다. 세 task 문서가 모두 「이 구멍은 T6.3 이 닫는다」고 적어 두고 넘어간 자리다.

### 1-2. T2.5 의 메모("시크릿 분기만 지우면 된다")는 **절반만 맞다**

[T2.5](./t2.5-refund-review.md#어드민-인증--어드민-앱에는-로그인이-없다t63-범위)는
"`resolveServiceAdmin` 분기를 지우고 어드민 앱이 세션 쿠키를 전달하게 바꾸면 된다" 고 적었다.
방향(세션 쿠키 전달)은 맞지만 **그것만으로는 구멍이 닫히지 않는다.**

| T2.5 의 제안 | 실제 |
|---|---|
| 시크릿 분기를 지운다 | **구멍은 시크릿이 아니다.** 시크릿이 없어도 web 은 401/403 이고, 있어도 실재하는 `isAdmin` 계정을 찾아야 통과한다. 지운다고 어드민 앱이 잠기지 않는다 |
| 어드민이 세션 쿠키를 전달한다 | 맞다. **다만 그 세션을 어디서 얻는지**가 빠져 있었다 — 어드민 앱에는 로그인 화면도, 세션을 발급받을 경로도 없었다. 그것을 만드는 것이 이 task 의 일이다 |
| 그러면 끝난다 | 아니다. 시크릿 경로는 **아직 필요하다.** Vercel Cron 이 `CRON_SECRET` 으로 `/api/cron/daily` 를 부르고, 어드민 `/cron`·`/deals` 화면이 같은 값을 쓴다. 사람이 없는 호출에는 세션이 없다 |

그래서 **문을 새로 달되, 문 뒤의 신분은 지금까지와 똑같이 `User.isAdmin`** 으로 두고,
시크릿은 "이 요청이 어드민 서버에서 왔다" 만 증명하는 **서비스 자격**으로 남겼다.
`requireRefundAdmin` 은 **한 글자도 고치지 않았다.**

### 1-3. 채택한 설계 — 세션은 web 의 것을 그대로 쓴다

```
[브라우저]
   │ ① 관리자 전화번호 + 어드민 패스코드
   ▼
어드민 서버(3001)  ──x-admin-secret + {phone, passcode}──▶  web  POST /api/admin/session
   │                                                          │ 패스코드 확인
   │                                                          │ User.isAdmin 확인
   │  ◀────────────── { token, expiresAt, admin } ────────────┘ Session 레코드 발급
   │ ② 토큰을 **어드민 도메인의 httpOnly 쿠키**(zari_admin)에 담는다
   ▼
[브라우저]  ──쿠키──▶  어드민 서버  ──Cookie: zari_session=<토큰>──▶  web  GET /api/admin/*
                                                                      getCurrentUser() → isAdmin
```

- **발급되는 것은 web 의 `Session` 레코드 그대로**다(같은 테이블·같은 30일 TTL·같은
  `getCurrentUser`). 인증 체계를 하나 더 만들지 않았다. 도메인이 달라 쿠키를 공유할 수 없을 뿐이다.
- 토큰은 어드민 도메인의 **httpOnly** 쿠키라 브라우저 JS 가 읽지 못한다. 패스코드는
  브라우저 → 어드민 서버 → web 으로만 흐르고 어디에도 저장되지 않는다.
- **어드민 앱은 여전히 DB 를 모른다.** 판정은 전부 web 이 한다 — T2.5·T4.2 가 세운 원칙 그대로다.

#### 로그인 입력이 왜 「전화번호 + 패스코드」인가

| 입력 | 무엇을 증명하나 |
|---|---|
| **관리자 전화번호** | *누구인지* — web 이 `User.isAdmin` 인 계정을 찾는다. 세션은 그 사람의 것이 된다(시드: `01000000000`) |
| **어드민 패스코드** | *들어와도 되는지* — 공개 API 로는 얻을 수 없는 서버 환경변수 |

**왜 OTP 가 아닌가.** 데모의 `POST /api/auth/otp/request` 는 **코드를 응답 본문에 그대로 실어
준다**(T0.3, 의도된 데모 장치다). 즉 누구든 관리자 번호로 코드를 받아 낼 수 있어, OTP 로 어드민
문을 잠그면 **잠근 척만 하게 된다.** 패스코드는 공개 경로로 얻을 수 없는 유일한 값이라,
"URL 만 알면 열린다" 를 실제로 막는다. 데모에 필요한 최소한이면서 실제로 닫히는 선택이다.

**패스코드가 설정돼 있지 않으면 로그인은 전부 거부된다(fail closed).** 환경변수를 빠뜨린 배포가
"인증 없음" 으로 열리는 것이 이 task 가 없애려는 바로 그 상태이기 때문이다.
값은 `ADMIN_PASSWORD` → `ADMIN_API_SECRET` → `CRON_SECRET` 순으로 떨어진다 —
로컬·데모에 이미 있는 값이라 **새 환경변수를 요구하지 않는다**([`.env.example`](../../.env.example)).

**실패 사유는 밖으로 구분해 주지 않는다.** "그 번호는 관리자가 아니다" 와 "패스코드가 틀렸다" 를
나눠 주면 어드민 계정 번호를 밖에서 찾아낼 수 있다. 응답은 전부 같은 403 문구다.
패스코드 비교는 `timingSafeEqual` 이다.

### 1-4. 게이트는 **세 겹**이다

| 겹 | 어디 | 무엇을 막나 |
|---|---|---|
| ① 화면 | `layout.tsx` → `_shell/AdminGate` | 로그인 안 한 브라우저에게 **어떤 업무 화면도 그리지 않는다**(로그인 폼만). 셸·사이드바도 그리지 않는다 |
| ② 데이터 | **모든 서버 액션 + 라우트 핸들러**의 첫 줄 `requireAdminGate()` | 화면을 건너뛴 직접 호출(서버 액션은 POST 로 그냥 불린다) |
| ③ 원천 | web `/api/admin/*` 의 `requireAdmin`(= `requireRefundAdmin`) | 어드민 앱을 우회한 직접 호출. **`User.isAdmin` 이 유일한 기준** |

②가 진짜 방어선이다. Next 문서가 못 박아 둔 그대로다 —
`node_modules/next/dist/docs/01-app/02-guides/authentication.md` 의 "Server Actions" 절:
*"레이아웃에서 null 을 반환하는 패턴은 권장되지 않는다 … 이 컴포넌트에서 호출되는 서버 액션도
각자 권한 검사를 해야 한다."*

**실제로 확인했다**: 로그인하지 않고 `/users` 를 열면 화면에는 로그인 폼만 보이지만,
**페이지 컴포넌트 자체는 서버에서 실행된다**(RSC 페이로드에 그 결과가 들어 있다).
데이터가 새지 않는 이유는 그 페이지가 부르는 서버 액션이 ②에서 막혀 "어드민 로그인이 필요합니다"
라는 오류 상태만 만들기 때문이다. 즉 **①만 있었다면 새어 나갔다.**

로그인 화면을 `/login` 라우트로 만들지 않고 **같은 자리에 대신 그린 이유**도 여기 있다 —
리다이렉트 루프도, "게이트에서 제외할 경로" 목록도 필요 없다. **예외가 없는 게이트가 가장 새지 않는다.**
`proxy.ts`(Next 16 미들웨어 규약)는 두지 않았다. 문서가 권하는 용도가 "낙관적 사전 판정" 인데,
그러면 같은 규칙이 한 곳 더 생기고(동기화 실패 지점) 어드민 앱의 라우트 핸들러는 하나뿐이라
얻는 것이 없다.

### 1-5. 기존 화면(`/refunds`·`/reports`·`/cron`·`/deals`)에 인증을 어떻게 얹었나

**화면 로직은 한 줄도 바꾸지 않았다.** 얹은 것은 두 가지뿐이다.

| 파일 | 바뀐 것 |
|---|---|
| `refunds/actions.ts` · `reports/actions.ts` | 두 서버 액션의 첫 줄에 `requireAdminGate()` (import 1줄 + 3줄 × 2) |
| `cron/actions.ts` · `deals/actions.ts` | `triggerDailyCron`·`triggerDealSync` 첫 줄에 같은 것(실패 모양에 `url` 이 필요해 `{ ...denied, url }`) |
| `refunds/documents/route.ts` | **라우트 핸들러는 레이아웃을 거치지 않는다** — 첫 줄에서 직접 확인, 실패면 401 |
| `layout.tsx` | `AdminShell` → `AdminGate`(그 안에서 `AdminShell`). 그래서 `/`(T6.1 지표)를 포함한 **모든 화면**이 자동으로 잠긴다 |
| `_shell/AdminShell.tsx` | 사이드바 하단에 로그인한 관리자 + 로그아웃(선택적 `admin` prop, 없으면 아무것도 안 그린다) |

**web 호출 방식(서비스 시크릿)은 그대로 두었다.** 시크릿은 신분이 아니라 통로의 자격이고,
web 은 여전히 실재하는 `isAdmin` 계정을 찾아 심사자·처리자로 기록한다. 이 네 화면은 이미
그렇게 검증돼 있고(단위 테스트가 시크릿 경로를 지킨다) 건드릴 이유가 없었다.

> **새로 만든 조회 화면은 반대로 세션 쿠키만 보낸다.** `callWebAsAdmin` 은 `x-admin-secret` 을
> **아예 붙이지 않는다** — 둘 다 보내면 세션이 끊긴 요청이 서비스 자격으로 슬쩍 통과한다.
> 조회는 언제나 "로그인한 그 관리자" 로 동작해야 한다.
> (기존 네 화면도 같은 방식으로 바꾸는 것은 한 줄씩이면 되지만, 그 파일들의 동작을 바꾸지
> 않는 것이 이 task 의 소유 규칙이라 남겨 두었다 → [뒤 task 가 알아야 할 것](#10-뒤-task-가-알아야-할-것))

### 1-6. 실제로 막히는지 — 확인 결과

두 앱을 띄우고(web 3170 / admin 3171, 시드된 테스트 DB) 직접 확인했고, 같은 내용을
`e2e/admin.spec.ts` E2E① 이 브라우저로 다시 확인한다.

| 확인한 것 | 결과 |
|---|---|
| 비로그인으로 `/users`·`/leases`·`/charges`·`/messages`·`/events`·`/`·`/refunds`·`/reports`·`/cron`·`/deals` | **전부 로그인 폼만** — 업무 화면·사이드바 0 |
| 비로그인으로 `/refunds/documents?...`(서류 프록시) | **401** |
| 쿠키에 아무 문자열이나 넣고 접근 | web 이 401 → 게이트가 막는다(단위 테스트) |
| 시크릿 없이 `POST /api/admin/session` | **401** |
| 시크릿은 맞고 패스코드가 틀림 | **403**, 세션 레코드 0 |
| 패스코드는 맞고 **관리자가 아닌 번호**(시드 임대인) | **403**, 세션 레코드 0 |
| 없는 번호 vs 틀린 패스코드 | **응답 본문이 완전히 같다** |
| 패스코드·시크릿이 하나도 설정 안 됨 | **403**(fail closed) |
| 관리자 번호 + 패스코드 | 200, `Session` 한 줄 생성, 마스킹된 관리자 정보 |
| 로그인 뒤 조회 5화면 | 전부 200 + 데이터 · 사이드바에 "관리자" |
| 로그인 뒤 기존 4화면 | 전부 200, 오류 0 — **환급 큐·신고 큐·크론·수집 화면 그대로 동작** |
| 로그아웃 | 다시 로그인 폼, web 의 `Session` 레코드도 삭제 |
| 화면에 나온 전화번호 | 전부 `010-****-XXXX` — 원문 0건 |

### 1-7. 한계 (데모라 하지 않은 것)

- **패스코드는 공유 비밀이다.** 관리자가 여럿이면 사람마다 자격이 나뉘어야 한다(실서비스라면
  관리자별 비밀번호 해시 + 2FA). 지금 신분은 "입력한 전화번호의 `isAdmin` 계정" 이라 **누가
  로그인했는지는 남지만**, 그 사람만 아는 비밀은 아니다.
- **로그인 시도 횟수 제한이 없다.** 데모 규모라 두지 않았다.
- **세션 TTL 은 web 과 같은 30일**이다. 백오피스라면 더 짧아야 한다(어드민 전용 TTL 은
  `issueSessionToken` 에 인자 하나를 더하면 된다).
- 어드민 앱은 여전히 **비공개 배포가 바람직**하다. 이 게이트는 "URL 을 아는 사람이 그냥 열 수
  있는 상태" 를 닫은 것이고, 네트워크 경계를 대신하지는 않는다.

## 3. 페이지네이션 규약 — **오프셋**을 골랐다

정의는 `apps/web/src/features/admin/pagination.ts` 한 곳이고, 다섯 화면이 같은 규약을 쓴다.

| 필요한 것 | 커서(T4.1·T4.4) | 오프셋(T6.3) |
|---|---|---|
| **전체 건수**("연체 계약 37건") | 못 준다 | 준다 |
| **"3 / 12 페이지"·마지막으로 점프** | 못 한다 | 한다 |
| URL 공유·북마크 | 불투명 커서가 박힌다 | `?page=3` — 사람이 읽는다 |
| 스크롤 중 삽입에 강함 | 강하다 | 약하다 |

커뮤니티·실거래가는 **무한 스크롤**이라 커서가 맞았다. 어드민 조회는 **번호 페이지**이고
운영자가 "몇 건인지" 를 먼저 본다. 조회 대상이 대부분 과거 데이터라 마지막 줄이 흔들리는 문제도
실제로 드물다.

대신 오프셋의 진짜 위험(정렬이 흔들려 페이지 경계에서 중복·누락)을 **정렬을 유니크 키로 닫아**
없앤다 — **모든 목록의 마지막 정렬 키는 언제나 `id`** 다(커서 규약이 `id` 로 닫는 것과 같은 이유).

| 화면 | 정렬 |
|---|---|
| `/users` | `createdAt DESC, id DESC` |
| `/leases` | `createdAt DESC, id DESC` |
| `/charges` | `dueDate DESC, id DESC` |
| `/messages` | `sentAt DESC, id DESC` |
| `/events` | `createdAt DESC, id DESC` |

- 요청: `?page=`(1부터, 기본 1) · `?pageSize=`(기본 20, 최대 100)
- 응답: 목록 + `page` 메타 `{ page, pageSize, total, totalPages, hasPrev, hasNext }`
- `total` 은 **필터 적용 후 전체 건수**다(페이지 크기와 무관).
- **범위를 넘는 페이지는 404 가 아니다** — 빈 목록 + 정확한 `total`. 필터를 좁히는 도중
  `page=5` 가 남아 있는 상황이 흔한데 에러를 띄우면 화면이 막힌다. 화면은 "결과 없음" 과 함께
  1페이지로 돌아가는 링크를 준다.
- `page=0`·`page=abc`·`pageSize=0`·`pageSize=101` 은 **400**. 이건 "무엇을 보여 줄지" 가 아니라
  **"어디를 보여 줄지"** 라, 조용히 넘기면 엉뚱한 화면이 나온다.
- 반대로 **필터 값**(상태·종류 등)은 모르는 값이면 **조용히 버린다**(T2.5·T4.2 와 같은 규칙) —
  화면을 막을 이유가 없다.
- **상태 탭의 건수는 그 탭의 필터를 뺀 조건으로 센다** — 탭을 눌러도 옆 탭 숫자가 흔들리지 않게.

## 4. 개인정보 마스킹 — **가린다. 그리고 서버에서 가린다**

규칙은 `apps/web/src/features/admin/mask.ts` 한 곳이다.

조회 화면은 운영자가 **"누구인지 식별"** 하려고 보는 화면이지 **"연락"** 하는 화면이 아니다.
목록 한 장에 수십 명의 번호가 원문으로 뜨는 상태는 어깨너머·화면공유·스크린샷으로 그대로
새어 나간다. 가운데 4자리를 가리면 뒷자리가 남아 식별에는 충분하고 번호는 재사용할 수 없다.

가림은 **응답을 만들 때** 한다(T4.2 블라인드와 같은 원칙) — 원문이 브라우저 번들·개발자도구·
네트워크 탭에 **아예 내려가지 않는다.** 화면이 실수로 원문을 그리는 것이 구조적으로 불가능하다.

| 대상 | 처리 | 근거 |
|---|---|---|
| 전화번호(회원·계약 세입자·발송 수신자) | `010-****-1111` | 위 |
| 이름 | **가리지 않는다** | 운영자가 사람을 특정하는 1차 키다. 가리면 화면이 쓸모없다 |
| 주소·건물명·호실 | 가리지 않는다 | 개인이 아니라 자산 식별자다 |
| 발송 **본문** | 가리지 않는다 | 무엇을 보냈는지 확인하는 것이 그 화면의 목적이다 |
| 발송 본문 중 **OTP 인증번호** | **가린다**(`••••••`) | 데모의 OTP 는 코드가 로그에 그대로 남는다(T0.3). 그건 *본인이 자기 코드를* 보는 이야기고, **어드민 로그에서 남의 코드가 읽히는 것은 계정 탈취 경로**다 |
| 트래킹 `anonId`·`sessionId` | 앞 8자리 | 가명 식별자라 "같은 브라우저인가" 비교만 되면 충분하다 |

- **검색은 원문 기준으로 동작한다.** 마스킹은 표시 규칙이지 저장 규칙이 아니다 —
  `01011111111` 로 검색하면 찾히고, 화면에는 가려진 채로 나온다.
- 기존 어드민 화면(환급 심사 T2.5·신고 처리 T4.2)은 신청자 전화번호를 원문으로 그린다.
  그 응답은 이 task 소유가 아니라 손대지 않았다 — **같은 함수를 그 DTO 에 끼우면 끝난다.**

## 5. API 요청·응답

에러는 전부 `{ "error": { "code", "message", "details?" } }` 한 형태다([D1](../DECISIONS.md#-d1-api-스타일)).
**모든 목록 응답의 전화번호는 마스킹된 값**이다.

공통 실패:

| 실패 | status · code |
|---|---|
| 세션도 시크릿도 없음 | 401 `UNAUTHORIZED` |
| **비어드민 세션** | 403 `FORBIDDEN` |
| 시크릿 불일치 · `isAdmin` 계정 없음 | 403 `FORBIDDEN` |
| `page`·`pageSize` 범위 밖·정수 아님 | 400 `VALIDATION_ERROR` |

### `POST /api/admin/session` — 어드민 로그인

```jsonc
// 요청 — 헤더 x-admin-secret 필수(어드민 서버만 부른다)
{ "phone": "010-0000-0000", "passcode": "…" }

// 200
{ "token": "007d1689…(64자 hex)",
  "expiresAt": "2026-10-03T05:31:23.598Z",
  "admin": { "id": "cmtl35…", "name": "관리자", "phone": "010-****-0000" } }
```

| 실패 | status · code |
|---|---|
| `x-admin-secret` 없음 | 401 `UNAUTHORIZED` |
| 시크릿 불일치 · **패스코드 불일치** · 패스코드 미설정 · `isAdmin` 아닌 번호 · 없는 번호 | 403 `FORBIDDEN` — **문구가 전부 같다** |
| `phone`·`passcode` 누락 | 400 `VALIDATION_ERROR` |

`GET` 은 세션 확인(`{ admin }` · 401 · 403), `DELETE` 는 그 토큰만 폐기하고 **204**(멱등).

## 6. 화면

전부 **서버 컴포넌트 + URL 쿼리**다. 필터는 `<a>` 링크, 검색은 `<form method="get">` 이라
**클라이언트 JS 가 한 줄도 없고** 상태가 전부 URL 에 있다 — 새로고침·뒤로가기·링크 공유가 그냥 된다.
운영 화면은 "이 조건으로 보세요" 를 주고받는 일이 잦은데, 클라이언트 상태로 들고 있으면 그게 안 된다.
(로그인 폼만 `useActionState` 를 쓰는 클라이언트 컴포넌트다.)

| 화면 | 필터 | 특별한 것 |
|---|---|---|

### 시간대별 카운트 차트 — 새 의존성 0

`events/HourlyChart.tsx` 는 PandaCSS 만으로 그린 24칸 세로 막대다
(T1.6 임대장부·T4.4 실거래가 추이와 같은 방식 — `pnpm-lock.yaml` 을 건드리지 않는다).

- **세로**를 고른 이유: 어드민은 데스크톱 폭이라 24칸을 세울 자리가 있고, 시간축은 왼쪽→오른쪽으로
  읽는 것이 자연스럽다(web 쪽 차트가 480px 셸 때문에 가로를 고른 것과 반대다).
- **색만으로 정보를 전달하지 않는다**(T0.6): 막대마다 **건수를 숫자로** 적고, 아래에 시(hour)
  라벨이 붙고, 막대마다 `title` 과 스크린리더 요약(`N시 M건`)이 있다. 막대 색은 한 가지뿐이라
  색이 뜻을 지지 않는다. 0건인 시간대도 자리를 남긴다(회색 실선 + `0`).
- 집계는 **SQL 이 아니라 JS** 로 한다 — 시각 → KST 시(hour) 규칙이 이미 `@/lib/rent` 의
  `KST_OFFSET_MS` 에 있고, SQL 에 `interval '9 hours'` 를 또 적으면 타임존 규칙이 두 벌이 된다.
  대신 훑는 행 수에 상한(50,000)을 두고, 걸리면 응답·화면에 그렇게 밝힌다.

## 8. 스키마가 필요했지만 만들지 않은 것

`packages/db/prisma/**` 는 이 task 소유가 아니라 열지 않았다.

| 필요했던 것 | 지금 어떻게 대신했나 |
|---|---|
| **감사 로그 테이블**(`ActivityLog`: 주체·대상·동작·시각) | 타임라인을 각 도메인의 시각 컬럼에서 **합성**한다(가입·프로필·계약·환급·민원·신고·발송). 정확하지만 쿼리가 7개로 흩어지고, "무엇이 바뀌었는지" 가 아니라 "무엇이 생겼는지" 만 남는다. T2.4·T4.2 가 미룬 것과 같은 테이블이다 |
| **어드민 전용 세션 구분**(`Session.kind` 또는 `Session.scope`) | web 세션과 **같은 테이블·같은 TTL** 을 쓴다. 그래서 어드민 세션만 골라 폐기하거나 TTL 을 짧게 줄 수 없다. 실서비스라면 백오피스 세션은 더 짧아야 한다 |
| **로그인 시도 기록**(`AdminLoginAttempt`) | 없다 → 시도 횟수 제한을 걸 자리가 없다 |
| **`MessageLog` 의 발송 주체** | 발송 이력에 "누가 보냈는지" 가 없다(계약을 통해 임대인은 유추된다). 크론이 보낸 것과 사람이 보낸 것도 구분되지 않는다 |
| **`TrackingEvent.name` 의 인덱스 조합** | 이름 목록(`groupBy name`)과 기간 필터는 `@@index([name, createdAt])` 를 쓰지만, "기간만" 거는 조회는 인덱스를 온전히 못 쓴다. 데모 규모에서는 문제되지 않는다 |
