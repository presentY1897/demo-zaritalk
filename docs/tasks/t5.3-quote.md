# T5.3 견적 제안·수락

> Phase 5 · 상태: ✅ · [Phase 구성](../PHASES.md)

| 라우트/API | 동작 |
|---|---|
| `/landlord/workorders/[id]` | 견적 비교 — 견적 카드(업체·금액·메시지), 하나 수락 → 나머지 자동 거절 → ASSIGNED. 완료 처리 시 연결 민원 RESOLVED |
| `/master/quotes` | 내 견적 목록·상태(제안/수락/거절) — 추천(push)으로 받은 건인지 피드(pull)에서 찾은 건인지 함께 표시 |
| `POST /api/work-orders/[id]/quotes` | 견적 제안(의뢰당 업체 1회) |
| `POST /api/quotes/[id]/accept` | 수락 — 트랜잭션: 수락 1 + 나머지 REJECTED + 의뢰 ASSIGNED |

**Phase 5 의 마지막 조각이다.** 이 task 가 닫히면 세입자 민원 → 임대인 전환 → 마스터 견적 →
임대인 수락·완료 → 세입자 「해결」까지 **3역할이 한 줄로** 이어진다(`e2e/quote.spec.ts`).

## 수락 원자성 — **의뢰 행이 관문이다**

`features/workorder/quotes.ts` 의 `runQuoteAcceptance` 한 곳에만 규칙이 있다.

| # | 쓰기 | 조건 | 실패하면 |
|---|---|---|---|
| ① | `WorkOrder` `REQUESTED → ASSIGNED` | `where: { id, status: "REQUESTED" }` | 전부 롤백 · **409** |
| ② | 이 견적 `PROPOSED → ACCEPTED` | `where: { id, workOrderId, status: "PROPOSED" }` | 전부 롤백 · **409** |
| ③ | 같은 의뢰의 **나머지 전부** `PROPOSED → REJECTED` | `where: { workOrderId, id: { not }, status: "PROPOSED" }` | 전부 롤백 · **500** |

세 쓰기는 `prisma.$transaction(async (tx) => …)` 한 경계 안이다. 규칙이 막으면
`QuoteAcceptConflictError` 를 **던져서** 롤백시키고, 라우트가 그 신호만 409 로 옮긴다.

**순서가 곧 동시성 규칙이다.** ① 을 먼저 두는 이유:

> 서로 **다른** 견적 2건을 동시에 수락하면 견적 행끼리는 다투지 않아 ② 만으로는 **둘 다 통과**한다.
> ① 은 두 트랜잭션이 **같은 `WorkOrder` 행**을 두고 다투게 만든다 — PostgreSQL 이 행 잠금을 걸고,
> 뒤에 온 쪽은 잠금이 풀린 뒤 조건(`status = 'REQUESTED'`)을 다시 평가해 `count = 0` 을 받는다.
> 그래서 **정확히 하나만** 성공한다(`app/api/quotes/[id]/accept/route.test.ts` 의 동시 요청 테스트).

같은 견적을 두 번 수락하는 것도 ① 이 막는다(의뢰가 이미 `ASSIGNED` 다) — 견적 상태를 보기 전에 걸린다.

`runQuoteAcceptance` 가 **트랜잭션 클라이언트를 인자로 받는** 이유는 테스트다.
`features/workorder/quotes.test.ts` 가 같은 함수를 자기 트랜잭션 안에서 굴려
③ 에서 터뜨리고 **①②도 되돌아가는지**를 직접 확인한다(프로덕션 코드에 테스트용 훅을 두지 않았다).

## 의뢰 상태 전이 — **`QUOTED` 를 쓰지 않는다**

| 시점 | 의뢰 상태 | 누가 옮기나 |
|---|---|---|
| 등록·전환 | `REQUESTED` | T5.1 |
| 견적 도착(1건이든 5건이든) | **`REQUESTED` 그대로** | — |
| 견적 수락 | `ASSIGNED` | `POST /api/quotes/[id]/accept` (①) |
| 완료·취소 | `DONE`·`CANCELLED` | 임대인 (`PATCH /api/work-orders/[id]`) |

**T5.1 문서는 "`QUOTED` 는 견적이 도착하며 옮기는 값" 이라고 적어 뒀지만, 실제로 구현해 보니
완료 기준과 충돌해서 쓰지 않기로 했다.**

- T5.2 의 마스터 피드(pull)는 **`REQUESTED` 만** 본다(`listMasterFeed`).
- 첫 견적에 `QUOTED` 로 올리면 그 의뢰가 **피드에서 사라진다** → 두 번째 마스터가 찾을 길이 없다
  → 이 task 의 완료 기준 **"견적 2개 이상 비교"** 가 성립하지 않는다.
- 피드 조건을 `REQUESTED + QUOTED` 로 넓히는 선택지도 있었지만, 그건 T5.2 가 확정한
  "피드 = 아직 아무도 안 잡은 의뢰" 라는 뜻과 그 최소 테스트(「REQUESTED 만」)를 바꾸는 일이다.
  **경쟁이 닫히는 시점은 배정(`ASSIGNED`)** 이고 그 전까지는 열린 의뢰인 편이 도메인에도 맞다.
- 대신 "견적이 왔다" 는 사실은 상태가 아니라 **개수로** 드러낸다 — 목록·상세의 「받은 견적 N」 배지
  (`quoteCount`)와 견적 카드가 그 자리를 대신한다.

`WORK_ORDER_STATUS_META.QUOTED`(「견적도착」)와 전이표의 `QUOTED` 행은 **남겨 뒀다** —
나중에 「견적 마감」 같은 개념이 생기면 그 자리다.

### T5.1 의 `PATCH /api/work-orders/[id]` 는 **요청 규약을 고치지 않았다**

그 라우트가 `QUOTED`·`ASSIGNED` 를 400 으로 막는 것은 **"임대인이 고를 수 있는 값이 아니다"** 라는
뜻이고, T5.3 도 그 규칙을 그대로 따른다 — `ASSIGNED` 는 수락 API 가 옮긴다. 전이표에
`ASSIGNED → DONE|CANCELLED` 가 이미 열려 있어 배정된 의뢰의 완료·취소도 그대로 된다.
**요청 스키마(`updateWorkOrderSchema`)·전이표(`canTransitionWorkOrder`)는 한 글자도 안 바꿨다.**
그 라우트에서 T5.3 이 더한 것은 아래 민원 연동뿐이다.

## 민원 연동 — 완료하면 민원도 닫는다

`PATCH /api/work-orders/[id]` 가 `DONE` 을 처리할 때, `WorkOrder.complaintId` 가 있으면
그 민원도 `RESOLVED` 로 옮긴다. 규칙 셋:

1. **전이 판정은 T2.6 의 `canTransition` 을 그대로 부른다** — 민원 전이표를 여기서 다시 쓰지 않는다.
2. **막힌 전이면 민원은 그대로 두고, 의뢰 완료는 성공시킨다.**

   | 민원 현재 | `→ RESOLVED` | 이 task 의 처리 |
   |---|---|---|
   | `OPEN` 접수 | ✅ | 함께 닫는다 |
   | `IN_PROGRESS` 진행중 | ✅ | 함께 닫는다(전환분의 기본 경로) |
   | `RESOLVED` 해결 | ❌(같은 상태) | 그대로 — 이미 원하는 상태다 |
   | `REJECTED` 반려 | ❌(종결끼리 못 넘어감) | **그대로** — 임대인이 반려로 닫은 판단을 작업 완료가 조용히 뒤집으면 안 된다 |

   어느 쪽도 "의뢰를 완료하지 못할" 이유는 아니라서 **409 로 막지 않는다.** 대신 응답의
   `complaintStatus` 에 **실제로 저장된 값**을 실어 화면이 사실만 말하게 한다.
3. **의뢰와 민원은 같은 트랜잭션**이다 — 갈라지면 "작업은 끝났는데 민원은 진행중" 이라는 거짓말이
   세입자 화면에 남는다.
4. **취소(`CANCELLED`)는 민원을 닫지 않는다** — 작업을 안 한 것이지 해결한 것이 아니다.

`features/complaint/**` 에서 고친 파일은 **없다**(`canTransition` 을 import 해서 쓰기만 했다).

## `WorkOrderTargetStatus` — **`SENT` 말고는 쓰지 않는다**

T5.1·T5.2 가 남긴 `VIEWED`·`ACCEPTED`·`DECLINED` 는 **이 task 에서도 채우지 않기로 했다.**

1. **견적 생애주기의 단일 출처는 `WorkOrderQuote.status` 다.** `WorkOrderTarget` 에 같은 뜻의
   상태를 또 두면 값이 둘이 되고, **pull 로 들어온 견적은 `WorkOrderTarget` 행 자체가 없어서**
   (추천을 안 받았으니까) 타겟 상태로는 견적 결과를 일관되게 표현할 수 없다 — 반은 기록되고
   반은 안 되는 지표가 된다.
2. **`WorkOrderTarget` 은 "그때 이 조건이라 보냈다" 는 발송 기록이다.** 사후에 덮어쓰면
   추천 성과(발송 대비 견적률·수락률)를 계산할 원본이 흐려진다. `distanceKm` 을 발송 시점 값으로
   굳혀 둔 T5.2 의 판단과 같은 결이다.
3. `VIEWED` 는 트래킹 이벤트 `master_order_view`(T5.2)가 **시각·횟수까지** 더 정확하게 남긴다.

enum 자체는 `BrokerageTarget` 과 형태를 맞추려고 둔 것이라 그대로 둔다 — T3.6 이 중개 쪽에서
쓸 수 있고, 스키마는 이 task 의 소유가 아니다.

## push / pull 구분 — 컬럼을 만들지 않았다

「이 견적이 **추천(push)으로 받은 의뢰**에 낸 것인가」는 `WorkOrderTarget` 행의 유무로 판정한다
(`quotes.ts` 의 `loadQuoteSources`). **T5.2 의 `recommended` 와 같은 판정**이라 마스터 홈의
「추천」 배지와 견적 목록의 「추천」 배지가 어긋날 수 없다.

| 값 | 라벨 | 뜻 |
|---|---|---|
| `PUSH` | 「추천」 | 이 의뢰가 나에게 추천으로 와 있다(유료 PRO 의 값어치가 보이는 자리) |
| `PULL` | 「피드」 | 전체 피드에서 찾아가 낸 견적 |

- **임대인 견적 카드에도 붙는다** — 어떤 경로로 닿은 업체인지가 비교에 쓰이는 정보다.
- 견적을 낸 뒤 플랜을 PRO 로 켜 백필되면 같은 견적이 `PULL → PUSH` 로 보일 수 있다. 라벨의 뜻이
  "**지금** 이 의뢰가 나에게 추천으로 와 있는가" 라서 거짓말은 아니고, 데모 범위에서 그대로 둔다.

## 견적 제안 자격 — T5.2 의 판정을 그대로 부른다

「이 마스터가 이 의뢰를 볼 수 있는가」는 T5.2 의 **`getMasterWorkOrder` 한 곳**에서만 판정한다
(추천으로 받았거나 · 내 업종 + 활동반경 안). 견적 자격을 새로 계산하면 **피드에는 보이는데
견적은 못 내는** 어긋남이 생긴다. 그 위에 상태 조건 한 겹(`acceptsNewQuote` = `REQUESTED` 만)만 얹는다.

- 추천받은 의뢰는 **사무소를 옮겨 반경 밖이 돼도 견적을 낼 수 있다**(T5.2 상세 접근 규칙 그대로).
- 없는 의뢰(404)와 볼 수 없는 의뢰(403)를 가르려고 존재 확인만 한 번 더 한다.

## 요청·응답

에러는 D1 규약대로 `{ "error": { "code", "message", "details?" } }` 한 형태다.

### `POST /api/work-orders/[id]/quotes` (마스터 전용)

```jsonc
// 요청 — 대상 의뢰는 경로가, 제안자는 세션이 정한다. 마스터가 적을 것은 금액·메시지뿐
{ "amount": 180000, "message": "순환펌프 교체 기준입니다. 방문 점검 후 확정하겠습니다." }
// message 는 생략·null 가능. 공백만 보내면 null 로 저장된다

// 201
{
  "quote": {
    "id": "cmf0…",
    "amount": 180000,

    "source": "PUSH",                     // PUSH(추천) | PULL(피드)
    "workOrder": {
      "id": "cmf0…", "category": "REPAIR",
      "description": "난방을 켜면 10분 만에 보일러가 꺼집니다.",
      "desiredDate": "2026-09-10", "status": "REQUESTED",
      "createdAt": "…", "updatedAt": "…",
      "place": { "buildingId": "…", "buildingName": "행당해피빌",
                 "buildingAddress": "서울 성동구 행당로 79",
                 "unitId": "…", "unitLabel": "201호" },
      "landlordName": "김임대",
      "distanceKm": 2.554                 // 내 사무소 → 의뢰 건물. 건물이 없는 의뢰면 null
    }
  }

```

| 실패 | status · code |
|---|---|
| 비로그인 | 401 `UNAUTHORIZED` |
| 마스터 프로필·업종/활동지역 없음(**임대인 계정 포함**) | 403 `FORBIDDEN` |
| 없는 의뢰 | 404 `NOT_FOUND` |
| **내 업종·반경 밖이고 추천도 아닌 의뢰** | 403 `FORBIDDEN` |
| **이미 견적을 낸 의뢰**(의뢰당 1회) | 409 `CONFLICT` |
| **`REQUESTED` 가 아닌 의뢰**(배정·완료·취소) | 409 `CONFLICT` |
| 금액이 1,000원 미만·1억 초과·소수·문자열 · 메시지 500자 초과 | 400 `VALIDATION_ERROR` |

409(중복)는 **두 겹**이다 — 조회로 먼저 막고, 동시 요청은 `@@unique` 위반(P2002)을 같은 409 로 바꾼다
(T5.1 의 민원 전환 409 와 같은 처리).

### `PATCH /api/work-orders/[id]` — 응답에 `complaintStatus` 가 붙었다

