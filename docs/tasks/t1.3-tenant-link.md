# T1.3 세입자 연결

> Phase 1 · 상태: ✅ · [Phase 구성](../PHASES.md)

**Phase 1 의 마지막 조각.** 계약이 `PENDING_TENANT` → `ACTIVE` 로 넘어가는 **유일한 경로**다
(`PATCH /api/leases/[id]`(T1.2)는 `status: "ACTIVE"` 를 일부러 받지 않는다 — 임대인이 혼자
계약을 성립시키면 안 되기 때문). 그로스 여정([T1.8](./t1.8-notice-public.md))의 마지막 구간도 여기서 닫힌다.

- **플로우**: ①임대인 계약 등록(전화번호 포함) → PENDING_TENANT ②세입자가 같은 번호로 가입/로그인 → `tenantPhone` 매칭 계약 노출 ③수락 → `tenantProfileId`·`tenantAcceptedAt` 기록, ACTIVE 전환

| 라우트 | 화면·기능 |
|---|---|
| `/tenant/leases/accept` | 대기 계약 목록 → 조건 확인 → 수락/거절 |
| `/tenant` | 세입자 홈 — 내 계약 카드, 이번 달 납부 상태 + 「자리페이로 결제」(T2.2), 환급 배너, 민원 진입 |
| `/tenant/leases/pending` | **옛 경로** — `/tenant/leases/accept` 로 리다이렉트만 한다 |

| 엔드포인트 | 동작 |
|---|---|
| `GET /api/tenant/pending-leases` | 내 전화번호 매칭 대기 계약 |
| `POST /api/leases/[id]/accept` | 수락 — `tenantProfileId`·`tenantAcceptedAt`·`ACTIVE` |
| `POST /api/leases/[id]/decline` | 거절 — `CANCELLED` |

## 경로 통일 결정 — `/tenant/leases/pending` → `/tenant/leases/accept`

T0.4 가 플레이스홀더를 `/tenant/leases/pending` 에 깔았고 `resolveProfileRedirect` 가 거기로 보냈다.
task 문서가 지정한 정식 경로는 `/tenant/leases/accept` 다.

**결정: 정식 경로 하나만 화면으로 두고, 옛 경로는 리다이렉트로 남긴다.**

| 항목 | 내용 |
|---|---|
| 정식 경로 | `/tenant/leases/accept` — 실제 화면 |
| 옛 경로 | `/tenant/leases/pending` — `redirect()` 만 한다(지우지 않는다) |
| 판정 | `features/profiles/pending-lease.ts` 의 `PENDING_LEASE_PATH` **한 곳**에서만 관리. `resolveProfileRedirect` 도 이 상수를 쓴다 |

지우지 않고 리다이렉트를 남긴 이유 — T0.4 가 이미 `redirectTo: "/tenant/leases/pending"` 을 응답으로
내보냈고 문서·E2E·북마크에 그 문자열이 남아 있다. 404 로 죽이는 것보다 한 번 튕겨 주는 편이 싸다.
반대로 두 경로에 **같은 화면을 두 벌** 두지는 않았다 — 대기 계약 화면이 두 URL 로 존재하면
트래킹 `path` 가 갈라지고 어느 쪽이 정식인지 코드에서 알 수 없게 된다.

> **이 결정이 건드린 소유권 밖 파일 2개** (경로가 바뀌면 깨질 수밖에 없는 검증이라 최소 수정했다)
> - `apps/web/src/app/api/profiles/route.test.ts` — `redirectTo` 기대값 1줄
> - `e2e/auth.spec.ts` E2E② — URL 기대값 + 플레이스홀더(`t13-placeholder`) 단언 → 실제 카드(`pending-lease`) 단언
>
> 다른 task 문서(T0.4·T0.5·T1.8)에 남은 `/tenant/leases/pending` 표기는 그 task 소유라 고치지 않았다.

## 전화번호 매칭

- 비교는 항상 `@/lib/phone` 의 `normalizePhone` 을 태운 숫자끼리 한다.
- **목록 조회**는 `where: { tenantPhone: normalizePhone(내 번호) }` — 스키마의 `@@index([tenantPhone])` 를 그대로 탄다.
  (저장 시점에도 `phoneSchema`(T0.3)가 정규화하므로 DB 값은 이미 숫자만 남은 형태다.)
- **수락·거절 가드**는 양쪽 다 정규화해 비교한다(`requireMatchedLease`) — 수기·시드로 하이픈이 섞여 들어와도 매칭된다.
- 대기 목록은 `status = PENDING_TENANT` **이고** `tenantProfileId = null` 인 계약만 본다.

## 수락하면서 이번 달 청구를 확보하는 이유

크론(T1.4)은 **ACTIVE 계약만** 훑고 **당월만** 만든다. 계약 등록 시점(T1.2)에 만들어 둔 첫 청구는
그때의 당월이라, 세입자가 한 달 뒤에 수락하면 크론이 도는 새벽(KST 03:00)까지 세입자 홈의
"이번 달 납부"가 비어 보인다. 그래서 수락 순간에 **크론과 같은 규칙**으로 이번 달 청구를 확보한다.

- 대상 월: `resolveInitialChargeMonth`(계약 기간 밖이면 만들지 않는다 → 응답 `charge: null`)
- 금액: `buildChargeDraft`(전월 잔액 이월·연체료 포함) — 크론이 하룻밤 뒤 만들 값과 같다
- 중복: 이미 있으면 그것을 쓰고, 동시 요청은 `@@unique([leaseId, year, month])` + P2002 흡수로 막는다

## 거절 규칙과 근거 — `CANCELLED`

| 후보 | 판단 |
|---|---|
| 그대로 두고 **세입자에게만 숨김** | **불가.** `Lease` 에 "숨김" 컬럼이 없어 **스키마 변경**이 필요하고 이 task 는 스키마를 건드리지 않는다. 무엇보다 임대인 화면에는 계속 「세입자 연결 대기」로 남고 호실도 「대기」로 잠긴 채여서 **임대인이 잘못 적은 번호를 영원히 모른다** |
| `ENDED` | 아니다. 성립한 적 없는 계약을 "종료" 로 남기면 임대장부(T1.6)·보증금 정산(T2.3)이 이력으로 읽는다 |
| **`CANCELLED`** | ✅ 채택 |

`CANCELLED` 를 고른 이유 — **임대인 화면에서 무슨 일이 있었는지 보이고, 곧바로 고칠 수 있다.**

| 임대인 화면 | 거절 후 |
|---|---|
| 계약 목록·상세 배지 | 「취소」(`LEASE_STATUS_META.CANCELLED`, tone `neutral`) |
| 호실 그리드(T1.1 `deriveUnitStatus`) | 진행 중 계약이 사라져 **공실**로 돌아간다 |
| 같은 기간 재등록(T1.2 `BLOCKING_LEASE_STATUSES`) | 취소는 기간 중복을 막지 않으므로 **바로 다시 등록**할 수 있다 |
| 홈 대시보드(T1.9) | 아래 청구 정리 덕에 미납·연체로 세지 않는다 |

- `tenantProfileId`·`tenantAcceptedAt` 은 **채우지 않는다** — 거절은 연결이 아니다.
- **청구 정리**: 성립하지 않은 계약의 청구는 받을 근거가 없으므로 지운다. 단 **납부 기록이 있거나
  고지서를 보낸 청구는 남긴다**(T1.2 계약 종료가 세운 "이미 받은 돈의 근거는 지우지 않는다" 원칙 + 공개
  고지서 T1.8 이 아직 그 청구를 참조한다). 지우지 않으면 임대인 홈이 성립하지도 않은 계약의 청구를
  계속 미납으로 센다 — 대시보드는 계약 상태를 가리지 않고 청구를 집계한다.
- 되돌릴 수 없으므로 화면에서 **확인 시트**를 한 번 거친다.
