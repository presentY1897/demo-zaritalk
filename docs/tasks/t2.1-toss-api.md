# T2.1 토스 결제 API

> Phase 2 · 상태: ✅ · [Phase 구성](../PHASES.md)

**자리페이 = 토스페이먼츠 결제위젯(Payment Widget) v2.** 발급받은 키가 `test_gck_`/`test_gsk_` 라
구버전 결제창이 아니라 **주문서형(위젯)** 연동이다(`@tosspayments/tosspayments-sdk` 2.8.1).
화면은 [T2.2](./t2.2-pay-ui.md), 여기서는 **서버 API 3개**를 다룬다.

- **플로우**: ①`checkout` 으로 orderId 발급(READY, 금액=청구 잔액) ②토스 위젯 결제 → successUrl 리다이렉트 ③`confirm` — 서버 금액 위변조 검증 → 토스 승인 → DONE ④같은 트랜잭션에서 RentPayment(CARD) 생성 → 청구 재계산 → 임대인 원장 즉시 반영

| 엔드포인트 | 동작 |
|---|---|
| `POST /api/toss/checkout` | orderId 발급 + TossPayment(READY) |
| `POST /api/toss/confirm` | 금액 검증 → 승인 → DONE + RentPayment 반영, 실패 시 FAILED |
| `POST /api/toss/webhook` | 상태 변경 수신(취소 등) — raw 저장 후 동기화 |

## ① 요청·응답 JSON

### `POST /api/toss/checkout`

**금액을 요청에 담지 않는다.** 클라이언트는 청구 id 만 보내고 금액은 서버가 정한다.

```jsonc
// 요청
{ "chargeId": "clx…" }

// 201 — orderId 는 토스 규칙(영문·숫자·`-`·`_`·`=` 6~64자)을 지키는 `zari_<uuid32>` 다
{
  "orderId": "zari_9f2c1a4b6d7e4f0a8b3c5d6e7f80912a",
  "amount": 1015500,                       // = 청구 잔액. 부분납이면 남은 금액만
  "orderName": "행당해피빌 201호 2026년 8월 월세",
  "customerKey": "clx_tenant_profile_id",  // 위젯 widgets({ customerKey }) — 세입자 프로필 cuid
  "customerName": "박세입",
  "chargeId": "clx…"
}
```

| 실패 | status · code |
|---|---|
| 비로그인 | 401 `UNAUTHORIZED` |
| 세입자 프로필 없음 | 403 `FORBIDDEN` |
| 없는 청구 | 404 `NOT_FOUND` |
| **내가 수락한 계약의 청구가 아님** | 403 `FORBIDDEN` |
| 이미 완납(잔액 0) | 409 `CONFLICT` |
| 토스 키 미설정 | 500 `INTERNAL_ERROR` (주문을 만들기 **전에** 막는다) |

### `POST /api/toss/confirm`

위젯이 `successUrl` 로 넘겨준 쿼리를 그대로 옮겨 담는다.
`{successUrl}?paymentType=NORMAL&amount=1015500&orderId=…&paymentKey=…`

```jsonc
// 요청
{ "paymentKey": "tviva202609…", "orderId": "zari_9f2c…", "amount": 1015500 }

// 200 — 영수증 + **원장 반영 결과**(재계산된 청구). 화면이 다시 조회할 필요가 없다
{
  "receipt": {
    "orderId": "zari_9f2c…",
    "paymentKey": "tviva202609…",
    "amount": 1015500,
    "method": "카드",
    "approvedAt": "2026-09-02T12:00:00+09:00",
    "receiptUrl": "https://dashboard.tosspayments.com/receipt/…",
    "cardCompany": "신한",
    "status": "DONE"
  },
  "charge": { "id": "clx…", "totalDue": 1015500, "paidAmount": 1015500,
              "outstanding": 0, "status": "PAID", "lines": [ … ], "payments": [ … ] }
}
```

| 실패 | status · code |
|---|---|
| 비로그인 | 401 `UNAUTHORIZED` |
| 남의 주문 | 403 `FORBIDDEN` |
| 없는 orderId | 404 `NOT_FOUND` |
| **금액 불일치**(위변조·청구 변경·승인액 상이) | 400 `VALIDATION_ERROR` + `details: { expected, received, outstanding }` |
| **이미 승인·취소·실패한 주문**(재승인) | 409 `CONFLICT` + `details: { status }` |
| 토스가 승인을 거절 | 409 `CONFLICT` + `details: { tossCode, tossMessage }` |

> 승인 거절은 의미상 **502** 가 맞지만 `lib/api/response.ts` 의 `ApiErrorCode` 집합(T0.3 소유,
> 이 task 는 읽기 전용)에 502 계열이 없어 409 로 내보내고 토스 코드는 `details` 에 실었다.
> 코드 집합을 넓힐 수 있다면 `BAD_GATEWAY` 를 추가하는 편이 정확하다.

### `POST /api/toss/webhook`

```jsonc
// 요청(토스) — data 는 Payment 객체다
{
  "eventType": "PAYMENT_STATUS_CHANGED",
  "createdAt": "2026-09-02T12:34:56+09:00",
  "data": { "paymentKey": "tviva…", "orderId": "zari_9f2c…", "status": "CANCELED", "totalAmount": 1015500, … }
}

// 200 — 언제나 200 이다(모르는 주문·다루지 않는 이벤트 포함)
{ "received": true, "ignored": false, "verified": true,
  "orderId": "zari_9f2c…", "status": "CANCELED", "action": "canceled" }
```

`action` 은 `none | approved | canceled | failed | unchanged`.
**JSON 이 아니거나 스키마를 벗어난 경우만 400** 이다 — 재전송이 의미 있는 유일한 경우라서다.

## ② 금액 위변조 검증 — 3중

클라이언트가 보낸 금액은 **대조용으로만** 쓴다. 세 개가 전부 같아야 승인한다.

| # | 비교 | 막는 것 | 시점 |
|---|---|---|---|
| ① | `body.amount` = `TossPayment.amount` | successUrl 쿼리의 `?amount=` 를 손댄 경우 | 토스 호출 **전** |
| ② | `TossPayment.amount` = `calcOutstanding(청구)` | checkout 이후 임대인이 수기 납부를 기록해 잔액이 줄어든 경우 | 토스 호출 **전** |
| ③ | 승인 응답 `totalAmount` = `TossPayment.amount` | 토스에 다른 금액이 결제된 경우 | 승인 **후**(→ FAILED, 원장 미반영) |

- ①② 는 **토스를 호출하기도 전에** 막는다(테스트로 호출 0회를 확인한다).
- **거절해도 사용자 카드는 이미 결제됐을 수 있다**(탭을 두 개 열어 두 번 결제한 경우 등).
  그래서 ①② 로 거절할 때 `TossPayment.raw.rejected[]` 에 `{ at, reason, paymentKey, expected,
  received, outstanding }` 을 남긴다 — 나중에 그 결제를 찾아 환불·대사할 수 있게. **상태와
  `paymentKey` 유니크 컬럼은 건드리지 않는다**(승인하지 않은 결제를 이 주문 것으로 확정하면
  잘못된 복구가 일어날 수 있다).
- ③ 에 걸리면 `TossPayment` 를 FAILED 로 내리고 `RentPayment` 를 만들지 않는다.
- 초과 납부는 ② 가 함께 막는다 — `TossPayment.amount` 가 잔액보다 크면 그 자체로 불일치다.
  (T1.5 의 `isOverpayment` 400 규칙과 같은 결과다.)
- **금액은 서버가 정한다**: `checkout` 이 잔액을 확정하고, `confirm` 은 그 값만 승인 금액으로 쓴다.

## ③ 재승인 방지 — DB 제약 + 조건부 UPDATE(CAS)

**스키마에 이미 있는 유니크 제약 3개**를 그대로 활용했다(스키마는 건드리지 않았다):

| 제약 | 막는 것 |
|---|---|
| `TossPayment.orderId @unique` | 주문 중복 |
| `TossPayment.paymentKey @unique` | 같은 결제가 두 주문에 붙는 것 |
| **`RentPayment.tossPaymentId @unique`** | **같은 결제로 납부 행이 두 개 생기는 것 — 최후의 방어선** |

여기에 **조건부 UPDATE 두 번**을 얹는다(Postgres 는 UPDATE 시 행 잠금 + WHERE 재평가라
`updateMany().count` 가 그대로 compare-and-set 이 된다):

```
② 승인 선점 : UPDATE … SET paymentKey = ? WHERE orderId = ? AND status='READY' AND paymentKey IS NULL
              count = 1 → 내가 승인한다        count = 0 → 다른 요청이 선점했거나 복구 대상이다
④ 원장 반영 : UPDATE … SET status='DONE' … WHERE id = ? AND status='READY'      (트랜잭션 안)
              count = 0 → 이미 반영됐다 → 중단
```

- **DONE·CANCELED·FAILED 주문은 진입 즉시 409** 다(`status !== "READY"`).
- **동시 요청**은 ② 에서 하나만 통과하고, 그마저 뚫려도 ④ 의 CAS + `tossPaymentId` 유니크가 막는다.
  (테스트: `축 ② 동시 승인 요청이 와도 납부는 1건만 생긴다`)
- 토스 쪽에서도 승인 요청에 **`Idempotency-Key: <orderId>`** 를 붙여 네트워크 재시도로 인한
  이중 승인을 막는다.

## ④ 승인 후 DB 반영 실패 대응 — "돈은 받았는데 원장에 없음"

토스 승인은 외부 HTTP 라 트랜잭션에 넣을 수 없다. 그래서 **승인 전에 paymentKey 를 먼저 박아 둔다**
(② 승인 선점). 이 한 줄이 복구의 근거가 된다 — 반영이 끊긴 주문은
`status = READY` **이면서** `paymentKey != null` 인 유일한 상태로 남는다.

```
정상        READY(key=null) → READY(key=set) → [승인] → DONE + RentPayment + 청구 갱신   ← ④ 는 한 트랜잭션
반영 실패   READY(key=null) → READY(key=set) → [승인] → ✗ (프로세스 사망·DB 장애)
                                                        ↑ 여기서 멈춘 주문을 두 경로가 복구한다
```

| 복구 경로 | 동작 |
|---|---|
| **재시도 복구** | 같은 orderId·paymentKey 로 `confirm` 이 다시 오면 승인을 **다시 하지 않고** `GET /v1/payments/{paymentKey}` 로 진짜 상태를 확인한 뒤 ④ 만 실행한다. 성공 화면은 새로고침만 해도 복구된다 |
| **웹훅 복구** | `PAYMENT_STATUS_CHANGED(DONE)` 이 오면 같은 ④ 를 실행한다. 사용자가 창을 닫아도 최대 7회(약 3일 19시간) 재시도되는 웹훅이 원장을 맞춘다 |

- 두 경로 모두 ④ 의 CAS + `tossPaymentId` 유니크를 지나므로 **중복 반영되지 않는다.**
- **네트워크 오류는 FAILED 로 확정하지 않는다.** 승인 여부를 모르는 상태라 FAILED 로 못박으면
  진짜 결제된 돈이 영원히 원장 밖에 남는다. READY 로 두고 위 두 경로에 맡긴다.
- `paymentKey` 가 다르면 복구하지 않고 409 다(남의 결제로 남의 청구를 메우지 못하게).
- **남은 위험**: 승인 성공 + 반영 실패 + 사용자가 돌아오지 않음 + 웹훅 미등록이면 원장이 비어 있다.
  운영에서는 웹훅 등록이 사실상 필수이고, 그 위에 `status='READY' AND paymentKey IS NOT NULL AND
  createdAt < now()-10min` 을 훑는 대사 배치를 두는 것이 정석이다(데모 범위 밖이라 만들지 않았다).

## ⑤ webhook 검증 — 서명이 아니라 **재조회**

토스 문서(2026-09 확인) 기준 **결제 상태 웹훅에는 서명 헤더가 없다.**
`tosspayments-webhook-signature` 는 `payout.changed`·`seller.changed` 전용이고,
`PAYMENT_STATUS_CHANGED` 에 오는 헤더는 `tosspayments-webhook-transmission-time`·`-id`·
`-retried-count` 로 **추적용**이다(IP 화이트리스트도 문서에 없다).

그래서 이렇게 한다:

1. **raw 를 먼저 저장한다** — 검증에 실패해도 "이런 웹훅이 왔다" 는 기록이 남아야 대사가 된다.
   `TossPayment.raw` 는 `{ payment, webhooks: [최근 10건], rejected: [최근 10건] }` 모양이다
   (`payment` = 토스 Payment 원문, `webhooks` = 받은 이벤트 원문, `rejected` = 금액 불일치로 거절한 승인 시도).
2. **본문을 신뢰하지 않고 토스에 다시 묻는다** — 우리 시크릿 키로만 호출할 수 있는
   `GET /v1/payments/{paymentKey}`(없으면 `GET /v1/payments/orders/{orderId}`)의 결과로만 동기화한다.
   **이 재조회가 곧 인증**이다. 위조 본문이 와도 토스 원본과 다르면 DB 는 바뀌지 않는다.
3. 조회 결과의 `orderId` 가 우리 주문과 다르면 동기화하지 않는다.

| 토스 실제 상태 | 우리 동작 |
|---|---|
| `CANCELED` · `PARTIAL_CANCELED` | `TossPayment` → CANCELED, **CARD `RentPayment` 삭제 + `recalcCharge`**(완납 → 부분납·연체로 복귀). 한 트랜잭션 |
| `DONE` (우리는 아직 READY) | ④ 원장 반영 복구 |
| `ABORTED` · `EXPIRED` | READY 인 주문만 FAILED |
| 그 외 | 아무것도 하지 않음(`unchanged`) |

- **항상 200** 이다 — 토스는 10초 안에 200 을 못 받으면 최대 7회 재시도한다. 모르는 주문·다루지
  않는 이벤트로 재시도가 쌓여 봐야 얻을 게 없다.
- **부분 취소도 전액 회수로 처리한다.** `RentPayment` 는 부분 취소 금액을 표현할 컬럼이 없고,
  잔액을 임의로 쪼개 넣으면 원장이 토스와 어긋난다. 부분 취소를 정확히 반영하려면
  `RentPayment` 에 취소 금액 컬럼이 필요하다(스키마 변경이라 하지 않았다 — 아래 참고).
- **로컬에서는 웹훅을 받을 수 없다**(공개 URL 필요). 검증은 단위 테스트가 라우트를 직접 호출해서 한다.

## ⑥ 토스 API 연동 사실 (공식 문서 + 실 호출로 확인)

| | |
|---|---|
| 승인 | `POST https://api.tosspayments.com/v1/payments/confirm` · body `{ paymentKey, orderId, amount }` |
| 조회 | `GET https://api.tosspayments.com/v1/payments/{paymentKey}` |
| 인증 | `Authorization: Basic base64("<시크릿키>:")` — **콜론까지 붙여** base64(비밀번호 없는 Basic) |
| 멱등 | `Idempotency-Key` 헤더 |
| 실패 | `{ "code": "…", "message": "…" }` |

실제 테스트 키로 호출해 확인한 응답:

```
정상 키 + 없는 결제 → 404 {"code":"NOT_FOUND_PAYMENT_SESSION","message":"결제 시간이 만료되어 …"}
잘못된 키          → 401 {"code":"UNAUTHORIZED_KEY","message":"인증되지 않은 시크릿 키 …"}
```

키는 [`.env.example`](../../.env.example) 의 `NEXT_PUBLIC_TOSS_CLIENT_KEY`(gck)·`TOSS_SECRET_KEY`(gsk).
**토스 문서에 공개된 체험용 키**라 개발자센터 대시보드에는 잡히지 않는다(정상).
자기 계정 키로 바꾸려면 두 값만 교체하면 된다.

## 후속 task 가 알아야 할 것

- **스키마는 변경하지 않았다.** `TossPayment`·`TossPaymentStatus`·`RentPayment.tossPaymentId` 는 이미 있었다.
  다만 **필요했지만 만들지 않은 것**이 셋 있다:
  1. `TossPaymentStatus` 에 `IN_PROGRESS` 가 없어 "승인 진행 중" 을 별도 상태로 표현하지 못한다 —
     `paymentKey` 선점으로 대신했다(동작에는 문제없다).
  2. `RentPayment` 에 **취소 금액 컬럼이 없어** 부분 취소를 그대로 반영하지 못한다(전액 회수로 처리).
  3. 반영 실패 대사 배치를 만들려면 `TossPayment` 에 `updatedAt` 이 있으면 편하다(현재 `createdAt` 만).
- **`recalcCharge` 에 선택 인자를 하나 더했다** — `recalcCharge(chargeId, client = prisma)`.
  `prisma.$transaction` 의 tx 클라이언트를 받기 위한 것이고 **기존 호출부·동작은 그대로**다
  (인자를 안 주면 전역 prisma). 승인 결과를 원자적으로 반영하려면 이 한 곳이 필요했다.
- **결제되지 않은 READY 주문은 남는다.** 결제 화면에서 버튼을 누를 때마다 주문이 하나 생기고,
  사용자가 결제창을 닫으면 그 주문은 READY 로 남는다(다음 결제는 새 orderId 를 쓰므로 섞이지 않는다).
  데모에서는 무해하지만, 운영이라면 오래된 READY 주문을 정리하는 배치가 있으면 좋다.
- **`DELETE /api/payments/[id]` 는 CARD 납부를 409 로 막는다**(T1.5 가 이미 그렇게 만들어 뒀다).
  카드 결제 취소는 토스 취소 API + 웹훅으로 처리해야 한다. **취소 API(`POST /v1/payments/{key}/cancel`)는
  이 task 범위가 아니라 만들지 않았다** — 웹훅 수신 쪽만 구현했다.
- **[PHASES.md](../PHASES.md) 의 T2.1 상태(⬜)는 갱신하지 않았다** — 파일 소유권상 이 task 범위 밖이라
  Phase 2 통합 시점에 함께 ✅ 로 바꾼다.
