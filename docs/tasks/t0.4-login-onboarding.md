## 화면 구조 (T0.5 가 셸을 붙일 때 알아야 할 것)

- 로그인·온보딩은 **route group `(auth)`** 아래에 있다 — `app/(auth)/{login,onboarding}/page.tsx`.
  `app/(auth)/layout.tsx` 는 **하단 탭바가 없는** 레이아웃이다(세션·프로필이 없는 상태이므로).
  탭바가 붙는 앱 셸은 `(auth)` **밖**에서 감싸면 된다 — 예: `app/(app)/layout.tsx` 를 새로 만들고
  홈·마이 라우트를 그 그룹으로 옮기는 식. 480px 폭 제한은 루트 `app/layout.tsx`(T0.7 소유)가 이미 잡는다.
- `/tenant/leases/pending` 은 `(auth)` 밖의 일반 라우트다 — 탭바가 생기면 자연히 그 아래로 들어간다.
- 클라이언트 훅은 `src/features/auth/hooks.ts` (Tanstack Query).
  `ME_QUERY_KEY = ["me"]` 를 공유하면 로그인·프로필 생성 응답으로 채워 둔 `/api/me` 캐시를 그대로 쓴다.
  - `useMe()` · `useRequestOtp()` · `useVerifyOtp()` · `useDemoLogin()` · `useCreateProfile()` · `useLogout()`
  - 응답 타입은 `src/features/auth/types.ts` (`@zari/db` 를 import 하지 않는 클라이언트 전용 미러)
- **활성 프로필 전환 API(`POST /api/profiles/active`)는 T0.5 소유라 만들지 않았다.**
  다만 `POST /api/profiles` 는 방금 만든 프로필을 활성으로 잡아 준다(`setActiveProfile`).

## `POST /api/profiles` — 프로필 추가 / 가입 확정

가입 티켓(`signupTicket`)이 있으면 **User 생성 + 프로필 생성 + 세션 발급**까지, 없으면
로그인 상태의 기존 User 에 프로필만 추가한다.

```jsonc
// 요청 ① 가입 플로우(임대인·세입자) — name 필수
{ "type": "TENANT", "name": "홍미가", "signupTicket": "cmf0…" }

// 요청 ② 중개인 — realtor 필수(officeName·address·lat·lng·radiusKm)
{
  "type": "REALTOR", "name": "이중개", "signupTicket": "cmf0…",
  "realtor": {
    "officeName": "왕십리부동산", "licenseNo": "12345",      // licenseNo·intro 는 선택
    "address": "서울 성동구 왕십리로 300",
    "lat": 37.56133, "lng": 127.03782, "radiusKm": 3
  }
}

// 요청 ③ 마스터 — master 필수(companyName·categories 1개 이상·address·lat·lng·radiusKm)
{
  "type": "MASTER", "name": "최마스",
  "master": {
    "companyName": "성수홈케어",
    "categories": ["REPAIR", "CLEANING"],                   // CLEANING|INTERIOR|REPAIR|ETC
    "address": "서울 성동구 아차산로 100",
    "lat": 37.54453, "lng": 127.05599, "radiusKm": 5
  }
}

// 201 — me 는 GET /api/me 와 같은 모양(가입 플로우면 세션 쿠키도 함께 설정된다)
{
  "profile": { "id": "cmf0…", "type": "TENANT", "createdAt": "…",
               "realtorDetail": null, "masterDetail": null },
  "me": { "user": { … }, "profiles": [ … ], "activeProfile": { … } },
  "redirectTo": "/tenant/leases/pending"
}
```

| 실패 | status · code |
|---|---|
| 유형별 Detail 필수값 누락·형식 오류, 모르는 유형, 가입 플로우인데 이름 없음 | 400 `VALIDATION_ERROR` |
| 티켓도 세션도 없음 | 401 `UNAUTHORIZED` |
| 이미 같은 유형 프로필 보유 (`@@unique([userId, type])`) | 409 `CONFLICT` |
| 티켓이 없음·이미 소진·만료(10분)·미검증 | 400 `SIGNUP_TICKET_INVALID` |

- 티켓 소진(`consumeSignupTicket`)은 **중복 유형 검사 뒤**에 한다 — 409 로 튕길 요청에 티켓을 태우지 않는다.
- `name` 을 함께 보내면 로그인 상태에서도 `User.name` 을 갱신한다.

## `PATCH /api/profiles/[id]` — 프로필 수정

유형은 바꿀 수 없다. **저장된 유형에 맞는 Detail 을 통째로** 받는다(부분 수정 아님).

```jsonc
// 요청 (REALTOR 프로필)
{ "name": "이중개", "realtor": { "officeName": "성수공인중개", "address": "…",
                                 "lat": 37.54453, "lng": 127.05599, "radiusKm": 5, "intro": "…" } }
// 200
{ "profile": { … }, "me": { "user": { … }, "profiles": [ … ], "activeProfile": { … } } }
```

| 실패 | status · code |
|---|---|
| 유형에 필요한 Detail 누락·형식 오류 | 400 `VALIDATION_ERROR` |
| 비로그인 | 401 `UNAUTHORIZED` |
| **남의 프로필** | 403 `FORBIDDEN` |
| 없는 프로필 | 404 `NOT_FOUND` |

## 리다이렉트 규칙

| 상황 | 이동 |
|---|---|
| OTP 검증 → 기존 회원(`status: "SESSION"`) | `/` (홈) |
| OTP 검증 → 신규 번호(`status: "SIGNUP_REQUIRED"`) | `/onboarding?ticket=<signupTicket>` |
| 온보딩 완료 — 세입자 유형 **AND** 내 번호로 `PENDING_TENANT` 계약 존재 | `/tenant/leases/pending` (T1.3 플레이스홀더) |
| 온보딩 완료 — 그 외 전부 | `/` |
| `/onboarding` 에 티켓 없이 비로그인 진입 | `/login` (서버 `redirect`) |
| `/onboarding?ticket=` 이 만료·소진된 티켓 | 안내 화면 + `/login` 링크 (리다이렉트 아님) |
| `/tenant/leases/pending` 비로그인 진입 | `/login` |

판정은 **서버가** 하고 응답의 `redirectTo` 로 내려 준다 — `src/features/profiles/pending-lease.ts`
(`resolveProfileRedirect(phone, type)`). 클라이언트는 그 값으로 `router.replace()` 만 한다.

## 좌표 입력 (임시)

카카오맵 키가 아직 없어 **주소 문자열 + 위도·경도 수동 입력**이다. 시연 편의를 위해
서울 주요 지역 프리셋(왕십리·성수·강남역·홍대입구·잠실·여의도)을 누르면 주소·좌표가 채워진다 —
`src/features/profiles/constants.ts` 의 `AREA_PRESETS`.
**T3.x(매물 지도·통근)에서 카카오 로컬 API 지오코딩이 들어오면** 이 프리셋과 위경도 입력칸을 함께 걷어내고
주소 검색 한 칸으로 바꾼다(해당 코드에 주석으로도 남겨 뒀다).
