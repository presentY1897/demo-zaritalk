# T3.6 중개 요청·반경 매칭

> Phase 3 · 상태: ✅ · [Phase 구성](../PHASES.md)

**[T3.7 중개인 수신함·수락](./t3.7-realtor-inbox.md)과 한 묶음으로 작업했다** — 요청과 수락은
같은 상태 기계의 양 끝이라 전이표·DTO·조회를 갈라 둘 이유가 없다. 공통 모듈은
`features/brokerage/**` 에 있고, 중개인 **화면**만 `features/realtor/**` 에 있다.

- **매칭 규칙**: ①공실 Unit에서 요청 → 건물 좌표 기준 `RealtorDetail` 사무소 좌표+활동반경 내 중개인 거리순 최대 20명 ②BrokerageTarget(SENT) 생성 + 알림톡 시뮬 발송 ③열람 VIEWED → 수락 ACCEPTED(복수 허용), 첫 수락 시 요청 MATCHED

| 라우트/API | 동작 |
|---|---|
| 요청 시트(공실 호실) | 메시지 작성 → 반경 내 중개인 미리보기(인원·지도) → 발송 |
| `/landlord/brokerage` | 내 요청 목록 — 대상 수·응답 현황(열람/수락/거절), 수락 중개인 연락 카드 |
| `POST /api/brokerage-requests` | 요청 생성 + 반경 매칭 + 타겟·알림 생성, `GET` 목록 |
| `GET /api/brokerage-requests/preview?unitId=` | 발송 전 대상 미리보기 |

## 거리 유틸을 새로 만들지 않았다 — T5.1 의 `lib/geo/distance.ts` 를 그대로 썼다

[T5.2 문서](./t5.2-master-feed.md)가 남겨 둔 대로 `rankByDistance(building, realtorDetails, { limit: 20 })`
한 줄이다. `RealtorDetail` 이 `{ lat, lng, radiusKm }` 을 가지고 있어 `RadiusCandidate` 를
구조적으로 만족한다 — 어댑터도 필요 없었다.

```ts
// features/brokerage/matching.ts — 매칭의 전부다
const candidates = await prisma.realtorDetail.findMany({
  where: { profile: { type: ProfileType.REALTOR } },
  include: { profile: { include: { user: { select: { name: true, phone: true } } } } },
  orderBy: { profileId: "asc" },   // 거리가 같을 때 순서가 실행마다 흔들리지 않게
});
return rankByDistance(origin, candidates, { limit: BROKERAGE_TARGET_LIMIT });
```

| | 작업 의뢰 push(T5.1) | **공실 중개(T3.6)** |
|---|---|---|
| 원점 | 의뢰 건물 | **공실 건물** (`Unit` 에 좌표가 없다) |
| 후보 | `MasterDetail`(업종 일치 + `plan=PRO`) | **`RealtorDetail` 전부** — 업종·플랜 같은 추가 조건이 없다 |
| 반경 | 후보의 `radiusKm`(경계 포함) | 같다 |
| 상한 | 10명 | **20명** |

**부족했던 점은 없다.** 저장하는 `distanceKm` 도 `rankByDistance` 가 이미 `roundKm`(소수 3자리)로
반올림해 준 값을 그대로 쓴다(화면 표시와 저장값이 같다). 유일하게 더한 것은 후보 조회의
`orderBy: { profileId: "asc" }` 인데, 이건 거리 유틸의 문제가 아니라 **DB 조회 순서**의 문제다 —
`rankByDistance` 가 안정 정렬이라 거리가 완전히 같은 후보의 순서는 **입력 순서**로 정해지고,
Postgres 는 `orderBy` 가 없으면 그 순서를 보장하지 않는다.

## 미리보기 = 실제 발송, 어떻게 보장했나

**함수를 하나만 두는 것**으로 보장한다(T5.2 의 `selectWorkOrderTargets` 와 같은 패턴).

```
GET /api/brokerage-requests/preview ─┐
                                     ├─→ selectBrokerageTargets(건물좌표)  ← DB 읽기만, 쓰기 없음
POST /api/brokerage-requests ────────┘        └─ rankByDistance(…, { limit: 20 })
```

- `selectBrokerageTargets` 는 **아무 것도 쓰지 않는다** — 미리보기가 부작용 없이 그대로 부른다.
- 발송은 그 결과에서 **이미 보낸 중개인만 빼고**(`@@unique([requestId, realtorProfileId])`) 저장한다.
  그래서 첫 발송에서는 `preview.count === dispatchedCount` 가 정확히 성립하고,
  재발송에서는 "이번에 새로 간 수" 만 줄어든다(화면 문구도 그렇게 말한다).
- 테스트가 **인원 수뿐 아니라 대상 id 배열과 거리 배열까지** 대조한다
  (`matching.test.ts` "미리보기와 실제 발송이 같은 대상을 고른다",
  `preview/route.test.ts` "미리보기 인원이 곧 발송 인원이다").

## 같은 호실에 다시 보내면 **새 요청을 만들지 않는다**

그 호실에 아직 `OPEN` 인 요청이 있으면 **그 요청에 재발송**한다(`200` · `reused: true`).

- 새 요청을 매번 쌓으면 임대인 목록이 같은 호실로 도배되고, 중개인은 같은 공실을 여러 번 받는다.
- 재발송에서는 이미 보낸 중개인을 건너뛰므로 **중복 타겟도 중복 알림톡도 생기지 않는다.**
  그 사이 새로 반경에 들어온 중개인에게만 간다.
- 요청이 `MATCHED`·`CLOSED` 면 **새 요청을 만든다**(`201`) — 이미 한 번 매칭된 건과
  다시 찾는 건은 다른 이야기다.
- 메시지를 새로 적어 보내면 갈아 끼우고, 비워 보내면 기존 문구를 지우지 않는다.

## 요청·응답

에러는 D1 규약대로 `{ "error": { "code", "message", "details?" } }` 한 형태다.

### `POST /api/brokerage-requests`

```jsonc
// 요청 — message 는 선택(최대 500자). 대상은 공실 호실 하나다
{ "unitId": "cmf0…", "message": "즉시 입주 가능합니다. 월세 50만원 선입니다." }

// 201 (새 요청) / 200 (열린 요청에 재발송 — reused: true)
{
  "request": {
    "id": "cmf0…",
    "status": "OPEN",                       // OPEN | MATCHED | CLOSED
    "message": "즉시 입주 가능합니다. 월세 50만원 선입니다.",
    "createdAt": "2026-09-02T12:00:00.000Z",
    "place": {
      "unitId": "cmf0…", "unitLabel": "101호",
      "floor": 1, "areaM2": 23.1, "rooms": 1,
      "buildingId": "cmf0…", "buildingName": "행당해피빌",
      "buildingAddress": "서울 성동구 행당로 79",
      "lat": 37.56152, "lng": 127.03648      // 매칭 원점 = 건물 좌표
    },
    "targetCount": 1,
    "counts": { "SENT": 1, "VIEWED": 0, "ACCEPTED": 0, "DECLINED": 0 },
    "accepted": [],                          // 수락 중개인 연락 카드(아래 GET 예시)
    "listing": null                          // 그 호실에 살아 있는 매물이 있으면 요약
  },
  "dispatchedCount": 1,                      // 이번에 새로 발송된 수
  "reused": false

```

| 실패 | status · code |
|---|---|
| 비로그인 | 401 `UNAUTHORIZED` |
| 임대인 프로필 없음 | 403 `FORBIDDEN` |
| 없는 호실 | 404 `NOT_FOUND` |
| 남의 호실 | 403 `FORBIDDEN` |
| **계약중·대기 호실** | 409 `CONFLICT` — "계약이 있는 호실에는 중개를 요청할 수 없습니다." |
| 호실 누락 · 메시지 500자 초과 | 400 `VALIDATION_ERROR` |

### `GET /api/brokerage-requests/preview?unitId=`

```jsonc
// 200 — 거리순. **연락처(name·phone)는 담지 않는다**
{
  "unit": { "…place…" },
  "realtors": [
    { "profileId": "cmf0…", "officeName": "왕십리부동산",
      "address": "서울 성동구 왕십리로 300",
      "lat": 37.56133, "lng": 127.03782, "radiusKm": 3, "distanceKm": 0.12 }
  ],
  "count": 1,
  "limit": 20,
  "blockedReason": null,        // 계약중 호실이면 문구가 들어온다(409 가 아니다)
  "openRequestId": null         // 있으면 "새 요청 대신 재발송" 안내
}
```

- **계약중 호실은 400·409 가 아니라 200 + `blockedReason`** 이다 — 화면이 "왜 못 보내는지" 를
  그려야 하고 그 안내에도 호실 정보가 필요하다(T5.2 의 `upgradeRequired` 와 같은 판단).
- 발송 전에 이름·전화번호를 주지 않는 이유: 그건 매칭이 아니라 **명부 유출**이다.
  테스트가 응답 본문에 번호·이름 문자열이 없는지 직접 확인한다.

### 지도는 거들 뿐이다

`BrokerageMap` 은 `NEXT_PUBLIC_KAKAO_MAP_JS_KEY` 로 카카오 지도 SDK 를 **동적으로** 불러
공실 건물과 중개인 사무소를 찍는다. 키가 없거나 스크립트가 막히면 **지도를 포기하고 목록만 남긴다** —
대상 인원·목록은 지도 없이도 완전히 읽힌다.

카카오 JS 키는 **도메인 등록제**라 E2E 포트가 등록돼 있지 않다. 그래서 **E2E 는 지도 렌더를
단언하지 않고** 인원 수(`brokerage-preview-count`)와 목록(`brokerage-preview-realtor`)으로 검증한다.

## 스키마를 건드리지 않고 앱에서 처리한 것

`packages/db/prisma/**` 는 이번 task 소유가 아니라 손대지 않았다. 있으면 좋았을 것들:

| 아쉬웠던 것 | 지금 | 스키마로 옮긴다면 |
|---|---|---|
| **`BrokerageTarget.sentAt`** 이 없다 | 발송 시각을 요청의 `createdAt` 으로 대신한다. 재발송으로 나중에 붙은 타겟도 요청 생성 시각으로 보인다 | `WorkOrderTarget` 처럼 `sentAt DateTime @default(now())` |
| 호실당 열린 요청 1건 | 라우트에서 `OPEN` 요청을 찾아 재사용 | 부분 unique 인덱스(`unitId` where `status = 'OPEN'`) — Prisma 가 부분 인덱스를 직접 지원하지 않아 raw 마이그레이션이 필요하다 |
| 중개인별 수신함 조회 | `BrokerageTarget(realtorProfileId)` 풀스캔 | `@@index([realtorProfileId])`(T3.1 문서도 같은 지점을 적어 뒀다) |
| **`MessageKind` 에 "중개 수락" 이 없다** | 수락 알림도 `BROKERAGE_REQUEST` 로 남긴다(제목으로 구분) | `BROKERAGE_ACCEPTED` 값 추가 |
| `BrokerageRequest.updatedAt` 이 없다 | 목록 정렬은 `createdAt` 기준 | `updatedAt DateTime @updatedAt` |
