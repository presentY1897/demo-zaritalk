## ✅ D4. 마스터 매칭 방식 — pull + push 하이브리드

- **확정**: **pull 피드를 기본으로 두고, push 추천을 공통 기능으로 함께 구현**한다.
  - **pull(전 마스터)** — 마스터가 자기 업종 + 활동반경 안의 `REQUESTED` 의뢰를 피드로 조회하고 견적 제안(T5.2).
  - **push(유료 가입 마스터)** — 의뢰 생성 시 조건에 맞는 유료 마스터를 골라 **추천 대상으로 발송**한다. 유료 마스터는 피드를 뒤지지 않아도 맞는 일감을 먼저 받는다 — 이것이 유료 플랜의 값어치.
- **대안(기각)**: pull 단독 / push 단독.
- **근거**: pull만으로는 유료 전환 동기가 없고, push만으로는 신규·무료 마스터가 일감에 접근할 길이 없다. 둘을 겹치면 "무료는 찾아가고, 유료는 받아본다"는 수익 모델이 데모에 드러나고, 중개 매칭(T3.6 push)과 패턴을 공유해 매칭 로직을 재사용할 수 있다.
- **스키마 영향** (Phase 5 착수 시 마이그레이션):
  - `MasterDetail` 에 유료 플랜 필드 — `plan: MasterPlan(FREE|PRO)`, `planUntil: DateTime?`
  - `WorkOrderTarget` 모델 신설 — `BrokerageTarget` 과 같은 형태(workOrderId, masterProfileId, distanceKm, status, sentAt). 의뢰 생성 시 반경·업종·`plan=PRO` 조건으로 거리순 N명 생성
- **관련 task**: T5.1(의뢰 생성 시 push 타겟 생성) · T5.2(피드 = pull, 추천함 = push) · T5.3(견적)

## ✅ D9. 대중교통 통근시간 — 모킹 (2026-09-02 확정)

- **확정**: **차량 통근시간만 실연동**(카카오모빌리티 REST)하고, **대중교통은 모킹**한다. 화면은 처음부터 두 수단을 나란히 보여주는 구조로 만들고, 대중교통 값은 모의 제공자가 낸다. ODsay 키를 나중에 넣으면 제공자만 교체된다.
- **대안(기각)**: ① ODsay 실연동 — 무료지만 승인 대기가 있어 일정이 묶인다 ② **직접 경로탐색 구현** — 아래 근거로 기각.
- **직접 구현을 기각한 근거**: 알고리즘(RAPTOR·Connection Scan)이 아니라 **데이터가 막는다.**
  - 전국 통합 GTFS 피드가 공개돼 있지 않다. 국가대중교통정보센터·서울시·경기도가 조각으로 내놓고 포맷·갱신주기가 제각각이라 정제·병합 자체가 별도 프로젝트다.
  - 환승에 필요한 **도보 네트워크**(출발지↔정류장, 정류장↔정류장)를 OSM 등으로 따로 태워야 한다.
  - 환승 할인·배차간격 기반 노선·첫차/막차까지 붙는다.
  - 산출물은 "매물 카드의 통근시간 배지" 하나다. 이 데모가 보여주려는 것(프론트엔드·그로스)과 투자 대비가 맞지 않는다.
- **카카오는 대안이 아니다**: 카카오모빌리티 REST 는 자동차·도보 길찾기만 공개하고 대중교통 경로 API 는 제공하지 않는다(2026-09 확인).
- **구현 규약**: 통근시간 제공자를 인터페이스로 두고 `car`(실연동) / `transit`(모의) 두 구현을 넣는다. **모의 값은 화면에 모의임을 표시**하고, 좌표 기반 결정적 함수로 만들어 같은 (매물, 근무지) 쌍이 항상 같은 값을 내게 한다(캐시·테스트가 흔들리지 않게). 관련 task: [T3.5](./tasks/t3.5-commute.md).
