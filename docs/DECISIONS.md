## ⏳ D1. API 스타일

- **제안**: REST형 Route Handlers로 통일(Server Actions 미사용), zod 4로 요청·응답 검증.
- **대안**: 변경(mutation)은 Server Actions, 조회는 Route Handlers 혼용.
- **트레이드오프**:
  - Route Handlers 통일 — Tanstack Query 훅과 1:1로 맞아떨어지고, "앱 웹뷰가 소비하는 API"라는 데모 서사가 명확. API 표면이 코드로 드러나 포트폴리오 리뷰에 유리.
  - Server Actions 혼용 — 폼 제출 코드가 간결하고 타입이 직결되지만, Query 캐시 무효화를 수동 관리해야 하고 API 계층이 데모에서 안 보임.
- **추천**: Route Handlers 통일.

## ⏳ D2. A/B 실험 소재 (1개 실운영)

- **제안**: `notice_cta` — 공개 고지서 페이지([§4](./specs/04-notice.md)) 하단 가입 CTA의 문구·배치 2안. 퍼널: `notice_view → notice_cta_click → signup_start → signup_complete`.
- **대안**: 환급 계산기 결과 화면의 신청 CTA / 매물 상세의 통근시간 버튼 노출 방식 등.
- **근거**: 고지서는 **미가입 세입자에게 도달하는 유일한 접점**이라 그로스(신규 유입) 스토리가 가장 강하고, 고지서 발송마다 노출이 생겨 데모 데이터 만들기도 쉬움.
- **추천**: `notice_cta`.

## ⏳ D3. 서류 업로드 저장소 (환급 신청)

- **제안**: Vercel Blob — 배포 환경과 통합이 간단, 무료 티어로 충분.
- **대안**: ① 파일 저장 없이 메타만 DB 기록(구현 최소, 대신 어드민 심사 화면의 서류 뷰어가 껍데기가 됨) ② AWS S3(과함).
- **추천**: Vercel Blob.

## ⏳ D4. 마스터 매칭 방식

- **제안**: **pull 피드** — 마스터가 자기 업종+활동반경 내 REQUESTED 의뢰를 피드로 조회하고 견적 제안.
- **대안**: **push 타겟팅** — 중개 매칭([§8](./specs/08-brokerage.md))처럼 의뢰 생성 시 대상 업체를 선정해 발송(타겟 테이블 필요 → 스키마 추가).
- **근거**: 업체가 일감을 찾아다니는 실제 UX에 부합하고, 중개 매칭(push)과 패턴이 달라져 데모에 매칭 패턴 2종을 보여줄 수 있음. 현재 스키마도 pull 기준(타겟 테이블 없음).
- **추천**: pull 피드.

## ⏳ D5. 웹(모바일) 셸

- **제안**: 최대폭 480px 중앙 정렬 + 활성 프로필별 하단 탭바([§1](./specs/01-auth-profile.md)) — 앱 웹뷰 가정을 명확히.
- **대안**: 반응형 풀와이드(데스크톱에서도 넓게).
- **추천**: 480px 셸. 데스크톱 접속 시 좌우 여백에 서비스 소개를 두는 변형도 가능.

## ⏳ D6. Phase 순서

- **제안**: 임대인 코어(§2·3·4) → 세입자 결제·환급·민원(§5·6·9전반) → 매물·중개·통근(§7·8) → 커뮤니티·실거래가(§10·11) → 마스터(§9후반) → 그로스 마무리(§12·13). [PLAN.md](./PLAN.md#구현-순서-제안--피드백-대기) 표 참조.
- **대안**: 비주얼 임팩트 기능(지도 탐색·통근시간)을 앞당겨 초반에 볼거리 확보.
- **근거**: 수납·계약 데이터가 결제·고지·환급·민원의 기반이라 의존 순서상 임대인 코어가 먼저. 매물·통근은 외부 키 대기와도 맞물림.
- **추천**: 제안 순서 유지.
